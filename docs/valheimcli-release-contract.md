# ValheimCLI fork and release contract

ValheimTesting supports the maintained [ValheimCLI fork](https://github.com/tvongaza/valheimCLI) as a release dependency. An upstream merge is not needed to publish ValheimTesting. The fork owns the transport protocol, the default game-side plugin with all built-in commands, and the extension API. This repository builds the fork's `Valheim.Cli.Testing` source unchanged into `Valheim.Testing.Cli` and owns that NuGet package's version and publication. [`cli-dependency.json`](../cli-dependency.json) is the single source pin for both the transport build and the game-side plugin bundle. [`loader-dependency.json`](../loader-dependency.json) pins the loader shipped for disposable installs.

The host-side `Game` package uses the transport's `ValheimClient` connection, completion support, command timeout, state-change subscription and `CommandResult` fields (`Ok`, output and error). `GameActor` requires `cli_expect` before every action and `cli_extensions` to discover schema-1 commands. `CliCapabilities.Toolkit` lists all built-in commands the toolkit itself calls: joining and hosted rounds, teleport signals, support readings and waits, and terrain, surface, paint and grid probes. The release contract checks every one against the pinned `valheimCLI.dll`. A scenario may require more commands from its own adapter; its plan names them so the installed set is checked before launch and again live before use. Missing commands, unsupported result versions and failed strict pins stop the run before its action.

## Move the fork pin

1. Review the fork commit and its single-plugin bundle. Update the commit and bundle URL/SHA-256 together in `cli-dependency.json`. Record any new built-in capability that the toolkit itself now requires in its owning `Game` API, rather than making the release manifest an independent list. Update the pinned loader only if a reviewed BepInExPack changes.
2. Mark the moved transport as a local build: set the Cli `packageVersion` in that file (Game's exact Cli reference reads it) to the current version with `-candidate.<first 7 hex of the fork commit>`. A local feed or NuGet cache may hold the published bytes of the old version, so the moved transport never reuses it. The release preparation (`dotnet run scripts/pins.cs -- bump`, [Contributing](../CONTRIBUTING.md#release-packages-maintainers)) gives the Cli, Game and every package that embeds or references them a version NuGet.org has never served; `release.yml` refuses a candidate, or a transport version NuGet.org already serves from another fork commit. Do not edit the published-version snippets before NuGet.org serves the new versions.
3. Run `sh scripts/bootstrap-cli.sh` on macOS/Linux or the Windows command in [CONTRIBUTING.md](../CONTRIBUTING.md#set-up-and-validate-locally), then `dotnet run scripts/validate.cs`. The Windows entrypoint needs only built-in Windows PowerShell. The bootstrap checks both NuGet caches before restore, exports only the pinned fork commit, builds the transport and checks the downloaded plugin and loader hashes. Validation builds all packages and runs a fresh local-feed consumer. Review the diff and the fork's license/provenance. For a changed in-game command, run one bounded native smoke with strict pins: prove the exact default plugin loads, its capability schema holds, and a missing or mismatched capability is refused before the scenario mutates the world.
4. Merge the reviewed change, then release from a tag on `main`. `release.yml` publishes the packages, waits for the NuGet.org-only consumer, and writes `release-contract.json` from the **NuGet.org repository-signed package bytes**. NuGet.org adds a signature after upload, so these hashes differ from the unsigned files attached to the GitHub release and hashed in `SHA256SUMS`; both sets are correct for their named bytes. The contract refuses a transport whose published nuspec names another fork commit or a `Game`/`GameSessions` pair with the wrong exact dependency. The GitHub release includes that contract: every package version and signed SHA-256, fork commit and bundle hash, loader version/hash, default commands, required built-in capabilities and compatible `Game`, `GameSessions` and `NativeSmoke` versions. If a transient NuGet.org download fails after publication, re-run the failed workflow jobs; the publish job is not repeated.
5. After publication, run `dotnet run scripts/pins.cs -- record` as described in [Contributing](../CONTRIBUTING.md#release-packages-maintainers). This moves copyable docs and examples to the published versions in one PR.

`release-contract.json` is a release record, not permission to trust an arbitrary installed plugin. Owned runs still compare the staged default plugin with its capability manifest and strict pin, then check the live `cli_extensions` reply. Attached clients must be explicitly pinned too. A test may use an earlier coherent fork build if its required commands and schemas hold, but a release never silently mixes a transport from one fork commit with a game-side plugin from another.
