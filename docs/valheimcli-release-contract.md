# ValheimCLI fork and release contract

ValheimTesting supports the maintained [ValheimCLI fork](https://github.com/tvongaza/valheimCLI) as a release dependency. An upstream merge is not needed to publish ValheimTesting. The fork owns the transport protocol, in-game core and command packs. This repository builds the fork's `Valheim.Cli.Testing` source unchanged into `Valheim.Testing.Cli` and owns that NuGet package's version and publication. [`cli-dependency.json`](../cli-dependency.json) is the single source pin for both the transport build and the game-side plugin bundle. [`loader-dependency.json`](../loader-dependency.json) pins the loader shipped for disposable installs.

The host-side `Game` package uses the transport's `ValheimClient` connection, completion support, command timeout, state-change subscription and `CommandResult` fields (`Ok`, output and error). `GameActor` requires `cli_expect` before every action and `cli_extensions` to discover schema-1 commands. `CliCapabilities.Toolkit` lists all ValheimCLI pack commands the toolkit itself calls: joining and hosted rounds from Standard, teleport signals, support readings and waits, and terrain, surface, paint and grid probes from World Tools. The release contract checks every one against the pinned bundle. A scenario may require more commands from its own adapter; its plan names them so the installed set is checked before launch and again live before use. Missing commands, unsupported result versions and failed strict pins stop the run before its action.

## Move the fork pin

1. Review the fork commit and its matching core, Standard, World Tools and Observe bundle. Update the commit and bundle URL/SHA-256 together in `cli-dependency.json`. Record any new pack capability that the toolkit itself now requires in its owning `Game` API, rather than making the release manifest an independent list. Update the pinned loader only if a reviewed BepInExPack changes.
2. Give `Valheim.Testing.Cli` a **new packageVersion** in that file. NuGet.org will not replace an existing version, even if source or bundle bytes changed. Bump `Game` and its exact Cli dependency, then `GameSessions` and `NativeSmoke` when their embedded or referenced dependency changes. Do not edit the published-version snippets before NuGet.org serves the new versions.
3. Run `sh scripts/bootstrap-cli.sh` on macOS/Linux or `pwsh -File scripts/bootstrap-cli.ps1` on Windows, then `dotnet run scripts/validate.cs`. The bootstrap checks both NuGet caches before restore, exports only the pinned fork commit, builds the transport and checks the downloaded plugin bundle and loader hashes. Validation builds all packages and runs a fresh local-feed consumer. Review the diff and the fork's license/provenance. For a changed in-game command or pack, run one bounded native smoke with strict pins: prove the exact core and packs load, their capability schema holds, and a missing or mismatched capability is refused before the scenario mutates the world.
4. Merge the reviewed change, then release from a tag on `main`. `release.yml` publishes the packages, waits for the NuGet.org-only consumer, and writes `release-contract.json` from the **NuGet.org repository-signed package bytes**. NuGet.org adds a signature after upload, so these hashes differ from the unsigned files attached to the GitHub release and hashed in `SHA256SUMS`; both sets are correct for their named bytes. The contract refuses a transport whose published nuspec names another fork commit or a `Game`/`GameSessions` pair with the wrong exact dependency. The GitHub release includes that contract: every package version and signed SHA-256, fork commit and bundle hash, loader version/hash, core commands, required pack capabilities and compatible `Game`, `GameSessions` and `NativeSmoke` versions. If a transient NuGet.org download fails after publication, re-run the failed workflow jobs; the publish job is not repeated.
5. After publication, update `toolkit-versions.json` and run `dotnet run scripts/pins.cs -- write` as described in [Contributing](../CONTRIBUTING.md#release-packages-maintainers). This moves copyable docs and examples to the published versions in one PR.

`release-contract.json` is a release record, not permission to trust an arbitrary installed plugin. Owned runs still compare staged files with their capability manifest and strict pins, then check the live `cli_extensions` reply. Attached clients must be explicitly pinned too. A test may use an earlier coherent fork build if its required commands and schemas hold, but a release never silently mixes a transport from one fork commit with game-side packs from another.
