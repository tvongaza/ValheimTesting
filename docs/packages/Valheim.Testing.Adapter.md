# Valheim.Testing.Adapter

*Assistant-written (Claude).*

`Valheim.Testing.Adapter` is a source package compiled into a mod's **test adapter**: a small BepInEx plugin, installed only in test runtimes, that registers the mod's test commands with ValheimCLI's extension API. A mod's owned server runs need one, because `OwnedServerSession` proves it started that very server by reading the adapter's `session` capability (token, process ID, save root, dedicated, readiness). The adapter references ValheimCLI and the game, so this repository builds none of it; the package ships the helpers mods' adapters kept copying, and the read-only observations the runners in [`Valheim.Testing.Game`](Valheim.Testing.Game.md) read. The mod itself never references this package, and production mods gain no testing dependency.

**Example:** [FullLifecycle's adapter](../../examples/FullLifecycle/ExampleMod.TestAdapter/Plugin.cs) is the whole pattern: registration, the session capability and the Harmony census. The [native acceptance suite's adapter](../../tests/Valheim.Testing.NativeAcceptance/AcceptanceMod.Adapter/Plugin.cs) registers most of the observations below and one fixture command. The released version to pin is in the [package table](../getting-started.md#package-versions-and-feeds); build the adapter against the exact ValheimCLI build you install, with [tools/game-references](../../tools/game-references/README.md).

## Registration and the session capability

`TestExtension.Register(id, version, tokenVariable, modReady, registered, logError, commands...)` waits for ValheimCLI's extension API, then registers the mod's extension with the `session` capability and any test commands of its own. Run it as a coroutine from the adapter plugin's `Start` and dispose the registration in `OnDestroy`:

```csharp
private IEnumerator Start() => TestExtension.Register("mymod.testing", "0.1.0", "MYMOD_TEST_SESSION_TOKEN",
    () => MyMod.Ready, registration => _registration = registration, Logger.LogError,
    ZonePresence.Command(), PlayerCustomData.Command(), ContentCensus.Command());
```

The session reports complete when the world is up and `modReady` returns true, and reports `acceptingConnections` separately: a dedicated server opens its game socket only when world generation finishes, on a first boot about 17 s after the world has loaded, and a join before that times out. `OwnedServerSession.WaitUntilJoinable(server, capability, timeout)` waits for it; call it just before the first join so the wait overlaps other work (server-side steps, an owned client's launch) instead of lengthening startup. `TestExtension.DevcommandsFlag()` reads the raw devcommands flag that ValheimCLI's extension gate uses. If the extension API does not become ready within `TestExtension.ApiWaitSeconds` (30 s), the adapter logs an error and stays inert.

## ValheimCLI's extension API

ValheimCLI owns the game-side extension API: registration and instance tokens, command roles, the devcommands and joined-client rules, the mutation gate, cancellation, cleanup and quiescence probes, result limits and `cli_extensions` discovery. Its reference is ValheimCLI's [extension API guide](https://github.com/tvongaza/valheimCLI/blob/80fb6cefcc99d7737ec9f9b589eff4d16e2fc5e3/docs/testing-toolkit.md#extension-api-v1), at the commit the released `Valheim.Testing.Cli` was built from; this repository does not keep a copy. What the toolkit adds:

- Keep the ValheimCLI core in `BepInEx/plugins` and only the test adapter in `BepInEx/scripts` (or both in `plugins`), and never load a second ValheimCLI assembly with the adapter.
- Arguments are single tokens; an adapter validates its own grammar. The API is a contract, not a sandbox, and cannot roll back arbitrary terrain, spawn or save effects: tests serialize their own console mutations.
- An adapter may keep established console command names as compatibility commands with ValheimCLI's own `ConsoleModuleHost`, which dispatches them through the extension host with the same role, world, devcommands, client opt-in, cancellation and mutation-gate checks. How the host dispatches them and why extension mutations read the raw devcommands flag is in the same guide.
- An adapter that patches unpatches only its own Harmony ID (`harmony.UnpatchSelf()`), never `Harmony.UnpatchAll()`, which also removes ValheimCLI's patches and with them the run's transport.

## Helpers and commands

Each helper checks the conditions under which the game would silently do nothing, and throws instead. The read-only commands are observations a runner in `Valheim.Testing.Game` reads; register them with `TestExtension.Register` on the side that needs them. Status says what has run: **native** on Valheim 1.0.16 through the example named, **unit-tested** (no game types), or **compile-checked** only (below).

### The quit-log flush

BepInEx 5.4's disk log flushes every 2 seconds and is not flushed again when the game quits, so lines a plugin logs while the game quits can be missing from the kept log the teardown [log scan](Valheim.Testing.Game.md#log-scan-at-teardown) reads. Call `QuitLogFlush.Enable()` in the adapter's `Awake`, `QuitLogFlush.Quitting("<adapter> OnApplicationQuit")` in its `OnApplicationQuit` and `QuitLogFlush.Disable()` in its `OnDestroy`. From the first quit signal it flushes BepInEx's disk logs, then flushes after every line any plugin logs, and it logs `Quit log flush armed by <signal>.` once. Before the quit it does nothing, and it never changes BepInEx's configuration or touches Harmony. Call `Quitting` from `OnApplicationQuit`, not from `OnDestroy`: a script reload destroys a plugin without quitting. The state is process-wide: reloads and several mods' adapters share one listener, any load's quit signal arms it, and only the last enabled load's `Disable` removes it. In the native check, with the helper every server boot and the client's clean stop kept both of the QuitLog probe's quit warnings and ValheimCLI's `Command server stopped`; without it, one boot in six lost the last two. What it cannot save: a line logged after the process stops running managed code, or anything after a kill.

## What CI checks

`Members`, `FixtureGate` and `ResultBudget` use no game types and have unit tests. The rest compile in CI in `tests/Valheim.Testing.Adapter.CompileCheck`: the sources as a consumer compiles them (net48, C# 10, nullable, warnings as errors) against the real HarmonyX 2.9.0 that BepInEx 5.4.23 ships and against declared signatures of the Unity, game, BepInEx and ValheimCLI members they use. That proves they compile and call those signatures; it does not prove the game still has them or that the private members they reflect on exist, which only a native run shows. That is what the **compile-checked** status means.

## Limits

An adapter observation answers for the process it runs in: a server's census says nothing about a client. Observations are read-only except the fixture commands, which run only when `FixtureGate` allows them. Nothing here grants client admin rights or bypasses ValheimCLI's devcommands gate.
