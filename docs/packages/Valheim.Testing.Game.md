# Valheim.Testing.Game

*Assistant-written (Claude).*

`Valheim.Testing.Game` (net10.0) drives the real game from outside it: named actors over ValheimCLI's transport with strict environment pins, event-driven waits, owned server and client sessions it starts and stops, plan rules and client rounds, this machine's environment inventory, typed observations, and JSON/JUnit reports. A run of several game processes, or one on another machine (`GameSession`, `PinnedServerRun`, game hosts over SSH or a container, Steam-account leases, the run journal's recovery), is [`Valheim.Testing.GameSessions`](Valheim.Testing.GameSessions.md)'s, built on this package. Use it for the few checks that need the game: save and restart, replication to a client, what a second process registered, what the log says. Keep decisions and formats in unit tests with [`Valheim.Testing`](Valheim.Testing.md) and [`Valheim.Testing.Doubles`](Valheim.Testing.Doubles.md). A mod's game-side half, the test adapter, compiles [`Valheim.Testing.Adapter`](Valheim.Testing.Adapter.md). The transport is [`Valheim.Testing.Cli`](Valheim.Testing.Cli.md), a dependency of this package.

**Example:** [FullLifecycle](../../examples/FullLifecycle/README.md) uses one small feature at every layer: unit tests, integration tests of the scenario against scripted replies, and native runs with an owned server and owned or attached clients through save, restart and rejoin. The released version to pin is in the [package table](../getting-started.md#package-versions-and-feeds). For a one-command disposable mod-load check, use the `valheim-test` tool ([NativeSmoke](Valheim.Testing.NativeSmoke.md)).

Topic pages for this package: [evidence linked from `result.json`](../evidence.md), [terrain site snapshots](../terrain-site-snapshots.md), [area object snapshots](../area-object-snapshots.md), [pinned world dumps](../world-dump-contract.md), [pinning a BepInEx loader](../bepinex-loader-package.md), [native dependency resolution](../native-dependency-resolution.md), [debugging a mod load or conflict](../debugging-mods.md), [optional authored fixtures](../fixture-authoring.md) and the [runtime hygiene checklist](../runtime-hygiene.md). Each type's members are in the [API reference](https://tvongaza.github.io/ValheimTesting/).

A successful fake-transport run is an orchestration test, not an in-game pass, and an input replay round-trip proves capture plumbing, not the game's terrain implementation.

## On one Windows PC

The usual setup is one Windows PC with Valheim installed through Steam. Everything runs on that machine: no inventory file, SSH or second host. Once both installs have BepInExPack_Valheim (valheim-test brings its pinned ValheimCLI bundle, or takes one from `VALHEIMCLI_BUNDLE`), `valheim-test server-load --mod YourMod.dll` is the whole command to check that a mod loads on a dedicated server and that a clean client joins it. The machine's own Steam installs, ports and folders are detected; `valheim-test env list` prints what it found and what it assumed, and names every path it tried for anything missing ([this machine, with no file](#this-machine-with-no-file)).

1. **Install** Valheim and the free **Valheim Dedicated Server** tool (Steam app 896660) through Steam, and keep the Steam client running and signed in; an owned client needs it, the dedicated server does not.
2. **Make test copies, never use the Steam folders themselves** (the FullLifecycle example's own runtimes; valheim-test makes its copies and stages its pinned ValheimCLI itself). A server runtime: a copy of the dedicated server folder with BepInExPack_Valheim, ValheimCLI's core and the packs the test uses (Standard, World Tools), your mod and its [test adapter](Valheim.Testing.Adapter.md). A client install: a copy of the game folder with BepInEx and ValheimCLI, and your mod when the client should have it. Give each its own ValheimCLI port. Use a disposable world and a disposable local character, never your own.
3. **Run the example**: FullLifecycle's native session test (`dotnet test --filter Category=Native`, with its private `session.json` and plan beside the test project) starts an owned server and an owned client on this PC, joins, saves, restarts only that server and rejoins, then stops both and scans their logs ([run the layers](../../examples/FullLifecycle/README.md#run-the-layers), [prepare the native session](../../examples/FullLifecycle/README.md#prepare-the-native-session)).

The runner copies the runtime and world again for every run and removes its runtime copy afterwards; it stops only the processes it started. What comes later, Linux servers and containers, macOS and, in [`Valheim.Testing.GameSessions`](Valheim.Testing.GameSessions.md), servers and clients on other machines and sessions with several clients, is optional: start there only when one PC is not enough ([launching servers and clients](#launching-servers-and-clients), [game hosts and the environment inventory](Valheim.Testing.GameSessions.md#game-hosts-and-the-environment-inventory)).

### What a test runtime holds

A clean test runtime is BepInEx core plus the plugins below, with an empty `BepInEx/patchers` folder: a preloader patcher left behind by a removed mod breaks the game's types before any plugin loads, and the pinned runner refuses a patchers folder that is not the pinned one (`runtimePins` and `installPins` `patchers`), naming what it holds. Keep the ValheimCLI core in `plugins` and put each optional pack in `plugins` **or** `scripts`, never both ([ValheimCLI's pack guide](https://github.com/tvongaza/valheimCLI/blob/9e8ca679298e559e995ab5b04ef84b782b15a0ad/docs/command-packs.md)); an older monolithic ValheimCLI and extracted packs cannot be mixed.

| Component | Dedicated server | Client |
|---|---|---|
| ValheimCLI core | Yes, in `plugins` | Yes, in `plugins` |
| Standard pack | Save and session commands | Character, session and protection commands |
| World Tools pack | Terrain and world observations | Terrain, collider, paint and player observations |
| Your mod and its test adapter | Yes | Yes, or pinned `absent` when the claim is that a client without the mod works |
| Reflection pack | Only if the test calls `cli_call` | Optional |
| Capture pack | Optional | Only for clutter controls |
| ScriptEngine | Only for reload tests | Only for reload tests |

The strict pins name every loaded plugin by MD5 and the world by UID, one `key=value` per line; `cli_manifest` reports the loaded plugins' hashes, `cli_world` the world's identity and `cli_extensions` the capabilities. An illustrative client file, not usable pins:

```text
worlduid=YOUR_FIXTURE_WORLD_UID
valheimCLI.valheimCLI=ACTUAL_CORE_MD5
valheimCLI.standard=ACTUAL_STANDARD_MD5
valheimCLI.worldtools=ACTUAL_WORLD_TOOLS_MD5
example.mymod=absent
```

List every other loaded plugin too, ScriptEngine and any further pack included; on the server, pin the mod and its adapter by their real MD5s instead of `absent`.

Plugin MD5 pins and the plan's SHA-256 input manifests serve different purposes; one does not replace the other. `cli_expect` cannot see the game build or BepInEx itself, so the pinned runner pins those on disk ([pins and the opt-out](#pins-and-the-opt-out)). For persistence, check the **same** independently declared expectations before and after a confirmed save, a server restart and the client's rejoin, and run a discriminating negative expectation too; never widen a tolerance to make a fixture pass.

## Actors, fixtures and reports

A `GameActor` wraps the existing transport; it never owns/stops the attached process. Verify `cli_expect` pins before using an actor (the only alternative is the explicit opt-out in [Pins and the opt-out](#pins-and-the-opt-out)). Require a capability/version, issue a mutation once, then poll its read-only observation. Unknown outcomes are failures, not permission to resend. Keep the command timeout below the overall scenario allowance: a synchronous read cannot be forcibly interrupted by an observation deadline.

`WorldFixture.Copy` requires a hash manifest, refuses links and unexpected files, verifies copied bytes and creates its own new directory (`CopyAsFound` records the hashes instead, for an explicitly unpinned run only). It deletes only that copy; `Preserve=true` keeps it for debugging. Stop the owned game BEFORE disposing its world fixture. It does not own accounts, characters, ports or remote machine reservations. Those stay with the operator.

`ScenarioReport` records outcomes and teardown failure in JSON/JUnit, with the evidence each step attached ([evidence](../evidence.md)). Use a unique output directory per run; include fixture/build/config hashes in `Provenance`. Output may contain player/world data; inspect before publishing. Do not include credentials in fixture configuration or logs.

## Strict pins from tests

Use `valheim-cli --expect-strict /private/pins.txt ...` when invoking the executable. Its flag is **`--expect-strict`**, not a global `--strict`. YAML plans can instead set `game.expect` and `game.expectStrict: true`. The underlying game command is `cli_expect --strict key=value ...`.

For library consumers, `GameActor.VerifyEnvironment` validates and normalizes supplied expectations to strict mode even if the caller omitted the switch. Every subsequent command rechecks those same pins before dispatch; drift invalidates the actor and blocks the action. `Execute` returns a `GameReply` and, by default, requires it accepted: the transport completed **and** no line is a known refusal (the game's `That command is a cheat`, `Error executing command`, `Unknown command`, or a ValheimCLI `ERROR:` line), because a refused console command still completes on the transport. Read the reply with `Line(prefix)`, `Lines(prefix)` and `RequireLine(prefix, failure)`; acceptance supplements a step's semantic check, it never replaces one. `Execute(..., requireAccepted: false)` lets a test inspect an expected refusal but cannot bypass a pin failure. The transport itself is low-level: use an actor for test actions and observations.

Strict mode rejects unlisted loaded plugins/worlds; it does not make `any` an exact build pin. Supply reviewed full hashes and the intended world identity. The preflight is a separate round trip, not an atomic lock on game state. For dispatch-time enforcement as well, configure the game's existing `[Expectations]` guard; tests never disable it.

Reload tests must provide a pins file and explicitly advance the changed plugin's expected hash using the artifact they intend to install, then require absence on removal. Only `cli_expect --strict` is rechecked while that known transition settles; pass `WaitForEnvironment` the reload's own log line (a `LogWait`) so it rechecks when the plugin has loaded rather than on a timer. Repin after world changes. The owned-server startup identity probe is a narrow read-only bootstrap exception while world loading is incomplete; it checks token/PID/save-root identity, then verifies strict pins before returning an actor.

## Capabilities and extension reload

`GameActor.RequireCapability`, `Invoke` and `Observe` discover a command with `cli_extensions` and reject a stale instance token; `ObserveComplete` rejects an incomplete measurement. The World Tools pack's `valheim.world/terrain x z generator|loaded-ground` observation reports `complete: false` and a null height where no heightmap is loaded, which stays incomplete, never a zero.

`ExtensionReload` and the [ReloadCheck](../../tools/reload-check/README.md) tool, with its probe, check a replacement end to end: new instance, removed command refused, old resources cleaned up, core and connection unchanged. `ExtensionReload` holds ReloadCheck's steps: `Install(artifact, deployed)` copies beside the deployed DLL and renames over it; `WaitForReplacement(actor, id, version, replacing, timeout, interval)` waits for a new live instance at that version; `WaitForRemoval` waits until none is live. Both re-read `cli_extensions`, which is read-only, since a registration announces itself nowhere else.

## Waiting

Wait for the event that announces a change, not for time to pass. Every wait takes an explicit, finite timeout; there is no default. Expiry throws `WaitTimeoutException` (a `TimeoutException`) and an early failure throws `WaitFailedException` (an `InvalidOperationException`). Both report what was awaited, the elapsed time and the last thing seen.

| Source | Wait | Notes |
|---|---|---|
| A log line | `LogWait` | Opens at the file's current end (or a given byte offset), so earlier lines never match; the file may not exist yet. Matches complete lines only, checks optional failure patterns first, and re-reads a truncated or replaced file from its start. A `FileSystemWatcher` wakes the wait; a 2 s re-read covers filesystems that drop watcher events (network shares, container mounts). |
| A process exit | Raced for you | The owned server and client sessions race every startup stage against their process's exit, so an exit ends startup at once with its exit code instead of at the deadline. For a process you start yourself, `Process.WaitForExitAsync` with a token from `new CancellationTokenSource(timeout)`. |
| A game state | `StateWait` | Subscribes to ValheimCLI's state pushes on a connection used for nothing else, asks the current state once, then awaits `STATE_CHANGED` pushes with a pending read; nothing is sent while it waits. A push that arrives during the question counts. A dedicated server's loaded world is `InWorldNoPlayer`. A state is not mod readiness. The transport keeps no history: a wait sees the current state and pushes from its own subscription on, not pushes sent before it connected. |
| No event | `ObservedWait.Until` / `UntilAsync` | The one polling fallback: re-observes a read-only source at most an interval apart until it matches, for example an adapter's `complete` flag. An optional `fails` ends the wait at once with a reason, `describe` names the last observation on expiry, and an optional `changed` event (such as a `LogWait` for the line the change writes) ends each pause early. The token cancels the pause too. |

```csharp
using var log = new LogWait(Path.Combine(runtime, "BepInEx", "LogOutput.log")); // before launching
// ... start the server ...
await log.WaitAsync(StartupEvents.CliListening, TimeSpan.FromMinutes(5), [LogWait.Literal("[Fatal")]);
```

`OwnedServerSession` waits on these when given `Events = new StartupEvents { CliLog = ..., Failures = StartupEvents.StartupFailures, States = () => StateWait.Connect(host, port) }`: no connection before this boot's `Command server listening` line, then the world-loaded push, then the session probe. The process exit is always watched: a server that exits during startup fails it at once with its exit code and the last log line. When that boot wrote nothing to its BepInEx log, the failure says so and points at Unity's player log (`Player.log` or the `-logFile` file) and at security software, a known cause of a game stopped before BepInEx starts. `StartupFailures` ends startup at once on:
- BepInEx's own "Could not load [" and "Error loading [" lines (`BepInExPluginLoadFailures`), so a pinned runtime with a missing dependency fails at once instead of at the readiness deadline;
- a `TypeLoadException`, `MissingMethodException` or `MissingFieldException` in a BepInEx warning, error or fatal line, or in an exception line that starts with its name (`System.TypeLoadException: Could not load type of field 'ZDO:...'`, as a leftover preloader patcher causes), and ValheimCLI's packs logging `CLI core 1.1 is not ready.` (`RuntimeLoadFailures`). An info or debug line that only mentions one of these exceptions, such as a mod's handled soft dependency, does not end startup.

A log failure carries the matched line and the five lines read before it (`WaitFailedException.Context`, also in its message). `DedicatedStartupEvents` and owned `ClientSession` launches use `StartupFailures`. Only the adapter's own readiness, which has no event, is re-probed at the poll interval. The startup deadline bounds every step, including a connection or command that blocks: each races the process exit and the time left, a connection that completes after startup gave up is closed, and the final pin verification gets only the time left (at most the command timeout). Without `Events`, connecting keeps its bounded retries. `GameActor.WaitForEnvironment` takes an event too, for example `(left, token) => log.WaitAsync(loadLine, left, cancellation: token)`: it rechecks the pins when the reload's line appears, not every 200 ms.

`StateWait` closes its connection when a wait expires or is cancelled, because the abandoned read leaves the stream's position unknown; later waits on that instance fail, so connect a new one. A failure state, a closed connection or a line that is not a push fails the wait at once.

World entry has one special case: a mod may hold Unity's main thread while ValheimCLI's socket still answers. During a bounded world-entry wait, if ValheimCLI explicitly reports that a **read-only** command timed out before it started, `GameActor` reads `STATUS` on a separate connection. A stale `mainThreadIdleMs` means the game is busy, so the reader waits within the original start/join deadline and sends the observation again after the heartbeat resumes. No mutation is retried. A missing STATUS reply fails immediately; a fresh heartbeat paired with an unstarted timeout is reported as a harness fault. `ClientRounds` writes the longest observed frame age as `clientMainThreadStallMs` and the last busy note, if supplied, as `clientBusyNote` in the private result provenance. The heartbeat proves liveness, not that a mod's generation succeeded.

## Owned server session

`OwnedServerSession` owns one dedicated-server process for a test: `DirectServerProcess` starts it on this machine (or, in `Valheim.Testing.GameSessions`, `HostServer` on a game host), and `RecordingTransport` records every command it sends. Each mod provides its own namespaced session capability, for example `other.mod.tests/session`, through its [test adapter](Valheim.Testing.Adapter.md#registration-and-session-identity); the package has no dependency on any mod.

The launch callback receives a fresh unpredictable token for every boot. Pass it to your prepared child process, and have your adapter report the exact token, PID, actual save root, `dedicated` and `complete`, under source `owned-test-session`. The session requires a valid extension result envelope from the configured owner, verifies process/save identity, then strict environment pins. Define `complete` to include your mod's readiness. Startup waits on events (see [Waiting](#waiting)) and re-probes only incomplete readiness observations, never mutations. Stop/restart owns only that process and refuses to start a replacement after failed cleanup. Per-boot logs preserve prior startup evidence. It does not own accounts, machine reservations or external processes.

## Pins, stopping and the log scan

What every owned run here and in [`Valheim.Testing.GameSessions`](Valheim.Testing.GameSessions.md) shares: the pins a runtime is checked against, how an owned process is stopped, and the scan of its logs at teardown ([the pinned server runner](Valheim.Testing.GameSessions.md#pinned-server-runner) applies all three).

### Pins and the opt-out

Strict pins are the default everywhere and the recommended mode. Each pin protects against a run that passes on something other than what you meant to test:

| Pin | Where | Protects against |
|---|---|---|
| `worlduid` | plan `pins`, checked in game by `cli_expect --strict` before every command | another world, or a world transition the test did not expect |
| plugin MD5s, `absent` | plan and client `pins`, same check | a stale or different mod build, an extra plugin, a mod that should not be there |
| runtime and world SHA256 manifests | plan `runtime` and `world` | a changed fixture: any file in the runtime or save |
| `game` | `runtimePins`, client `installPins` | another game build that changes the game's code: a hotfix, or the `default_old` / `default_pre1_0` branches |
| `loader` | same | another BepInEx, BepInExPack or Doorstop build (Valheim 1.0 shipped a new pack), or a Doorstop proxy or configuration replaced on its own, which starts the game without BepInEx |
| `patchers` | same | a preloader patcher a removed mod left behind, or another build of one the run needs |

ValheimCLI's `cli_expect` knows plugins and the world only, so the game build and the loader are pinned on disk before launch (`InstallPins`). Each value is the SHA256 of a listing: one line per file, `<sha256>  <relative path>` with `/` separators, ordered by path, as `sha256sum` prints it; Finder's `.DS_Store` and AppleDouble `._*` files (which a copy through macOS adds) are left out, and an empty or absent folder hashes the empty listing. `game` lists every `assembly_*.dll` in the game's Managed folder (`<executable>_Data/Managed`, or `Valheim.app/Contents/Resources/Data/Managed` on macOS): `assembly_valheim`, `assembly_utils`, `assembly_guiutils`, `assembly_postprocessing` and the rest of the game's own code, which exists in a copied runtime and in a client install and needs no Steam files. A build that changes only assets or Unity's own assemblies keeps the same `game` value. Steam's build id is not in the install (it is in Steam's `appmanifest_*.acf`, outside the game folder and absent from a runtime copy), `steam_appid.txt` holds only the app id, and the executable's version is Unity's. `loader` lists BepInEx's loader as one set, relative to the install's root: `winhttp.dll`, `doorstop_config.ini`, `libdoorstop.dylib`, and everything under `BepInEx/core` and `doorstop_libs` (`BepInEx/config/BepInEx.cfg` is configuration, which BepInEx rewrites, and is not part of it); a reviewed loader package's `BepInExLoaderPackage.Loader` is the same value for an install it is applied to. `patchers` lists the whole folder, subfolders included. `InstallPins.Of(path)` computes all three; a mismatch names what differs and the value found. Without the library, in the folder concerned: `find . -type f ! -name .DS_Store ! -name '._*' | sed 's|^\./||' | LC_ALL=C sort | while IFS= read -r f; do printf '%s  %s\n' "$(sha256sum "$f" | cut -d' ' -f1)" "$f"; done | sha256sum` (for `game`, list `ls assembly_*.dll` in the Managed folder instead of `find`; for `loader`, at the install's root, give `find` the paths `winhttp.dll doorstop_config.ini libdoorstop.dylib BepInEx/core doorstop_libs` instead of `.`, with `2>/dev/null` for those absent). The runtime manifest also covers these files, but a manifest regenerated after an update silently accepts the new build; `runtimePins` makes that a deliberate change. `FileHash` computes every hash: `FileHash.Sha256` for these pins, manifests and evidence, and `FileHash.Md5` for plugin pins, which stay MD5 because ValheimCLI's `cli_manifest` and `cli_expect` report and compare MD5. A link in a pinned folder or loader file is refused, locally as on another host.

**Computing the pins.** Every strict plan needs `runtimePins`, and an owned client section needs `installPins`; `ValidateServerPlan` and `ClientRunPlan.Validate` refuse a plan without them. Compute the values once with `InstallPins.Of(<runtime>)` and `InstallPins.Of(<client install>)` (or the shell listing above), review them, and add them to the plan: `"runtimePins": { "game": "...", "loader": "...", "patchers": "..." }`, and the same object as `"installPins"` in the client section. An attached client needs neither. `bepinexCore`, which pinned `BepInEx/core` alone, was replaced by `loader` (#295); a plan that still names it is refused with that instruction.

An owned client pins its install with `installPins`; the launch refuses a mismatch before anything starts. An attached client's install is its operator's and is not read, so its game build is not pinned: the game refuses a join only across network versions, which builds of one release usually share. Use an owned client when the client's build matters.

`"pinning": "none"` in a plan (or a client section) is the explicit opt-out, for trying the toolkit before keeping pins. It is never a default: an omitted `pinning` is `strict`, any other value is refused, and no environment variable sets it. An unpinned plan lists no `pins` or `runtimePins` (so nothing looks enforced that is not) and may leave out the fixture manifests, whose copies are then recorded as found (`WorldFixture.CopyAsFound`). The runner prints `WARNING: environment not pinned: ...` once the plan is read, records the runtime's `InstallPins` without checking them, and marks every report and evidence file: `result.json` (`Pinning: "none"` and provenance `environment`), `junit.xml` (an `environment` property and a skipped test case named `environment not pinned`), `input-hashes.json`, `boot-N.process.json`, the first line of `connection-N.jsonl`, and the result banner. The run can still pass. An unpinned client's actor runs without `cli_expect`, prints the warning, and marks `client-commands.jsonl` and `client-process.json`. For your own actors, `GameActor.VerifyEnvironment(EnvironmentPinning.None)` is the same opt-out (`Pinned` is then false until pins are verified again). A result without pins is not evidence for any particular build; pin it before you rely on it.

### Stopping owned processes

A killed game skips its own shutdown: nothing after the last confirmed save is kept, a crossplay server's PlayFab lobby stays active, and what mods do at quit never runs. So every owned process is first asked to quit, and killed only if it does not exit in time (`IOwnedProcess.StopCleanly(quit, kill)`, which returns a `ProcessStop`: `Clean`, `Killed` or `AlreadyExited`, with the exit code when known, the time taken and how it was asked):

| Process | Asked with | Waits (default) |
|---|---|---|
| Owned dedicated server, local (`DirectServerProcess`) | Linux and macOS: SIGINT. Windows: Ctrl+Break to the server's own windowless console when the runner was launched over SSH (whose inherited setting can ignore Ctrl+C); Ctrl+C otherwise | plan `quitSeconds` (120) |
| Owned dedicated server on a Linux host (`HostServerProcess`, GameSessions) | SIGINT, only while its start time still matches | plan `quitSeconds` (120) |
| Owned dedicated server on a Windows host (`HostServerProcess`, GameSessions) | Ctrl+Break to the exact server process's console, only while its start time still matches | plan `quitSeconds` (120) |
| Owned client (`ClientSession`) | Windows: its main window is closed. Linux and macOS: SIGTERM | `ClientSession.QuitTimeout` (60 s) |
| Client in a host's desktop session (`InteractiveClientProcess`, GameSessions) | Windows: its main window is closed; from an SSH session the window is in another session and cannot be closed, so it is killed. Linux: SIGTERM | as the caller passes |

The game then saves (a server its world, a client its profile), retires a crossplay lobby and exits if its shutdown handler runs. `quitSeconds: 0` kills at once. `OwnedServerSession.Stops` (and `ServerActor.Stops`) records every stop, restarts included; `PinnedServerRun` writes them to the report as `serverStops` (for example `boot-1 clean after 9.4 s (Ctrl+C, exit 0); boot-2 killed after 120.0 s (Ctrl+Break; no exit within 120.0 s)`) and prints a warning for each killed boot. A short `quitSeconds` belongs only to a disposable setup/load smoke that does not claim a save or lobby retirement; `NativeSmoke server-load` uses 20 s. Save/restart and crossplay runs retain their longer deadline and must verify the game's shutdown evidence. `ClientRounds` records the owned client's as `clientStop`. An ordinary run still passes after a kill, because the kill frees the process; a crossplay run does not (see [Crossplay](#crossplay-playfab)). `IOwnedProcess.Stop(timeout)` still kills at once, for callers that want that.

### Log scan at teardown

Many mod failures only log a warning, or appear long after startup. After the processes stop, `ScenarioReport.ScanLogs(logs, classifications)` reads each `RunLog` (a role, the kept copy's path and whether it is required) with `LogScanner` and records the `scan run logs` step and one `Logs` entry per file in `result.json`: every pattern's severity, count, first line number and first line. The step fails when a failure pattern matched or a required log is missing; warnings are only counted. `PinnedServerRun` scans, per boot, the BepInEx log (required), the Unity log (the copy of `{runtime}/toolkit-unity.log`, so pass `-logFile {runtime}/toolkit-unity.log` in the plan's arguments) and the process output (Unity's log on Linux without `-logFile`). A client opened with `session.OpenClient` adds its logs (its BepInEx log and `Player.log`) itself; a scenario adds any other log with `session.AddLog`.

| Pattern | Matches | Default |
|---|---|---|
| `harmony-unpatch-all` | HarmonyX "UnpatchAll has been called - This will remove ALL HARMONY PATCHES": a mod removed every mod's patches (not the skipped "Legacy UnpatchAll has been called AND DisallowLegacyGlobalUnpatchAll=true") | failure |
| `harmony-undefined-target` | HarmonyX "Undefined target method for patch method": the patched method does not exist. On the Valheim 1.0.16 Windows dedicated server (BepInEx 5.4.23.5, HarmonyX 2.9.0) `PatchAll` throws it, and only Unity's own log (`-logFile`) records it; BepInEx's log has the `accesstools-not-found` warning before it. To name the missing patch while the run goes on, use the [Harmony census](#harmony-census) | failure |
| `accesstools-not-found` | HarmonyX `AccessTools.*: Could not find ...`. On Valheim 1.0.16 (BepInEx 5.4.23.5, HarmonyX 2.9.0) this warning is the only line a `[HarmonyPatch]` on a missing method leaves. Mods also probe optional members this way; name those lines as expected (below) | failure |
| `missing-method`, `missing-field`, `type-load` | `MissingMethodException`, `MissingFieldException`, `TypeLoadException` | failure |
| `nre-remove-objects` | a `NullReferenceException` whose stack trace (up to a blank line or the next BepInEx header) has `ZNetScene.RemoveObjects` | failure |
| `rpc-method-missing` | the game's "Failed to find rpc method" for a per-object RPC without a handler | warning |
| `missing-prefab-hash` | the game's "Missing prefab hash: N": a saved object whose prefab is not registered in this process (a server-side mod's prefab on a client without it); logged again each time the scene tries to create it | warning |
| `missing-script` | Unity's own "The referenced script ... is missing" warning (asset bundle scripts not loaded) | warning |
| `shader-unsupported` | Unity's "Desired shader compiler platform N is not available in shader blob", "not supported on this GPU" and "Shader Unsupported" (magenta bundles on Vulkan or OpenGL clients; wording as in the Valheim-Modding wiki's [Valheim-Unity-Project-Guide](https://github.com/Valheim-Modding/Wiki/wiki/Valheim-Unity-Project-Guide)) | warning |
| `macos-apple-plugin-missing` | a `DllNotFoundException` whose stack trace has `Apple.GameKit.` or `Apple.Core.`: the macOS game's own GameKitWrapper and AppleCoreNativeMac plugins, which fail to load in the Unity log of every macOS client and dedicated server run (Valheim 1.0.16, native arm64 and Rosetta, with or without mods) while the game goes on | warning |
| `headless-server-graphics` | a dedicated server's own errors on its null graphics device (`GPU Device: 0000:0000`), by their whole text: "AsyncResourceUpload failed.", "This custom render path shader needs to have at least 1 passes.", "Could not find material Hidden/VideoDecode" and "Hidden/VideoComposite" ("Make sure the Video shaders are included in your build ..."), "Could not find video decode shader pass <name> in shader <not found>" and the game's timestamped "Failed to play intro cinematic". Every kept dedicated server boot on Valheim 1.0.16 (Unity 6000.0.75f1; Windows, Linux and macOS, with or without mods) logged 12 to 14 of them and no client log had one. Linux and macOS servers write them to the BepInEx log as `[Error  : Unity Log]` records, which would otherwise fail as `unknown-error`; the Windows server writes them only to its Unity log. Another error from the same systems, such as a mod's missing material, still counts as `unknown-error` | warning |
| `unity-exception` | an exception Unity printed that no pattern above names: a line that starts with the exception's type name (`NullReferenceException: Object reference not set ...`), outside a BepInEx warning or error record. `FirstFrame` is the first frame of its stack trace outside the runtime's own `System.`, `Mono.` and wrapper frames | failure |
| `unknown-warning` | BepInEx warning records that match no pattern above | warning |
| `unknown-error` | BepInEx error and fatal records that match no pattern above | failure |

Owned processes are asked to quit at teardown and killed only if they do not (see [Stopping owned processes](#stopping-owned-processes)), so after a clean stop the scan also sees what the game and its mods logged while shutting down, such as a mod calling UnpatchAll when the game closes (the usual case for that warning). After a kill that part is never written and cannot be counted; `serverStops` and `clientStop` in the report say which happened. Even after a clean stop, BepInEx 5.4's disk log may lack the last lines: it flushes every 2 seconds and is not flushed again when the game quits. On the 1.0.16 Windows server, a plugin's `OnApplicationQuit` and `OnDestroy` warnings (the native acceptance suite's QuitLog probe) were in the kept BepInEx log of one boot and missing from the next, although both quit cleanly within 3 s. Unity's own log (`-logFile`) is written as it goes and kept every quit line; plugins' lines do not go there. A test adapter closes the gap with the [quit-log flush](Valheim.Testing.Adapter.md#the-quit-log-flush), which flushes BepInEx's disk log after every line once the game starts to quit. Without the helper, a quit-time line the scan counts is evidence, and a missing one is not proof that nothing was logged.

A plan's `"logScan": { "rpc-method-missing": { "severity": "Failure", "reason": "..." } }` changes a severity for that run; the reason is required and recorded beside the count. `"expected": ["..."]` names lines the run expects instead: a line of that pattern containing one of the texts is counted apart (`Expected`, first as `FirstExpected`) and never fails, while every other line of the pattern still counts. For `unknown-error`, expected text must instead be the **entire exact BepInEx Error or Fatal header line**, for example `"unknown-error": { "expected": ["[Error  :   BepInEx] Unable to start Unity log writer"], "reason": "This loader reports a known environmental log-writer limitation" }`. The whole `unknown-error` category cannot be downgraded. Name a mod's deliberate lookup (`"accesstools-not-found": { "expected": ["name m_optionalField"], "reason": "probes a field only newer game versions have" }`) rather than making the whole pattern a warning, which would hide a patch whose target is gone. An absent log has no counts (absent is not zero). A missing required BepInEx log fails the scan: when the game never created it, the message points at the Unity log and at security software; otherwise its process was not stopped by its session, which copies the logs when it stops. Counts are per file, and the same Unity message may appear in both the BepInEx log and `Player.log`. `Player.log` has no levels, so there only the named patterns and `unity-exception` count.

**A mod's own patterns.** Under a name that is not built in, a `logScan` entry is a pattern of the run's own: a `line` regex (.NET syntax), an optional `frame` regex for a line of its stack trace, a `severity` and the reason. It is counted like the built-in patterns at teardown (not at startup) and reported under its name, so a mod can fail on its own known-bad line, name another mod's known noise instead of counting it as `unknown-warning`, or allow a new game line after a game update without a toolkit release: `"mymod-fallback": { "line": "^\\[Warning *: *My Mod\\] fell back to ", "severity": "Failure", "reason": "MyMod must never fall back in a pinned runtime" }`. A built-in pattern's regex cannot be replaced. The built-in table is `LogScanner.Patterns`: the problems, then `LogScanner.KnownGameNoise` (game lines measured on the version their comments name). The patterns marked `LogPhase.Startup` (`missing-method`, `missing-field`, `type-load`) also end an owned startup at once; `StartupEvents.RuntimeLoadFailures` uses their regexes, so each exists once.

`unity-exception` and `unknown-error` cover different logs. BepInEx gives every line a level, so an exception in its log sits in an error record (`[Error  : Unity Log] NullReferenceException: ...`, or a plugin's error with the exception on its continuation lines) and counts once as that record: as a pattern when one matches, otherwise as `unknown-error`, which fails unless its exact header line is named as expected. Unity's own log has no levels, and the exception is the only sign: Unity prints its type name at the start of a line and the stack trace under it. Such a line outside a BepInEx warning or error record (`Player.log` and a server's output also hold BepInEx's console lines) that no pattern names counts as `unity-exception`, which fails: a mod threw, and the BepInEx log may not have it (BepInEx's "Unable to start Unity log writer" means Unity's messages never reach it). A Jötunn negative control (Jötunn #494) is the case: Jötunn's `NullReferenceException` in a death hook was only in the client's `Player.log`. A known pattern's exception (`nre-remove-objects`, `missing-method`, `macos-apple-plugin-missing`, ...) counts only as that pattern. A scenario that causes an exception on purpose names it by text in its first line or in one of its first 20 frames, since the first line rarely says which code threw: `"unity-exception": { "expected": ["Jotunn.Managers.CreatureManager.EnableCumulativeLevelEffects"], "reason": "the negative control runs Jotunn without the fix" }`. Every other exception in that run still fails. What a clean run logs, measured natively (the native acceptance suite's lifecycle-world scenario, Valheim 1.0.16, BepInEx 5.4.23.5; a Windows dedicated server with ValheimCLI, MyMod and its adapter, a Windows client with the same, both stopped cleanly), so these are the counts to expect; the known client log-writer error needs the exact expected-line classification shown above:

| Log | Counts | What they are |
|---|---|---|
| Server BepInEx log, each boot | none | |
| Server Unity log (`-logFile`), each boot | `missing-script` 13, `headless-server-graphics` 14 | Unity's "The referenced script on this Behaviour (Game Object '<null>') is missing!" with only vanilla content loaded; the server's graphics errors (`headless-server-graphics`) |

## Launching servers and clients

### Dedicated server launch

`GameLaunch.ForServer` builds an owned dedicated-server launch from a copied runtime directory, and `ToStartInfo()` renders it as the `ProcessStartInfo` that `DirectServerProcess` starts. The platform comes from the runtime's contents (`GameLaunch.DetectServer`): `valheim_server.exe` is Windows, `valheim_server.x86_64` is Linux, and both or neither is refused. It requires BepInEx's preloader and core and the platform's Doorstop loader (on Windows `winhttp.dll` and a `doorstop_config.ini` that enables Doorstop and targets the preloader, as for `GameLaunch.ForClient` below), so a broken or redirected install is refused instead of starting a vanilla server. A caller value for `DOORSTOP_ENABLED`, `DOORSTOP_TARGET_ASSEMBLY` or `DOORSTOP_DISABLE`, or a `--doorstop-*` argument, is refused on both platforms and the same variables are removed if inherited; both `GameLaunch` builders share this loader policy. These are checks of the install before launch; plugin pins after startup remain the proof that BepInEx ran. On Linux it also requires the executable's user-execute bit (not checked on a Windows host, which has no mode to read) and reproduces what BepInExPack_Valheim's `start_server_bepinex.sh` exports: `DOORSTOP_ENABLED`, `DOORSTOP_TARGET_ASSEMBLY`, `linux64` and `doorstop_libs` prepended to `LD_LIBRARY_PATH`, and `libdoorstop_x64.so` prepended to `LD_PRELOAD`. Existing entries are kept and no empty entry is added. `SteamAppId` defaults to 892970 on both platforms unless the caller sets it. The executable is started directly rather than through the script, so the owned-session PID check is unchanged. Arguments stay the caller's plan. Unlike a client launch, a machine may build the other platform's server launch: a Windows machine builds a Linux launch for inspection (it cannot run it), and callers that launch check the machine themselves. Given a host platform (`hostPlatform: ServerPlatform.Windows` or `Linux`), the same builder makes the launch `HostServer.StartAsync` starts on a game host: the runtime is then an absolute path there, only the path and variable-name rules are checked here, and the host checks the launch's `RequiredFiles` before it starts anything.

`docker/linux-server` is a local Ubuntu 24.04 image: .NET 10 SDK, non-root user, the dedicated server from anonymous SteamCMD at build time and the hash-verified BepInEx pack. The manual `native-linux.yml` workflow builds it on the runner and runs `docker/linux-server/smoke`, which requires BepInEx's `Chainloader startup complete` and the server log's creation of the generated world followed by `Opened Steam server`, then stops the process. Only logs and the report are uploaded.

The macOS dedicated server is `valheim_server/Valheim` with its `valheim_server/Data` folder, from Steam app 896660's macOS build ([platforms](../platforms.md#macos) has the install). `GameLaunch.DetectServer` returns `MacOS` for it; it runs only on a Mac, and a Mac still refuses the Windows and Linux servers before reading their mode, naming the macOS server, the Linux container (`--platform linux/amd64`, experimental on Apple Silicon) or a remote Windows/Linux host. `ToStartInfo()` on a Mac starts the server through `/usr/bin/arch -arm64` (or `-x86_64` on an Intel Mac) with `-e DYLD_INSERT_LIBRARIES=<the runtime's libdoorstop.dylib>` and `-e DYLD_LIBRARY_PATH=<runtime>/valheim_server`, because the kernel strips DYLD_* from that SIP-protected launcher's environment and a universal server otherwise starts as its parent's architecture. Doorstop is enabled for BepInEx's preloader. The library path is the server's own folder: with Doorstop injected, Mono finds `libmono-native.dylib` only through it, and with no library path or the install root (the Mac client's launcher value) the server never started. The server and the Doorstop library must both have the machine's slice. `arch` executes the server in place, so the PID is the server's own and a clean stop is a SIGINT, as on Linux. [LinuxServerSmoke](../../docker/linux-server/smoke/README.md) has passed natively on an Apple M2 (macOS 26.5.2, the Mac client's native BepInEx 5.4.23.5 core, Doorstop 4.5 and ValheimCLI): BepInEx on `OSX Arm64`, a clean SIGINT stop that saved the world, and a second boot that loaded that save. A native arm64 Mac client has joined one in the native acceptance suite's synced-config scenario ([#113](https://github.com/tvongaza/ValheimTesting/pull/113)). `GameLaunch.DetectServer` still refuses a macOS game client (a `Valheim.app` bundle, a renamed bundle recognised by `Contents/MacOS/Valheim`, or a directory holding `Valheim.app`). The local Windows and Linux launchers retain their platform checks; the hosted Windows path is on the [GameSessions page](Valheim.Testing.GameSessions.md#a-server-only-plan-on-a-remote-host). The host is injectable internally, so every host's branches are unit-tested on any OS, and CI runs the tests on Windows, Linux and macOS.

The image pins `linux/amd64`.

Limits: this boots a server with no ValheimCLI or mod plugins; it does not test save, networking or gameplay, and Steam's backend connection is recorded but not required. Unit tests cover detection, refusal and environment merging with fake files. Game clients in the cloud are not supported; for remote hosts over SSH see [Game hosts](Valheim.Testing.GameSessions.md#game-hosts-and-the-environment-inventory). Images contain game files and must never be pushed or published.

### Game client launch

`GameLaunch.ForClient` is the client builder beside `GameLaunch.ForServer`: it builds the launch of one BepInEx game client from its install directory and starts nothing; `ToStartInfo()` renders it for this machine. The platform comes from the install's contents (`GameLaunch.DetectClient`), never the host: `valheim.exe` is Windows, `valheim.x86_64` is Linux and a `Valheim.app` bundle (any case) is macOS. An install with more than one is refused, as is the bundle itself (pass the directory that holds it and BepInEx) and a dedicated-server runtime, which is pointed at `GameLaunch.ForServer`; `GameLaunch.DetectServer` likewise names `GameLaunch.ForClient` when given a client. A client runs only on its own OS, so any other host throws `PlatformNotSupportedException`; there is no Wine or Proton support. `GameLaunch.DetectClient` still works on any host.

| | Windows | Linux | macOS |
|---|---|---|---|
| Detected from | `valheim.exe` | `valheim.x86_64` (user-execute bit required) | `Valheim.app/Contents/MacOS/Valheim` (user-execute bit required) |
| Loader files required | `BepInEx/core/BepInEx.Preloader.dll` and `BepInEx.dll`; `winhttp.dll`; `doorstop_config.ini` enabling Doorstop and targeting `BepInEx\core\BepInEx.Preloader.dll` (any case, either separator, relative or absolute; another existing DLL is refused), in Doorstop 4 (`[General] enabled`, `target_assembly`) or Doorstop 3 (`[UnityDoorstop] enabled`, `targetAssembly`) form; when `winhttp.dll` shows its version (the key its code reads), the file must be written for that version, so a Doorstop 4 proxy beside a Doorstop 3 file is refused ([Owned-run preflight](#owned-run-preflight)) | BepInEx core; `doorstop_libs/libdoorstop_x64.so` | BepInEx core; `doorstop_libs/libdoorstop_x64.dylib` (BepInExPack_Valheim) or a `libdoorstop.dylib` at the root (UnityDoorstop 4.5 or later, universal or arm64-only) with the requested slice; for arm64 also `BepInEx/core/MonoMod.RuntimeDetour.dll` 25 or later |
| Started executable | `valheim.exe` | `valheim.x86_64` | `/usr/bin/arch -x86_64` or `-arm64`, then the bundle executable |
| Loader variables set | none; the proxy DLL reads its ini | `DOORSTOP_ENABLED=1`, `DOORSTOP_TARGET_ASSEMBLY`, `doorstop_libs` prepended to `LD_LIBRARY_PATH`, `libdoorstop_x64.so` prepended to `LD_PRELOAD` | `DOORSTOP_ENABLED=1`, `DOORSTOP_TARGET_ASSEMBLY`, the library's full path prepended to `DYLD_INSERT_LIBRARIES` and passed with `arch -e` |
| Architectures | x64 | x64 | x86_64 (default; the Rosetta compatibility path on Apple Silicon) or native arm64, chosen by the caller (`client.architecture` in a plan) |
| Also needed to run | desktop session, Steam | desktop session with `DISPLAY` or `WAYLAND_DISPLAY`, GPU, Steam | logged-in desktop session, Steam |

On every platform `-console` is added first unless the caller passes `console: false` or already includes it, other arguments follow unchanged, `SteamAppId` defaults to 892970 unless the caller sets it, and caller environment is applied first with existing search-list entries kept. A caller value for `DOORSTOP_ENABLED`, `DOORSTOP_TARGET_ASSEMBLY` or `DOORSTOP_DISABLE`, or a `--doorstop-*` argument, is refused because it would start a vanilla client; the same variables are removed if inherited. Linux and macOS install paths may not contain `:` (Linux also `;`), which their search lists cannot represent.

On macOS the game is started through `/usr/bin/arch` with an explicit slice, because a universal executable otherwise runs as the parent's architecture, which the Doorstop library may lack. `arch` is a protected system binary, so the kernel drops `DYLD_*` from its environment; `ToStartInfo()` passes them with `-e` instead, and `arch` execs the game in place, so the started PID is the game's. It reads the Mach-O slices of the game and of each Doorstop library and inserts the first library with the requested slice, refusing with the slices it found otherwise; `arch` fails rather than start another slice, so an arm64 request never falls back to Rosetta. BepInExPack_Valheim ships only an x86_64 library and a core on legacy MonoMod, which is the x86_64 route under Rosetta: the default and the compatibility path. The native arm64 route needs a `libdoorstop.dylib` with an arm64 slice (a universal build is one way) and a BepInEx core whose MonoMod can hook on arm64. `GameLaunch.ForClient` checks the core by the version of `BepInEx/core/MonoMod.RuntimeDetour.dll` (read, never loaded): 25 or later, the reorganised MonoMod that the native BepInEx 5.4.23.5 core uses, or the arm64 launch is refused with the version it found. Nothing on disk says whether each plugin's own hooks and native libraries work on arm64. `GameLaunch.ClientLaunchArchitectures` reports the slices an install can be launched as, arm64 only with such a core. [Native Apple Silicon client](../platforms.md#native-apple-silicon-client) has the install recipe, the default and the limits.

Limits: `GameLaunch.ForClient` only builds the launch. A game client needs an interactive desktop session with a display, a GPU and a running, signed-in Steam client. A process started from a service, a scheduled task without a logged-in user or an SSH session usually has no display, so it fails or never shows a window. Starting it inside the user's session on another machine is [`InteractiveClient`'s job](Valheim.Testing.GameSessions.md#clients-in-a-hosts-desktop-session). The toolkit ships no Linux client environment (a display, a GPU and a signed-in Steam client are the operator's); the rented-GPU-VM client container was retired (#230, recoverable from the `archive/linux-client-image` tag). Unit tests cover detection, refusals, loader checks, slice selection and environment merging with fake install trees on all three platforms. `ClientSession.Launch` builds its owned launch with `GameLaunch.ForClient`, and the [native Windows joined-client check](https://github.com/tvongaza/ValheimTesting/pull/94#issuecomment-5912134571) started its client that way.

## Game clients in system tests

A system test that looks from a client describes it with a `ClientRunPlan` section and opens it with `ClientSession`. The [FullLifecycle example](../../examples/FullLifecycle/README.md) uses both.

- `ClientRunPlan` holds the mode (`owned` or `attach`), the install, its `installPins`, launch arguments and `architecture` (owned only; `x64`, the default, or `arm64` for a native macOS client; see [the native client](../platforms.md#native-apple-silicon-client)), the client's ValheimCLI host and port, strict plugin pins, the join address, a disposable local character, the name of the environment variable holding the join password, and the start, join and arrival timeouts. `Validate(params absentPlugins)` refuses a plan before anything starts: an owned client off this machine or without `installPins`, an `architecture` other than `x64` or `arm64`, `arm64` for a Windows or Linux client (a Windows-style path, or an install here that is not `Valheim.app`), a `Valheim.app` install on this machine that the launch's own slice and core check refuses for the plan's architecture (so a runner's `validate` refuses it, and `run` refuses it before the server starts), and any architecture for an attached client, pins with a world key, no exact ValheimCLI pin, a listed plugin that is neither an exact MD5 nor `absent`, and any of `absentPlugins` not pinned `absent` (a server-only mod's claim is what a client without it sees). `MenuExpectations` and `WorldExpectations(worldUid)` are the strict pins at the menu and once joined. `"pinning": "none"` opts the client out ([Pins and the opt-out](#pins-and-the-opt-out)). `bepInExSeconds` (owned, default 60) bounds how long BepInEx may take to write this launch's first log line. `capabilities` lists the ValheimCLI commands (`owner/command`) the run uses beyond its runner's own, and `cliManifest` (owned only, a full path) names the hash-bound manifest of a ValheimCLI core and packs ([ValheimCLI capability manifest](#valheimcli-capability-manifest)). `inPlace` (owned only) runs the install itself instead of the disposable copy a session makes of it ([GameSessions](Valheim.Testing.GameSessions.md#an-owned-client-on-this-machine-runs-from-a-disposable-copy)); a plan that is the source of a copy needs no ValheimCLI pin, since the copy's are the staged set's. `Preflight()` runs every static check of the run before anything is copied or started ([Owned-run preflight](#owned-run-preflight)).
- `ClientSession.Launch(plan, output)` starts an owned client through `GameLaunch.ForClient` and returns it at its main menu, strictly pinned. It launches only an install bound to a disposable copy (a session's, a targeted regression's) or one run in place (`inPlace`), and refuses any other owned plan: the user's install is never launched unless asked. It refuses first when its game build, loader or patchers differ from `installPins`, when the rest of the [owned-run preflight](#owned-run-preflight)'s install checks fail (a Doorstop version mismatch, a pinned plugin build that is not installed, a script ScriptEngine will not load at start, a standing expectations file that would refuse the run, a ValheimCLI set that is not its `cliManifest`'s or lacks a capability in `capabilities`), when something already listens on the client's CLI port (a command could reach a client it does not own), when no Steam client runs in this session, or when the password variable is missing from its own environment (the client inherits it). Startup waits on events, never on polling: this launch's first BepInEx log line within `bepInExSeconds` (a game still running without it runs without BepInEx, and startup fails then, naming the loader, rather than at the start deadline), ValheimCLI's listening line in this launch's BepInEx log (any of `StartupEvents.StartupFailures` ends it), then the `MainMenu` state push, each raced against the process exit, which ends startup at once with the exit code (and, when BepInEx wrote nothing, the path of `Player.log`). Once the client answers at its menu, `capabilities` are required live (`CliCapabilities.Require`), for an attached client too. A failed startup stops the process it started. Disposing closes the connection and stops only that process, then keeps its BepInEx log and `Player.log` beside the evidence; `Logs` lists them for the teardown scan.
- `ClientSession.Attach(plan, output)` connects to an operator's client and verifies its menu pins; disposing never touches that process.
- Each session records every command to `client-commands.jsonl` (then `-2`, `-3`, and so on: evidence is never overwritten); an owned session also writes `client-process.json`, with the `architecture` it launched, which `Architecture` also gives (null for an attached client). `ClientRounds` records it as provenance `clientArchitecture` (`attached` for an attached client). `ClientSession.Open(plan, output, logs)` adds the owned client's kept logs to `logs` for the teardown scan, also when its startup fails after the process started; `GameSession.OpenClient` does the same for the session's `Logs`, so a client that never reached its menu is still scanned and listed in `result.json`. An arm64 plan is refused before the CLI port, Steam or the process are touched when `GameLaunch.ForClient` refuses the install, and a remote campaign client refuses `arm64` before its host is locked.
- `ClientSession.Launch(plan, output, start, connect, ready)` takes the process, connection and readiness as functions, so a mod's integration tests can drive startup failures, timeouts and cleanup without a game.
- `PinnedFile` pins a plan's input file by full path and SHA256; `Verified()` rechecks the hash before use.

Limits: an owned client must run in the desktop session where Steam is running and signed in; `ClientSession` can tell only that Steam runs, not that it is signed in, and never signs in. Disposing asks an owned client to quit (it closes the game's main window on Windows, SIGTERM on Linux and macOS), so the game saves its profile as a player's quit does, and kills it only after `QuitTimeout` (one minute); `Stopped` says which. Valheim 1.0 refuses a joined client's cheat commands whatever the server's admin list says; ValheimCLI's client setting `AllowOnServerClients = true` is what lets its test commands run there.

## Joining, protecting and placing a player

`PlayerPlacement` places and protects the player of a joined client for any mod's client check:

- `SkipIntro(client, timeout)` ends a new character's first-spawn intro (the Valkyrie ride) as the menu's Skip does, or stops it before it starts, and waits for the player to respawn on the ground (`cli_skip_intro`, not a cheat command). It returns whether an intro was running; for a character that has spawned before it changes nothing.
- `Protect(client)` turns on god, ghost and debug modes (`cli_set_player_safety true`, which sets them rather than toggling) and requires the game to read all three back, and ghost mode to be replicated (`ghostReplicated=True`); it is issued once, and an unconfirmed reply fails. Debug flying stays off. `SessionControl.WaitForWorld` calls it by default (see below), so a joined player is protected without asking. The game keeps ghost mode in the player's own process while a creature's AI runs in whichever process owns the creature, often another client; ValheimCLI's Standard pack writes ghost mode to the player's ZDO and every process that loads it reads it from there, so a protected player is invisible to every creature in a session whose processes all run ValheimCLI (#261: natively, a Skeleton another client owned targeted a player protected only locally). An older ValheimCLI, without `ghostReplicated` on its reply, fails the protection and so the join: use the build `cli-dependency.json` pins or later on every joined client, attached ones included. God mode keeps health at 1 or more; it does not stop hits or knockback.
- `SetFly(client, on)` turns debug fly on or off (`cli_fly on|off`) and requires the game to read the state back. Fly is for review and visual steps only: a flying player is never supported, so `Arrive` and `RequireSupported` refuse (an `InvalidOperationException`, not a `SupportException`) as soon as a reading shows the player flying. Turn it off before measuring again.
- `Arrive(server, client, point, timeout)` returns a `TeleportArrival`: the client's supported landing (`Support`), the teleport's trace line (`Trace`), its parsed phase times (`Timing`) and the point the landing was judged against (`Target`). It first skips the intro (pass `skipIntro: false` to leave it, and the readiness wait then also requires the player grounded), refuses a player that one reading shows flying, and then makes one bounded in-game wait per transition instead of reading the player over the network: ValheimCLI waits until the game would take a teleport (it silently drops one during the Valkyrie ride and within 2 s of a spawn or teleport), arms a one-hop trace, the server's only connected player with a character (none or several is refused) is teleported once just above the point with the game's own teleport at its ordinary timing, then ValheimCLI waits for the teleport to finish with a ready floor and for the player to stand supported there. With no server (`Arrive(null, client, ...)`) the client teleports its own player instead (`cli_teleport`): the way to place one of several players, which needs the client's test access (`SessionControl.JoinWorld` gives an owned client that) and ValheimCLI's `AllowOnServerClients` on a joined client. With `loadedGround: true` the point's height is only the teleport target: once the floor is ready the client measures the loaded ground there and the landing must be supported at that height, for a check that is not about terrain where a location's levelling moves the ground from the generator's height (the ownership handoff); a terrain check leaves it off. A teleport reply is never taken as arrival, and nothing is repeated: a timeout (at most 600 s; each CLI wait at most 120 s), a finish without a ready floor or an unsupported landing fails. It needs `PlayerPlacement.ArrivalCapabilities` on the client: `valheim.session/teleport-signals` (Standard pack: `cli_wait_teleportable`, `cli_teleport_trace_arm`/`cli_teleport_trace_wait`) and `valheim.world/player-support-wait` (World Tools), in the ValheimCLI build `cli-dependency.json` pins. List them in a client plan's `capabilities` to have them checked before launch.
- `PeerCount(server)` reads `cli_peers` once and returns how many peers are connected, refusing a reply whose count line disagrees with the peers it lists; `OnlyPeer(server)` reads the same listing.
- `RequireSupported(client, point)` takes three readings half a second apart, each of which must show the player grounded and stationary on the declared ground; a `SupportException` carries every reading.

`SessionControl.Join` turns the client's devcommands on before joining, because ValheimCLI refuses the join (a mutating extension command) until it is on; `EnableDevcommands()` does the same on its own. Both are `TestAccess.Ensure(actor, TestActorRole.ClientMenu)`: read ValheimCLI's `cli_access`, toggle once only if devcommands are off, and verify. Cheats are acknowledged once the client is in a world, for an owned client only; an attached operator's client keeps devcommands only. `SessionControl.JoinWorld(plan, worldUid)` is the one join of a client plan to an owned dedicated server, used by `ClientRounds`, `LogoutCycle` and scenarios that join several clients themselves: devcommands first and the join exactly once (by address, or into the server's lobby for a crossplay plan), the world pins verified and the world awaited; then for an owned client `TestAccess.Ensure(..., ClientInWorld)`, which also requires `AllowOnServerClients` when the player is to be protected, so a client staged without it is named there; then the player is protected (`protectPlayer: false` leaves it, as for `WaitForWorld`). A hosting client's rounds acknowledge cheats in their own step ("establish test access on the owned host").

`SessionControl.WaitForWorld` protects the local player once the world is ready (`PlayerPlacement.Protect`), so a test that forgets to cannot lose its character to a fall, the water or a mob before it arrives, a failure that would look like a mod bug. A protection the game does not read back fails the wait. A dedicated server has no local player and is left alone; a game hosting its own world reports ready before its player spawns, so the wait goes on, within the same timeout, until that player exists, and times out saying so if it never does. On a joined client the command needs ValheimCLI's `AllowOnServerClients` setting, like the join.

Protection changes gameplay (as the game does in 1.0.16): monsters neither notice nor target a player in ghost mode, an egg hatches only near a player who is not in ghost mode, and a creature hit by a player in god or ghost mode is marked cheated, which marks the items it drops. A client plan's `"targetable": true` protects its joined player without ghost mode (`Protect(client, targetable: true)`, `cli_set_player_safety true targetable`): it cannot die, but creatures notice it, for AI and aggro checks. Pass `WaitForWorld(..., protectPlayer: false)` for combat, taming, hatching and loot checks, for any check that needs a vulnerable player, and when an operator manages these modes; call `PlayerPlacement.Protect` yourself for the steps that should be protected.

Declare the support point on dry ground: a player standing in water is not grounded at the ground's height, so the check fails, which is correct but tells you nothing about the mod. `examples/ObserveCheck`'s `surface` probe uses `RequireSupported`.

A console reply is not a successful mutation. The game's cheat confirmation can refuse a command such as `cli_arrive` even after devcommands is on, and the transport still returns that console text as a completed request. `GameActor.Execute` therefore requires the reply accepted by default (`GameReply`); a step still requires the command's documented result, or observes its effect independently.

## Plan rules and client rounds

Mod runners repeat two kinds of glue, which the toolkit owns. The [FullLifecycle example](../../examples/FullLifecycle/README.md) uses both.

Plan rules on `ServerRunPlan` refuse a plan before anything is copied, with an `ArgumentException` that names the field and the fix:
- `RequireScenario(known...)`: the plan's `scenario` is one the runner knows.
- `RequireEnvironmentFlag(variable, purpose)`: an explicit fixture opt-in, set to exactly `1`. A missing variable, any other value (`true`, `1 `) and a key that differs only in case are refused.
- `OnlyForScenario(settings, supplied, scenarios...)`: settings another scenario reads are refused rather than silently ignored.

The toolkit's own tests cover the rules every pinned plan follows: output path, launch host, executable, pins, save root, Doorstop and token variables, and unknown fields. A mod's plan tests need only cover its own rules.

`ClientRounds` runs a persistence scenario's client rounds over `ClientSession`, `SessionControl` and `PlayerPlacement`, for a client that joins an owned dedicated server and, with the same loop and teardown, for a client that hosts its own world ([hosted worlds](#hosted-listen-server-worlds)). The mod supplies the per-round measurement as a delegate, and its step names where it wants its own (`OpenStep`, `ArriveStep`). A joining client's rounds take the owned server as `OwnedServer`, an `IOwnedServer`: pass the runner's `ServerActor` (`session.Server`), which waits on its own session capability within its startup deadline and restarts only that server (a no-game test implements the two members over scripted servers). They also take the server's `WorldUid`. For each of `Rounds` (default `first`, `after-restart`), `Run(server, openClient, measure, afterRestart)`:
1. waits until the server accepts game connections;
2. joins with `SessionControl.JoinWorld` in one step (devcommands first, exactly once), which verifies the client's world pins and waits for the world, then, for an owned client, acknowledges cheats on its disposable character (`TestAccess.Ensure`, ClientInWorld), and protects the player unless `ProtectPlayer` is false;
3. arrives at `Arrival` if one is given (`PlayerPlacement.Arrive`), writing `{round}-arrival.json` and `{round}-teleport-trace.json`; with an `Arrival`, the client's ValheimCLI must offer `PlayerPlacement.ArrivalCapabilities`, which is checked once at its menu, before any join;
4. runs the measurement, which records `{round}: ...` steps with `round.Step` and writes `{round}-{name}.json` with `round.Write`, refusing to overwrite existing evidence.

Between rounds come a confirmed save, the client's leave and a restart of only the owned server. The optional `afterRestart` check runs next (for example "the server still has the marker"). The last round only leaves. Every step goes through the `ScenarioReport`. `clientRounds` and `clientRoundsCompleted` in its provenance record how far the run got. The first failure stops the rounds and is rethrown: nothing runs after a failed save, restart or measurement, and that round's evidence stays. The client is closed in every outcome: an owned client's process is stopped, and an attached client is detached and left running. A failed close fails a passing run, but never hides an earlier failure. The teardown is the same for a hosting client, which then also releases its world. `Run` returns the server's actor after the last restart.

Limits: the helper orders and records the steps, and its integration tests use scripted transports and fake processes. The steps' native behaviour is that of the pieces it calls, which have their own native evidence. Natively, #299's measurement ran it ten times on the FullLifecycle dry-site scenario (dedicated server, owned joined client, two rounds each).

### Arrival

Arrival has one procedure, `PlayerPlacement.Arrive`, at the game's ordinary teleport timing. Each round's `{round}-teleport-trace.json` holds the trace's numeric `RequestedMs`, `MovedMs`, `AreaReadyMs`, `FloorReadyMs` and `DoneMs` (milliseconds from arming; -1 for a phase that did not occur, such as `MovedMs` when the player was already within 5 m of the point), the final position and the original reply; malformed fields, another trace id, a missing ready floor or an unsupported landing fail the run. The waits run in the game rather than polling it: a paired native measurement (dedicated server, owned joined client, ten arrivals each) found them faster than polling the player, median 10.35 s per arrival against 12.36 s, and faster in every pair. A plan that names the removed `eventDrivenArrival` is refused with what to do.

## Refused joins, crossplay and hosted worlds

Three join variants beside the plain dedicated-server join. They use ValheimCLI commands that the pinned build already has. Their fakes-based tests are in [SessionVariantTests](../../tests/Valheim.Testing.Tests/SessionVariantTests.cs), [CrossplayPlanTests](../../tests/Valheim.Testing.Tests/CrossplayPlanTests.cs) and [ClientRoundsTests](../../tests/Valheim.Testing.Tests/ClientRoundsTests.cs).

A native run (real Valheim 1.0.16, the [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md)'s mod, then named MyMod) covered all three. A client with a mismatched MyMod was refused with `ErrorVersion` (3) after about 1.5 s, and a matching client then joined. A hosted world (the fixture in Valheim 1.0's chunked layout) ran the mod's feature and its broadcast handler in the host process, and kept its marker across the host's restart. A crossplay server's lobby opened and a Windows client joined it through PlayFab, twice across a server restart.

### Expect a refused join

`SessionControl.JoinExpectingRefusal(address, character, expected, menuExpectations, timeout)` tests that a server refuses a client, for example a mod's version check refusing a mismatched client with `GameConnectionStatus.ErrorVersion` (3). It:
1. turns devcommands on, as `Join` does, and issues `cli_extension valheim.session/join <host:port> <character> [password-variable]` once;
2. requires ValheimCLI's structured failure with code `join_failed`, which it reports when the new connection ends in an error status;
3. re-pins the client with `menuExpectations` (plugins only, such as `ClientRunPlan.MenuExpectations`) and reads `valheim.session/state` until the client is back at its menu (phase `menu`, no world);
4. reads `cli_connection_status` once (`OK: connectionStatus=ErrorVersion, server=...`) and requires the expected status.

It fails when the join succeeds (the client is then in the server's world: leave it before another join), when ValheimCLI reports any other code (`character_unavailable`, `transition_timeout`, `load_error`, ...), when the client does not return to its menu within `timeout`, and when the refusal has another status. Nothing is retried. It returns a `JoinRefusal` with the status, its number and the server string. The client is then at its menu, pinned, and the server's acceptance of a matching client is checked with a normal `Join`.

`GameConnectionStatus` has the game's names and numbers (1.0.16): 3 `ErrorVersion`, 4 `ErrorDisconnected`, 5 `ErrorConnectFailed`, 6 `ErrorPassword`, 7 `ErrorAlreadyConnected`, 8 `ErrorBanned`, 9 `ErrorFull`, 10 `ErrorPlatformExcluded`, 11 `ErrorCrossplayPrivilege`, 12 `ErrorKicked`. As the game does in 1.0.16, a refused client keeps its status at the menu until its next join starts. `ConnectionStatusReading.Read(actor)` reads it at any time.

Limits: in the native run the refused client's final status was `ErrorVersion`, as the mod's version check set it. The game can overwrite an error with `ErrorDisconnected` when the connection closes after it, so check the expected status of another mod's refusal in a native run.

### Crossplay (PlayFab)

- **Server:** `"crossplay": true` in a `ServerRunPlan` makes the runner launch the dedicated server with `-crossplay` (`LaunchArguments`) and record `crossplay` (`true` or `false`) in every report's provenance. `-crossplay` in `arguments` is refused in any case, for every plan the runner reads, so the report always says which backend ran.
- **Port rule:** a crossplay lobby is keyed by the server's public IP and game port. Two crossplay servers behind one public IP must use different game ports, or the second takes the first one's joins. A crossplay plan therefore names exactly one `-port N` (1024 to 65535) rather than relying on the default 2456.
- **Separate fixtures:** keep a crossplay fixture server separate from a Steam one rather than switching one server between modes. A client remembers each server's mode in its recent-server list.
- **No password:** run the crossplay fixture server private without a password (`-public 0`, no `-password`). The client's join command, `cli_connect_playfab_user`, takes a password as command text, which would be recorded.
- **Lobby:** clients join a crossplay server by its PlayFab id, not its address. `CrossplayServer.WaitForLobby(server, CrossplayServer.BepInExLog(runtime), timeout)` first reads `cli_multiplayer_identity` (`OK: steamId=..., playFabLoginState=..., playFabId=..., backend=PlayFab, gameState=..., connectionStatus=..., isServer=True, isOpenServer=True, server=...`) and refuses a server whose backend is not `PlayFab`. It then waits on the server log for the game's lobby line, `Created PlayFab lobby with ID "...", ConnectionString "..." and owned by "<id>"`, reading this boot's log from its start. A failed PlayFab login ends the wait at once. The owner id is what the client joins. The log is the source because the identity's `playFabId` can be `unavailable`; when it is present, it must equal the owner. BepInEx copies the game's log lines into its `LogOutput.log` by default; otherwise pass the Unity log that the plan's `-logFile` names. For a server on another machine (`PinnedServerRun --inventory` or a session), the session's `ServerActor.Lobby(boot)` waits for the same line in the host's log, with the host's event-driven log wait.
- **Client:** `"crossplay": true` in a `ClientRunPlan`, with no `join` and no `passwordVariable`. `SessionControl.JoinCrossplay(remotePlayerId, character, worldUid, menuExpectations, timeout)` joins from the idle menu. It turns devcommands on, then sends `cli_select_character <character>` (`OK: Selected character '...'`) and `cli_connect_playfab_user <id>` once (`OK: PlayFab user join started for <id> using ...`). That command only starts the join, so it re-pins with the menu pins and reads the session state until the client is connected in `worldUid` with its player ready. A load error, another world, or a return to the menu with an `Error...` status after the join started fails it. A status left from an earlier join does not count. Then verify the world pins and `WaitForWorld` as usual. The join can load the world before the menu pins are checked or between two state reads; a strict client then refuses the menu pins (`world: ... is loaded but not listed (strict)`). Pass `worldExpectations` (`ClientRunPlan.WorldExpectations(worldUid)`) and the client is re-pinned to that world once, on that refusal only; another world fails that pin check. `ClientRounds` passes it.
- **Linux server:** a Linux dedicated server needs `libpulse0` and `libpulse-mainloop-glib0` for crossplay: the game's PlayFab library (`valheim_server_Data/Plugins/libparty.so`) loads them. Without them Unity logs `Failed to open plugin`, the first PlayFab call fails with `DllNotFoundException: libParty.so`, and the server retries its network every 30 s without ever opening a lobby. The [docker/linux-server](../../docker/linux-server) image has them. A crossplay `PinnedServerRun` checks this before any server starts, in `validate` too. On a server host (`--inventory` or a campaign) the step is "the server host can load crossplay's libraries"; for a local Linux runtime on Linux it is "this machine can load crossplay's libraries". The check (`CrossplayLibraries.RequireAsync`) runs the host's `ldd` on the **server** runtime copy's `libparty.so` with the launch's library path. It refuses a missing library by name, with its Debian or Ubuntu package and the `apt-get install` line. It also refuses a runtime without the server's `libparty.so` and a host without `ldd`, and records `crossplayLibraries` in the report. `HostServer.StartAsync` makes the same check for any launch with `-crossplay`, so nothing starts on a host with unresolved dependencies. This is a dependency preflight, not proof that the running game opened a PlayFab lobby; the native lobby wait still decides that.
- **Stopping a server:** a server stopped by killing its process leaves its PlayFab lobby active for hours. A later join on the same IP and port, or the same PlayFab identity, can reach the dead lobby and fail with `ErrorConnectFailed` (5). Owned servers are asked to quit first ([Stopping owned processes](#stopping-owned-processes)); on a clean quit the game saves, logs `Unregister PlayFab server ...` and asks PlayFab to mark its lobby inactive. It logs `Deactivated PlayFab lobby <id>` only if PlayFab's reply arrives before the process ends, which on the 1.0.16 Windows server it did not. A crossplay `PinnedServerRun` ends with the step "every boot quit cleanly and retired its crossplay lobby" (`CrossplayServer.RequireLobbiesRetired`): every boot, restarts included, must have quit cleanly, and its kept logs (BepInEx's, the `-logFile` file, the process output) must show the lobby it created and the `Unregister` line. A killed boot fails the run, because its lobby can take the next run's joins, and so do logs without any lobby line. `crossplayLobbies` in the report lists each boot's lobby and whether PlayFab's confirmation was logged. That the retired lobby really stopped taking joins shows in the next run's joins on the same address and port. The lobby line is in the log the game writes to: the `-logFile` file when the plan passes one (`ServerRunPlan.GameLogFile`); the Windows server's BepInEx log did not carry it.
- **Rounds:** `ClientRounds` with a crossplay client needs `Lobby` (for example `server => CrossplayServer.WaitForLobby(server, log, timeout)`). It reads the lobby before each round's join, because a restarted server opens a new one, and records `clientJoin` (`crossplay` or `address`).

### Hosted (listen-server) worlds

A client can host a world from its menu instead of joining a server. The host is the server of its world and also has a local player: its session state reads `server` true and `dedicated` false. A broadcast RPC therefore runs the server and client handlers in the same process. The `hostWorld` section of a `ClientRunPlan` describes the world:

| Field | Meaning |
|---|---|
| `world` | The fixture as a pinned directory holding one world in either layout the game loads: Valheim 1.0's chunked save, one `<name>/` directory at its root with `_main.<n>.fwl2` and its chunks (what a 1.0 server or client writes), or the older pair, one `<name>.fwl` at its root with its data beside it (`<name>.db`). Every entry is named for the world; the name is at least 3 characters and one token. |
| `worldUid` | The fixture world's exact UID. It is required even with `"pinning": "none"`, because the game silently creates a fresh world when the named one is missing. |
| `crossplay` | Host a crossplay world. |
| `saveDirectory` | The client's data directory, which holds `worlds_local`. Default: this user's for the client's platform: `AppData/LocalLow/IronGate/Valheim` on Windows, `Library/Application Support/IronGate/Valheim` on macOS, `.config/unity3d/IronGate/Valheim` on Linux. Set it when a Windows or Linux client runs as another user. Native macOS hosted runs require the signed-in user's default directory; a custom path or `-savedir` is refused before fixture placement. |
| `saveSeconds` | The confirmed save's timeout, 1 to 600 (default 120). |

`ClientRunPlan.Validate` refuses a hosting client with `join`, `passwordVariable`, the client-level `crossplay` or `joinsHost`, one whose ValheimCLI host is not this machine (the runner places the world in its data directory), a fixture that does not name one world, a missing or inexact `worldUid`, and, when pinned, a fixture without hashes. Unknown fields are refused as elsewhere.

`HostedWorld.Place` copies and verifies the fixture into the output directory, as the server runner does, and keeps that copy. It then copies the fixture into the client's `worlds_local`. It refuses if anything named for the world is already there (`<name>`, `<name>.*`, `<name>_*`, in any case), so a user's world is never overwritten or used. `Collect` moves the world, with what the game wrote for it (saves, `.old` files, backups), into `host-world` in the output directory.

`HostWorlds.Start(host, plan, worldName, timeout)` starts from the idle menu:
1. turns devcommands on (ValheimCLI refuses its save and leave without them) and selects the plan's character (`cli_select_character`);
2. sends `cli_start_host_world <name> --public false --crossplay true|false` once and requires the reply `OK: Starting hosted world '<name>' using <character>; open=true, public=False, crossplay=<True|False>, backend=<PlayFab|Steamworks>, passwordSet=False`;
3. re-pins the client with its menu pins and waits for the plan's world UID to be ready (a fresh world has another UID and fails here, naming both UIDs as the wrong world rather than a load failure);
4. verifies the world pins, then waits for the host's player and protects it (`WaitForWorld`). A world that loads between two reads makes the strict menu pins refuse it ("loaded but not listed"); the world pins are then checked at once, so another UID fails as a wrong fixture.

`HostWorlds.Restart` leaves the world, which saves it, then starts it again: the host's restart. The host's world is not restarted as a separate process.

`ClientRounds.Run(openClient, measure)` runs a client whose plan has a `hostWorld` section; it refuses `OwnedServer`, `Lobby`, `Arrival` and `ArriveStep`, which only a joining client uses, and its `WorldUid` is the fixture's (leave it out). It first runs the plan's `Preflight(CliCapabilities.HostedRounds)` (the fixture's pinned files and its own world UID, and an owned client's install, whose ValheimCLI set must provide the session commands the rounds use when the plan names a `cliManifest`; see [Owned-run preflight](#owned-run-preflight)), so a wrong fixture, install or ValheimCLI set stops the run before the fixture is copied or the client started. A native Mac host also refuses a custom save directory or `-savedir` before placement. A no-game test keeps its world in a private test directory with a `FakeClientDataDirectory` scope (see [Test fakes](#test-fakes)), and the macOS rule still runs against it. It then places the world, opens the client (owned or attached), requires the session commands the rounds use (`CliCapabilities.HostedRounds`) and runs each round in turn, bounding each start by the client plan's `joinSeconds`:
1. hosts the world, which is a restart from the second round on, and protects the host's player unless `ProtectPlayer` is false;
2. runs the mod's measurement; `round.Server` and `round.Client` are the same host;
3. between rounds, saves with a confirmed `valheim.session/save` on the host;
4. the host leaves to its menu.

The report's provenance records `role` = `host`, `hostWorld`, `hostCrossplay`, `hostRounds`, `hostRoundsCompleted` and `cliPreflight`. The client is closed in every outcome, as for a joining client, then the world is moved into the evidence (`hostWorldEvidence`). After a failure an attached client, or an owned client that did not stop, may still host the world, so its world is left in place and named in `hostWorldLeftInPlace`; remove it once that client has left it.

## Owned-run preflight

An owned native run can fail in setup long before its first assertion, and each such failure used to cost a client start deadline or a world round. The preflight checks what is on disk before anything is copied or started, and names what only the live game can show as soon as it can. Strict per-command plugin and world pins are unchanged: this is an earlier diagnostic, not a relaxation.

`ClientRunPlan.Preflight()` runs every static check, after `Validate` and before anything is copied or started. The hosted `ClientRounds` run it as their first step; `ClientSession.Launch` runs the install part itself, before it reserves the port or looks for Steam. A mod runner can call it in its own `validate` mode. An attached client's install is its operator's and is not read, so only a hosted fixture is checked for it.

| What went wrong | Where it is caught | What is checked |
|---|---|---|
| A Doorstop 4 `winhttp.dll` beside a Doorstop 3 `doorstop_config.ini`: the game reached its menu without BepInEx, and adding a `[General]` section to the file did not fix it | Static, in the loader check (servers too) | The proxy's version from the configuration key its code reads (`target_assembly` for 4, `targetAssembly` for 3); the file must be written for that version (Doorstop 4: `[General]` and no `[UnityDoorstop]`; Doorstop 3: `[UnityDoorstop]`). A proxy that shows neither key is checked as before. |
| The game runs, but BepInEx never starts | Live, right after launch | This launch's first line in `BepInEx/LogOutput.log` within `bepInExSeconds` (default 60). Lines from an earlier run never count. For a client in a host's desktop session, a BepInEx preloader crash log (`preloader_*.log` beside the game) written by this launch is quoted in the failure (its first `[Error` or `[Fatal` line) and kept in the client's evidence as `game-2.preloader-N.log`. One from before this launch is only named, in `preloader.stale`, and never taken as the cause. |
| ValheimCLI in `BepInEx/scripts` with ScriptEngine's `LoadOnStart = false` (its default): the client never answered | Static | A pinned plugin found in `scripts` needs ScriptEngine itself installed and pinned in `plugins`, and `[General] LoadOnStart = true` in `BepInEx/config/com.bepis.bepinex.scriptengine.cfg`. The message also offers the simpler layout: the current core and packs in `plugins`. |
| An old monolithic ValheimCLI answers `cli_expect` but has no `cli_extensions`; a core without its packs | Live, once the client answers, before the world round | `CliCapabilities.Require(actor, paths)` reads `cli_extensions` once and names every missing command and the pack that provides it (`valheim.session`: Standard; `valheim.world`: World Tools), or says that this ValheimCLI predates command packs. `GameActor.RequireCapability` gives the same messages. A hosting client's `ClientRounds` require `CliCapabilities.HostedRounds`. |
| The monolithic ValheimCLI, and a core and packs with the right file names and plugin GUIDs from an older generation without `valheim.session/state`, `save` and `leave`, both found only after the client started | Static, with a `cliManifest`, before anything is copied or started | The staged ValheimCLI files are compared by SHA256 with the manifest of one coherent build, and the set must provide every capability the run uses; see [ValheimCLI capability manifest](#valheimcli-capability-manifest). The live check above still runs. |
| A generated standing expectations file put eight `key=value` pins on one line | Static, when ValheimCLI's config sets `[Expectations] File` | `StandingPins.Format` and `Write` write one pin per line, each checked with ValheimCLI's own parser; `Parse` and `Read` check a file and name a line that holds several pins. The preflight also refuses a configured file that is missing, a strict one (`Strict = true`) that names no world (every command is refused once a world loads; `world=any` lets the transition through while the actor still pins the exact UID), and one that contradicts the plan's pins or hosted world UID. |
| A reused world name hid another snapshot with another UID | Static, before the fixture is copied | `WorldIdentity.Read(fixture)` reads the name, seed and UID from the fixture's own metadata (`<name>/_main.<n>.fwl2` or `<name>.fwl`); `HostWorldPlan.Preflight()` refuses a `worldUid` the fixture does not hold, naming the UID it does. After the start, another UID fails as the wrong world, with both UIDs, never as a load failure. |
| A hand-typed candidate file name was wrong | Static | `InstallPins.Plugins(install, files)` derives pins from the staged files and refuses a name that is not there, listing what the folder holds. The preflight refuses a pinned MD5 that no DLL in `BepInEx/plugins` or `BepInEx/scripts` has (naming similarly named files and their hashes) and one installed more than once; a pinned fixture whose files changed is refused before copying (`WorldFixture.Verify`), naming each file. |

The world metadata is read as a length-prefixed package that starts with the world version, the name, the seed name, the seed and the UID; on 1.0.16 chunked saves (version 41) the UID read this way matched what `cli_world` reported for them, and older `.fwl` files (version 37) have the same layout. `FileHash.Md5(path)` is the hash `cli_manifest` reports.

Limits: the plugin checks need strict pins, so an unpinned client skips them. A Doorstop proxy is recognised by the key its code holds (Doorstop 3 `targetAssembly`, Doorstop 4 `target_assembly`); one that holds neither or both is refused, since its configuration cannot be matched to it. Every check of an install on another host (a campaign's source inspection, a remote client before launch) uses one list of the loader files each platform needs (`BepInExLoader.LoaderFiles`, also the remote launches' required files): the Windows proxy and configuration or the Linux `doorstop_libs/libdoorstop_x64.so`, beside the preloader and core; a macOS install needs either `libdoorstop.dylib` or BepInExPack's `doorstop_libs/libdoorstop_x64.dylib`. A remote client's files are checked for existence in one round trip; only the Windows proxy and configuration are read. The live BepInEx check covers owned clients; an owned server already fails its startup on an exit before BepInEx wrote its log, but not yet on a missing line while it runs. A remote client the hosted run opens (`HostedServerRun`) runs the loader-file and Windows proxy checks before launch, but not yet the other install checks; `InteractiveClient.StartAsync` called directly checks only its launch's required files. The checks were tested with fakes and hand-built files; none of them has run against a native game yet.

### ValheimCLI capability manifest

A staged ValheimCLI can be the wrong generation: an old monolithic build with no extension API, or a core and packs whose file names and plugin GUIDs look right but which do not offer `valheim.session/state`, `save` or `leave`. A file name, plugin GUID or version cannot tell these apart from the current set; the DLL's hash can. A `CliCapabilityManifest` records one coherent ValheimCLI build (its core and packs): each DLL's file name, full SHA256, the BepInEx plugin GUIDs it declares, and the extension commands it registers with their result versions. It is a small JSON file:

```json
{
  "schema": 1,
  "build": "tvongaza/valheimCLI d112140 (core, Standard, World Tools)",
  "files": [
    { "file": "valheimCLI.dll", "sha256": "<64 hex>", "plugins": ["valheimCLI.valheimCLI"], "extensions": {} },
    { "file": "Valheim.Cli.Standard.dll", "sha256": "<64 hex>", "plugins": ["valheimCLI.standard"],
      "extensions": { "valheim.session": { "join": 1, "leave": 1, "save": 1, "state": 1 } } }
  ]
}
```

An owned client is always checked against a manifest: its disposable copy's against the staged set's (the plan's `cliManifest`, else the pinned bundle's), and an install run in place against its `cliManifest` when it names one. Before the copy exists, the runner's own capabilities (the hosted rounds' session commands, the arrival waits) are checked against a named manifest and recorded, so the copy's check before its launch covers them. On the install it checks, `ClientRunPlan.Preflight()` (and so the hosted `ClientRounds` and `ClientSession.Launch`) refuses before anything is started:

- a manifest file that is missing or malformed: it is never treated as absent;
- a manifest DLL that no file in `BepInEx/plugins` or `BepInEx/scripts` (any subfolder) has by SHA256, or that is installed more than once;
- any other DLL there with one of the manifest's file names, or declaring one of its plugin GUIDs (read from the assembly's `[BepInPlugin]` metadata, never by loading it): another build, a stale copy or a renamed one, so a mixed set is refused, and replacing any declared DLL without updating its hash invalidates the manifest;
- a manifest DLL in `BepInEx/scripts` when ScriptEngine is not pinned in `BepInEx/plugins` with `LoadOnStart = true`, even if that pack is not separately pinned in the plan;
- a set that lacks a capability in the plan's `capabilities` or the runner's own (the hosted `ClientRounds` add `CliCapabilities.HostedRounds`), or offers it with a result version other than 1.

File and capability mismatches name the file, the hashes found and expected, and the capabilities lost; a set whose files register no extension commands at all is named as a monolithic ValheimCLI. A ScriptEngine refusal names the manifest file in `scripts` and the missing startup setting. DLLs the manifest does not mention (the mods) are not judged here. `plan.CheckCliManifest(capabilities)` checks the file set and capabilities alone and returns what it found (`CliManifestCheck`: the build, the installed files, the capabilities); `CliCapabilityManifest.Read(path).Check(install, capabilities)` does the same without a plan. The plan's full preflight also checks that ScriptEngine can load any manifest files in `scripts` at startup.

The report's provenance says which checks ran (`ClientRounds` records it): `cliPreflight` is `static and live` for an owned client, `live only: an attached client's files are its operator's` for an attached one, and `live only: static check not run: your install, run in place` for an install run in place without a `cliManifest`, where nothing claims a static pass that did not happen. An attached client takes no manifest (`Validate` refuses one); its `capabilities` are required live when the session attaches. A targeted regression's `regression.json` must name its `cli.manifest` (`valheim-test start` writes it), so its staged set is always checked.

The toolkit hard-codes no ValheimCLI version. The pinned ValheimCLI fork writes its build manifest with `CliBuildManifest.Write(build, dllPaths, output)`; `CliCapabilityManifest.Read(output)` validates that manifest before the toolkit uses it. `CliCapabilityManifest.Generate(build, dllPaths, listing)` remains a convenience wrapper over the same fork-owned metadata reader. It hashes each DLL, reads its plugin GUIDs, and reads the extensions from its IL: each `ExtensionRegistry.Register(id, version, apiVersion, new ExtensionCommand(name, ..., resultVersion), ...)` with literal names, as ValheimCLI's packs register them. Registrations without literal names and console-module listings (`cli.standard/commands`) are not claimed; a registration whose shape it does not recognise is refused rather than guessed. Pass `listing`, the `cli_extensions` reply of a client that loaded exactly these files (from its `client-commands.jsonl`, for example), and the generator also requires every owner the files register to be live there with the same commands and versions, so the game confirms what the IL says. `Write(path)` and `Read(path)` check the format.

Limits: the static check proves which files are installed, what their IL registers, and whether ScriptEngine is configured to load manifest files in `scripts` at startup. It cannot prove that BepInEx actually loads them or that their registrations succeed in the game; `CliCapabilities.Require` after launch stays authoritative. Generating from IL covers ValheimCLI's registration pattern, not every way a plugin could register an extension.

## Targeted native regressions

Many third-party regressions need the same small shape: one owned client hosting one disposable fixture world, one mod under test in a parent and a candidate build, its dependencies and perhaps a probe. Hand-written A/B runs of this shape spend most of their attempts on setup: a fixture passed one directory too deep, a dependency the mod declares but nobody staged, a stale ValheimCLI pack set, a wrong DLL staged under the right name. [TargetedRegression](../../examples/TargetedRegression/README.md) is a copyable template for that shape; the library part is a manifest, a stager and a preflight, and the run itself is the existing hosted `ClientRounds`.

`RegressionInputs` holds what the run loads: the disposable character, the fixture root and UID, the ValheimCLI core and packs, other plugins, an optional probe and the mod's arms, each with its file, SHA256 and source commit. Where it runs is not in it. `new TargetedRegression(inputs, capabilities, inventory, clientEnvironment)` takes the machine from the [environment inventory](Valheim.Testing.GameSessions.md#game-hosts-and-the-environment-inventory)'s client environment (its first, or the one named; this machine with no inventory): the prepared game is its install (only read), the disposable install is `<runtime>/regression-<name>`, the port is its `cliPort` and the loader its `loaderPackage`. The environment must be on this machine. `TargetedRegression.Read(regression.json)` uses the `environments.json` beside the file when there is one, as `valheim-test start` writes it for `--game`, otherwise this machine. `RegressionInputs.Read` resolves relative paths against the file and refuses unknown fields. It refuses a retired environment manifest (`game`, `install`, `loaderPackage`, `client.port`, `client.saveDirectory`, `client.steamUserDataDirectory`), naming where each field now comes from. Scenario source stays free of all of it.

For an owned client, `client.environment` in the regression JSON sets non-secret process variables on its disposable game process, such as a mod's documented defer-generation switch. The same `environment` field is available on an owned `ClientRunPlan`; attached plans refuse it. Validation rejects invalid names, multiline values and loader overrides before copying or launching the game. It is not a credential channel: scenario evidence may include the plan.

`TargetedRegression.Stage(arm)` works without the game and refuses at the first problem, naming the field and the fix:

| Check | What is refused |
|---|---|
| Fixture layout (`FixtureLayout.Discover`) | A root that is the world folder itself, a `worlds_local` wrapper, several worlds or none, each named with the expected one-world tree and the tree found; then a world whose own metadata holds another UID (`HostWorldPlan.Preflight`) |
| Hashes | A file that is missing or not its pinned SHA256 (an empty `sha256` prints the hash to review); an arm whose file is another build than its commit's; two arms with one SHA256 unless `mod.repeatability` |
| Clean install | An existing install directory this tool did not create (`valheim-testing-install.json`); the install copies the game except `BepInEx/plugins`, `patchers`, `config`, `scripts` and `cache`, which are rebuilt from the manifest only. Each arm is copied under its own artifact name first |
| Declared metadata (`PluginMetadata.Read`, no assembly loaded) | A hard `[BepInDependency]` no staged `[BepInPlugin]` declares, or one older than its minimum version; a staged `[BepInIncompatibility]`; a plugin whose `[BepInProcess]` excludes the client; one GUID declared twice; an assembly reference that neither the game's Managed folder, `BepInEx/core` nor a staged DLL provides (unless listed in `optionalReferences`). File names never count |
| Plan | The disposable character missing from `characters_local`, then the strict plan's own `Validate` and `Preflight` on the staged install, which with `cli.manifest` includes the [static ValheimCLI capability check](#valheimcli-capability-manifest): the hosted rounds' commands and the scenario's capabilities owned by ValheimCLI (`valheim.*`, `cli.*`). A probe's or the mod's own commands are checked live only, before the first round |

It returns a `StagedArm`: the strict `ClientRunPlan` (every staged plugin's declared GUID pinned by its MD5, no `absent` pins for anything else; the clean install loads nothing unlisted), its `RunManifest` (the arms, the allowlist with SHA256 and MD5, the install pins, the world and capabilities; install-relative paths only) and `Verify()`, which refuses any file added, changed or removed in the staged folders since. `Preflight()` stages every arm in turn. `Run(arm, output, scenario, rounds, measure)` stages the arm, writes `run-manifest.json`, calls `Verify()` right before the launch, runs the hosted `ClientRounds` with the scenario's capabilities required live before its first round, scans the client's logs and writes the report in every outcome. `Remove()` deletes the disposable install, only when it carries the marker.

Limits: one owned client hosting one world. The disposable install is a full copy of the game on first use, copied again when the game build, the loader or the set or contents of files at the game's root and in `doorstop_libs` change. The checks read what BepInEx reads before loading; a dependency found by reflection at run time is caught only live. Characters and machine reservations stay with the environment's own procedure. The checks are tested with emitted assemblies and fake installs.

A public copy of a regression for review (scrubbed sources, a pinned project, the A/B table from the checked evidence) is made with the maintainer tool [tools/regression-bundle](../../tools/regression-bundle/README.md), which is not part of any package.

## This machine's environment inventory

`EnvironmentInventory` describes the machines and installs a run may use; with no file it is this machine. Placing a session's actors on it, other machines and Steam-account leases are [`Valheim.Testing.GameSessions`](Valheim.Testing.GameSessions.md#game-hosts-and-the-environment-inventory)'.

### This machine, with no file

On one Windows PC with Valheim installed through Steam, there is nothing to write. With no inventory file (`EnvironmentInventory.Read(null)`, a campaign that leaves out `inventory`, or `valheim-test env list` and `env preflight` without `--inventory`), the inventory is this machine. It contains host `local`, with `local-server` from Valheim Dedicated Server (Steam app 896660) and `local-client` from Valheim (Steam app 892970).

Steam is found as follows:

- Windows: the registered `HKCU\Software\Valve\Steam` `SteamPath`, then `Program Files (x86)\Steam`.
- macOS: `~/Library/Application Support/Steam`.
- Linux: `~/.local/share/Steam`, `~/.steam/steam`, then the Flatpak's.

Each app is then found in every library `steamapps/libraryfolders.vdf` lists, through its `appmanifest_<id>.acf` `installdir`. An install counts only if its executable is there.

Under ValheimTesting's own folder (`%LOCALAPPDATA%\ValheimTesting`, macOS `~/Library/Application Support/ValheimTesting`, Linux `$XDG_DATA_HOME/ValheimTesting`), the defaults are:

- runtimes in `runs\<environment>`;
- the host lock in `lock`;
- Steam-account leases in `leases`;
- the run journal in `journal`.

A no-game test moves the whole folder to a temporary one with a [`FakeDataRoot`](Valheim.Testing.Game.md#test-fakes) scope.

The ports are ValheimCLI 5688 for the server and 5689 for the client, and game port 2486. These are valheim-test's own ports, kept away from Valheim's standard 2456, so a personal server on the same machine or network keeps its port and a crossplay lobby (keyed by public IP and port) never takes another server's joins. Each further local environment takes the next CLI port not already used on this machine (by a local or host-network container environment, or an ssh tunnel) and a game port whose three-port range is clear.

`valheim-test env list [--inventory FILE] [--json]` prints each detected or assumed value on a `detected:` line, each thing it looked for and did not find on a `NOT FOUND:` line (with every path it tried), and each environment with its host, roles, install, runtime and ports. It gives no verdict; it refuses only an inventory it cannot read (on this machine with no file: no Valheim install found, naming every path it tried). `valheim-test env preflight [--inventory FILE] [--json]` prints the same lines and says whether a one-off can run: it refuses an inventory without a server and a client. It also reads this machine's run journals (its own and those of the inventory's local hosts; `session check SESSION --hosts` reads every host's) and refuses, in the same words as a session's preflight, while a run of another process is still going there, may still be going, or left something (`RECOVERABLE` or `UNRECOVERABLE`) that was not recovered, or while a journal cannot be read (`EnvironmentRuns.LocalJournalProblemsAsync`).

A missing dedicated server is reported with three ways forward: install it from Steam (it is free), add a server environment, or run `valheim-test start` for a hosted local world. A Mac gets no local dedicated server, because the campaign runner does not run a macOS server.

A file lists the environments to use, in preference order. A file never gains this machine's environments unless it lists them, so an inventory of other machines is read exactly as written. An environment on this machine (on a host of kind `local`, or with no host) needs only its name and role, for example `{ "name": "local-client", "roles": ["client"] }`: its install, runtime and ports are filled in as above. If the file names its own `local`-kind host, environments without a host go to that host. `leaseHost` and `leaseDirectory` default to this machine's only when every client is on it. Two inventories on one machine exclude each other only if they share the host lock and lease folder; leave `lock` and the leases out of a file for this machine to share the defaults. Every run's `result.json` records what was detected (`inventoryDetected`), and a run with no file records `inventory: this machine`.

## Terrain, surface and paint probes

`TerrainProbe` validates coordinate identity, metres, completeness and explicit generator versus loaded-ground layers. It compares up to 256 declared independent expectations and reports every residual. See `examples/ObserveCheck`'s `ground` probe for a read-only game check and `examples/SharedWorld` for a no-game example with declared expectations. Neither a replay of its own capture nor a synthetic plane alone establishes Valheim terrain conversion or client physics.

`SurfaceProbe` and `examples/ObserveCheck`'s `surface` probe compare loaded heightmap vertices and **their own** mesh colliders separately. They also require three stationary, grounded local-player observations; correct position alone, flying, an attachment or an active teleport is insufficient.

To record a site's ground, collider and paint as evidence rather than assert on it, use a [terrain site snapshot](../terrain-site-snapshots.md); for a site's objects, an [area object snapshot](../area-object-snapshots.md). `SiteSearch` finds test sites on a freshly created world from the generator's heights read through ValheimCLI, never from the mod under test; the mod's own rule decides what a site is.

## Lifecycle steps: leave the area and log out

Beyond save, restart and rejoin, two lifecycle events break mods: the game unloading a zone the player has left, and the character being written at logout. `ZoneCycle` and `LogoutCycle` drive each once from a joined, protected client, observe the event instead of waiting a fixed time, and leave the client joined for the mod's own re-observation. They read two read-only client observations from ValheimCLI's optional Observe pack: `valheim.observe/zones` and `valheim.observe/custom-data`. Both run inside a `ClientRounds` measurement, where each part becomes a `{round}: ...` step and the readings are written to `{round}-zone-cycle.json` or `{round}-logout.json`, whether the cycle passes or fails.

**Leave the area and come back.** In 1.0.16 a client keeps a zone's objects while its player is within its simulation distance: every object within *near* rings of zones round the player's zone, distant objects (large trees, locations) up to *near + far* rings, and the zone's terrain within *near* rings, removed once it has been out of that range for 4 s and its last near object has gone. The graphics setting picks the distance (near 1 to 6, far 2; the default is near 2, far 2, square), and the server lowers a client's to its own. Leaving destroys each object's instance; returning recreates it from its saved data. So a value kept only in a component field is gone, and a component whose teardown throws shows up in the log scan as `nre-remove-objects`.

`ZoneCycle.Run` reads the `Zones` of interest and requires them loaded (terrain, and an instance for every saved object), then reads the client's simulation distance and refuses an `Away` point whose zone is fewer than near + far + 1 rings from any of them, before anything moves: nothing of a zone is unloaded closer, in any mode. The player arrives at `Away` with `PlayerPlacement.Arrive` (one teleport by the server, arrival read on the client, refused while flying); the zone the player actually stands in must be far enough too. It then waits until the client holds nothing of the zones (no terrain, no instance), has the player arrive at `Back` and waits until they are loaded again. `Away` and `Back` are declared dry ground, as for `ClientRounds.Arrival`. `StepTimeout` bounds each of the four waits; expiry names the zones still pending and the last reading, and no teleport is repeated. `ZoneId.Around(x, z, radius)` lists the zones round a site, and `ZoneCycle.RingsToLeave(range)` says how far is far enough.

**Log out and log in.** In 1.0.16 the character is saved inside the logout, before the menu loads: the game writes `<name>.fch.new`, moves the previous file to `<name>.fch.old` and renames the new one to `<name>.fch`. It skips the save when its save system blocks character saves (logged "Character save blocked") and when the disk is full; a mod that breaks the save at quit (another mod's `UnpatchAll`, an exception in a save patch) has the same effect. The custom data (`Player.m_customData`) is saved with the player and read back when the character next spawns.

`LogoutCycle.Run` reads the custom data and requires every one of `Keys` set, a character the game saves `Local` and the plan's character. It hashes `<CharactersDirectory>/<profile file>.fch` (SHA256), which must be in a folder named `characters_local`, the game's local characters; a cloud character is refused. The client leaves to its menu (ValheimCLI's session leave, which issues the logout and replies once the menu is up), and the runner waits up to `WriteTimeout` for the file's hash to change, woken by file events and re-reading every `RereadInterval` for filesystems that raise none. Then the client joins again with the plan's character, protected, as `ClientRounds` joins, and every key must come back with its value. `LogoutResult.OldMatchesBefore` says whether the `.fch.old` backup is the file hashed before: one save replaced it, not several.

```csharp
// Pin ValheimCLI's Observe pack on the joined client; the mod adapter needs no zone or custom-data command.
var zones = new ZoneCycle
{
    Zones = ZoneId.Around(site.X, site.Z, 16),
    Away = new HeightExpectation(site.X + 640, site.Z, 31.2f), // declared dry ground ten zones away
    Back = site, StepTimeout = TimeSpan.FromSeconds(60),
};
var logout = new LogoutCycle
{
    Capability = "valheim.observe/custom-data", KeyPrefix = "mymod.", Keys = ["mymod.home"],
    CharactersDirectory = Path.Combine(clientSaveRoot, "characters_local"), WriteTimeout = TimeSpan.FromSeconds(10),
};
rounds.Run(server, openClient, round =>
{
    var before = ReadMarkers(round.Client);                       // the mod's own observation
    zones.Run(round);
    round.Step("the markers survive the zone reload", () => Compare(before, ReadMarkers(round.Client)));
    logout.Run(round, plan.Client, worldUid);                     // leaves, checks the write, joins again
});
```

`ClientRounds` makes the client leave after each measurement, so the logout cycle leaves the client joined again for it. Scan the client's logs at teardown (`ScenarioReport.ScanLogs`) for `nre-remove-objects` and errors during logout.

Limits: in CI both helpers are tested against scripted transports, with the negative controls a native check needs (a component field that does not survive the reload, an away point inside the loaded range, zones that never unload, a logout that writes nothing, a key the save leaves out). The adapter observations compile against declared signatures. Native run (Valheim 1.0.16 Windows server and client, [the native acceptance suite's lifecycle-world scenario](../../tests/Valheim.Testing.NativeAcceptance/README.md#native-campaign)): `ZoneCycle` unloaded and reloaded the marker's zones and the marker came back with its saved label, and `LogoutCycle` saw the character file rewritten by the logout and the custom data back after rejoining; the two control mods (a value kept only in a component field, a suppressed profile save) each made their check fail for the named reason. The runner must see the client's character folder: an owned client's on this machine, or a mounted copy of an attached client's. An unchanged hash is all the runner sees of a save that rewrote identical bytes; a moved player or a changed value makes the file differ. A world save asks every client to save its profile, so a save in the window between the hash and the leave counts as the logout's own (`OldMatchesBefore` is then false).

## World observations: global keys, synced config, vanilla clients, dungeon rooms

The runner reads generic observations from ValheimCLI's optional Observe pack. Only the fixture's guarded global-key mutation remains in the native acceptance adapter. The observations were previously implemented in the adapter and exercised on a 1.0.16 dedicated server with a joined client; the moved Observe pack still needs its own native check. The runner side is tested with scripted replies, including negative controls.

For location authoring context, the wiki explains [altitude relative to sea level and terrain-modifier ordering](https://github.com/Valheim-Modding/Wiki/wiki/Creating-Locations). Those notes are not evidence for the room encoding, zone pairing or replication behavior measured here; the pinned 1.0.16 run and game-code checks below are.

Install and pin `Valheim.Cli.Observe.dll` on each actor that uses `valheim.observe/*` commands. The [adapter page](Valheim.Testing.Adapter.md) describes the remaining mod-specific boundary.

### Global keys

In 1.0.16 a key change goes to the server, which applies it and sends its whole list to every client; each client replaces its list with it. Keys are stored lower case, as `name` or `name value`. `GlobalKeyFixture.Apply(server, client, changePath, listPath, set: ["defeated_eikthyr"], remove: ["nomap"], timeout, interval)` issues each change once through the fixture command (which refuses unless `FixtureGate` allows fixture commands), checks the server kept it, then waits until the client lists exactly the server's keys; expiry names the keys the client lacks and the ones only it has. `Set`, `Remove`, `Read`, `Compare` and `WaitForClient` are the pieces. The game's `setkey` console command is not used: it refuses a key that is not a world-modifier setting (a boss key, for example) unless the game already counts as cheated, and that check reads the world-modifier menu. ValheimCLI's `cli_check_global_key` answers for one key at a time, so it cannot show a key only the client has. A world-modifier key (one the world-modifiers menu sets, such as `nomap`) set or removed through `GlobalKeyCommands.Change` is also written into, or removed from, the world's saved settings (its starting global keys), as the game does for any change of such a key; other keys, boss keys for example, are saved only in the world's own key list.

### Synced config

`SyncedConfig.Read(actor, "valheim.observe/config", guid, section, key)` reads the entry's current value in that process, as BepInEx would write it to the file (`true`, `5`, `1.5`), with its type and default. The observation reads the `ConfigEntry` itself on each side: how the mod syncs it (ServerSync embedded in the mod, Jötunn, its own RPC) is the mod's business, and a synced mod sets the client's entry. Sections and keys are percent-encoded on the way (`Server%20Settings`), because extension arguments are single tokens. `WaitForValue(client, ..., expected, timeout, interval)` waits for a value to arrive, for example after an admin change on the server; a plugin that is not loaded or an entry that does not exist fails at once, since that value can never arrive. `RequireSame(server, client)` compares both sides. Only entries in the plugin's own `Config` are found. Nothing here writes config.

### Vanilla clients

A server-side mod that says clients do not need it fails quietly on a client without it: in 1.0.16 an object whose prefab only the mod registers is never created there (the game logs "Missing prefab hash" and skips it), a per-object RPC without a handler logs "Failed to find rpc method", and objects can throw while they unload. Give the client BepInEx, ValheimCLI and the mod's test adapter, pin the mod `absent` in the client plan, and use `VanillaClientCheck` as a `ClientRounds` measurement (`measure: check.Measure`): for each of its `Points` it arrives there, waits for a complete census of the objects within `Radius` (the census is complete once every zone it touches has loaded; the adapter leaves out the client's own player object, which is always there, so an empty census proves nothing), and fails on any unresolved hash, naming it and, when one of `KnownPrefabs` hashes to it, the prefab. With `ClientLogs` it then scans the client's logs so far and fails on `missing-prefab-hash`, `rpc-method-missing` and `nre-remove-objects` lines. Pass `VanillaClientCheck.LogClassifications` to the run's teardown scan as well, so those lines fail the whole run wherever they appear. Evidence: `{round}-vanilla-client-{n}-arrival.json`, `{round}-vanilla-client-{n}.json`, `{round}-vanilla-client-logs.json`. `StableHash.Of(name)` is the game's prefab hash. A client loads zones, and so objects, only within about near simulation distance x 64 + 32 m of its player (about 160 m at default settings): keep `Radius` inside that, since a larger census never becomes complete on a client.

### Dungeon rooms

In 1.0.16 a dungeon generator saves its rooms as one byte array, `roomData`: an int32 count, then per room the room prefab's name hash, its position and its rotation as Euler angles (little-endian int32 and float32). Worlds saved before that keep `rooms` and `room<i>`, `room<i>_pos`, `room<i>_rot` fields, which the game reads when `roomData` is absent and replaces at its next save; the observation reads either and says which (`Format`). The game gives the interior its environment with a 64 m wide box centred on the location's zone, 5000 m above the location, so a room reaching outside that zone is partly outside the interior. `DungeonRooms.Read(server, path, x, z)` lists the generators near a location's ground position, each with the location nearest (x, z) in the 3 x 3 zones around it (the game keys a location by the zone it stands in, so it is found from the query rather than the generator's zone, and a generator displaced into a neighbouring zone still pairs with its location and fails the zone comparison); a dungeon has no saved generator until its zone has been generated, so `Read` returns an empty list for an unvisited dungeon; `InteriorOffset` is the generator's position minus the location's (the generator's offset in the location prefab, turned by the location's rotation). `RequireWithinZone(dungeon, sizes)` fails naming every room that reaches past the zone's edge, a generator standing in another zone than its location, a dungeon without saved rooms and one without a location. Give room sizes (`Room.m_size`, by room prefab name) to check each room's footprint turned by its yaw; a room without a size is checked by its centre only, which cannot see an oversized room.

Native run (Valheim 1.0.16 dedicated server and a joined client, [the native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md#native-campaign)): `defeated_eikthyr` set on the server was listed on the client and survived a world save and restart; a config entry changed on the server reached the client and survived a restart; a client without the mod resolved every prefab hash near the site, and a prefab registered only on the server was named by its hash (`1334784479`, `MyModControl_ServerOnly`); a `SunkenCrypt4`'s saved rooms (1.0 `roomData`) all lay in its location's zone, with an interior offset of about (0.63, 5001, 0.26).

Not validated in game: an oversized room in a custom test dungeon failing the check, and a generator displaced from its location's zone; both are covered only by scripted replies.

## Registered content census

A registration double (#21) shows that a mod calls ObjectDB or ZNetScene; only the running game shows what each process ended up with. An item can be missing on a client whose registration ran too early, a recipe can point at a crafting station or resource the game cannot find, and two names can share one hash. The content census (#91, #114) asks each process for its items, recipes, network prefabs, build-table pieces and status effects by stable identity, then reconciles them with what the mod declares for each side.

**Declare the expectations** in a file the mod's system tests own, from the mod's design, never from a census (a census copied into its own expectations can only pass):

```json
{
  "owner": "example.mymod",
  "scope": ["MyMod_", "Recipe_MyMod_"],
  "items":   [{ "name": "MyMod_SurveyStake", "sides": ["server", "client"] }],
  "prefabs": [{ "name": "MyMod_SurveyStake", "sides": ["server", "client"] },
              { "name": "MyMod_SurveyPost", "sides": ["server", "client"] }],
  "pieces": [{ "name": "MyMod_SurveyPost", "tool": "Hammer", "sides": ["server", "client"],
               "station": "none", "resources": ["Wood"] }],
  "statusEffects": [{ "name": "MyMod_SurveyBlessing", "sides": ["server", "client"] }],
  "recipes": [{ "name": "Recipe_MyMod_SurveyStake", "sides": ["server", "client"],
                "item": "MyMod_SurveyStake", "station": "piece_workbench", "resources": ["Wood"] }]
}
```

`owner` is the plugin GUID whose build must be pinned on each side. `scope` lists the mod's own name prefixes: every expected name starts with one, and only names in scope can be unexpected. An entry names the prefab, recipe, piece or effect object and its required `sides`. A recipe may declare the `item` it crafts, its `station` (a prefab name, or `none` for crafting by hand) and its `resources` (item prefab names). A piece must declare the `tool` whose `PieceTable` contains it; it may also declare its station and resources. A prefab existing in `ZNetScene` without the piece in that tool's table is **unresolved**, never present. Status effects resolve by `ObjectDB.GetStatusEffect(NameHash())`, with collisions detected across the full status-effect list. Optional dependencies left out are not checked. Unknown keys, duplicate declarations, invalid sides or names outside scope are refused. `ContentExpectations.Load(path)` reads the file.

**Install the optional Observe pack** on both server and client and require `valheim.observe/content-census`. It is read-only and needs a loaded world. A census whose reply would exceed ValheimCLI's 256 KiB extension result (a large content mod, or a broad prefix) fails `result_too_large` naming the prefixes and how many entries of each kind it held; name fewer or narrower prefixes.

**Read and reconcile** each side through its own strictly pinned actor:

```csharp
var expectations = ContentExpectations.Load("content-expectations.json");
var server = ContentCensus.Read(serverActor, "valheim.observe/content-census", expectations);
var client = ContentCensus.Read(clientActor, "valheim.observe/content-census", expectations);
var report = ContentCensus.Reconcile(expectations,
    new SideObservation(CensusSide.Server, plan.Pins["example.mymod"], server),
    new SideObservation(CensusSide.Client, plan.Client.Pins["example.mymod"], client));
round.Write("content-census", new { server, client, report }); // evidence first
report.RequirePassed();
```

`Read` throws for a census that is not ready (no world, the registries not populated yet, a client whose player has not spawned), for an empty registry, for a reply for another owner or scope and for any malformed reply: none of them is an empty census. `Reconcile` gives every expected entry a state per side, and every in-scope entry a side was not expected to have is unexpected:

| State | Meaning |
|---|---|
| `present` | Registered once and the game's own lookup resolves it; a piece also appears in its declared tool's build table with an enabled `Piece` component |
| `missing` | Not registered on that side, not observed there, or listed but not found by the game's lookup (registered after the index was built) |
| `unexpected` | In scope on that side but not declared for it, or a recipe resource that is not declared |
| `duplicate` | Listed more than once, or its hash shared with another name (the game's indexes use `Dictionary.Add`, so one of them is not indexed), or two recipes of one name |
| `unresolved` | A recipe or piece dependency the game cannot find, a piece missing from its declared tool's table, or a table piece missing from `ZNetScene` |
| `unsupported` | A check the census cannot answer: an older adapter that omits the kind, a duplicated recipe's dependencies, or a reference without a name. Never a pass |

A side is refused, and its expected entries are missing, when no observation was supplied for it, when the observation reports being the other side, or when its owner plugin is not loaded or is another build than pinned (`stale build: ...`). The census reports the MD5 of the owner's file as ValheimCLI's strict pins hash it, and `Reconcile` takes the pinned MD5 or a prefix of at least 8 hex characters; the actor's strict pins still check every loaded plugin, and whether a file changed after it loaded, before each command. `Passed` holds only when every side with expectations was accepted and every entry is present. `Failures` lists every problem as `side: state kind name (why)`.

**Which checks need a client.** Every process builds its own registries from its own plugins, so a server census says nothing about a client: a client expectation is satisfied only by that client's own census, and a server census handed in as the client's is refused. Declare `client` for items and recipes players craft or carry, build pieces they place, status effects applied to them, and prefabs created on the client. A server-only entry declares `["server"]`, and the client then must not have it in scope. A client census is read only once the client has joined and its player has spawned; later registrations still need a later census.

**When the adapter reads.** On demand, never at a registration hook. In Valheim 1.0.16 the world scene's `ObjectDB.Awake` indexes its items and `ZNetScene.Awake` its prefabs as the scene loads, and mods register in postfixes on those, so both have settled before a world loads; the main menu's own ObjectDB (`FejdStartup.SetupObjectDB`) is not the world's and is never read. A recipe's item and resources resolve when `ObjectDB.GetItemPrefab` returns a prefab of that name whose shared item name is the reference's (crafting adds the result by prefab name and counts resources by shared name); its station when `ZNetScene.GetPrefab` returns a prefab of that name with a crafting station of the same station name. Nothing else is looked up.

The [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md#native-campaign)'s `content-census` scenario runs it on a server and a joined client in both rounds. Its controls omit the recipe or status effect in a separate MyMod build; each must fail for exactly that omission.

Limits: the runner side is tested against scripted replies and the adapter compiles against declared Valheim 1.0.16 signatures, but this new piece/status-effect slice has not yet run in game. Ownership of an entry is not observable (the registries do not record which plugin added it), which is why scope uses name prefixes. The census checks registration and resolution, not whether a player can build a piece or whether an effect behaves correctly. Localization tokens remain out of scope.

## Harmony census

ValheimCLI's optional Observe pack command `valheim.observe/harmony` lists every patched method with each patch's owner, kind, priority, index, before/after and patch method, from HarmonyX's own record. A patch whose target method is missing is easy to miss. On the Valheim 1.0.16 Windows dedicated server (BepInEx 5.4.23.5, HarmonyX 2.9.0) the missing target leaves one `accesstools-not-found` warning (`AccessTools.DeclaredMethod: Could not find method ...`) in the server's BepInEx log. Then `PatchAll` throws "Undefined target method", as the modding wiki's troubleshooting logs show, and only Unity's own log (`-logFile`) records the exception. The [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md#native-campaign)'s control logs a line after `PatchAll`, and that line never appeared: the rest of that plugin's `Awake`, including its later patch classes, never runs, and the mod stays loaded half-patched. The teardown [log scan](#log-scan-at-teardown) fails on both lines by default, but only after the run; the census names the missing patch while the run goes on. `HarmonyCensus.Read(actor, "valheim.observe/harmony", owner).Check(owner, declared)` compares the census with the patches the mod declares (`new DeclaredPatch("Terminal::InitTerminal", "postfix", "MyMod.Plugin+RegisterCommands::Postfix")`; a target without a parameter list names every overload). `RequireApplied()` fails naming each declared patch that is not applied; other owners' patches on the same methods are reported beside it, never failed. `HarmonyCensus.OthersChanged(before, after, owner)` lists other owners' patches that a reload or unload removed or added. The toolkit's own reload path and adapter helpers never unpatch; an adapter that patches unpatches only its own Harmony ID (`harmony.UnpatchSelf()`), never `Harmony.UnpatchAll()`. [FullLifecycle](../../examples/FullLifecycle/README.md) checks its mod's patch first, and the [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md)'s `patchReload` plan section checks an unload in game: a script patching MyMod's method is loaded, replaced and removed through ScriptEngine, and `OthersChanged` stays empty each time (1.0.16 Windows server), while a control that also removes MyMod's ID is named. A mod that calls `Harmony.UnpatchAll()` removes ValheimCLI's patches as well: in that control no CLI command ran afterwards, so a run can lose its own transport, and the teardown scan's `harmony-unpatch-all` failure is what names it.

## Test fakes

`Valheim.Testing.Game.Fakes` tests scenario and session code without a game:
- `ScriptedTransport` answers strict pins, the extension listing, registered extension commands (in the real `EXTENSION_RESULT` envelope), confirmed saves and any command a test registers. It throws on anything unscripted, records every command, and `Actor()` returns a pinned `GameActor` on it.
- `FakeOwnedProcess` is the one fake `IOwnedProcess`, for an owned server or client (for example `ClientSession.Launch(plan, output, () => process, connect, ready)`): `Exit(code)` ends it, `FakeOwnedProcess.Exited(code)` is one that crashed during startup, `IgnoreQuit` makes a clean stop end in a kill, and `StopFailure` makes every stop throw (a refused or unproven stop). It counts `Stops` and `Disposals`.
- `FakeOwnedServer` launches `FakeOwnedProcess`es and answers the session probe and pins as an owned server with a session adapter. Switches make each failure happen: not ready, wrong PID, refused pins, exit on launch, refused connections, refused stop. Gates hold a connection or pin check open. `ConnectEntered`/`PinEntered` let a test inject a failure at exactly that stage, and `Events` records the lifecycle.
- `FakeClientDataDirectory` is a scope in which a simulated game client keeps its data in a given directory: `HostedWorld.DefaultSaveDirectory` returns it on every platform, so a hosted-world test places its fixture in a temporary folder while the macOS save-directory rule still runs. Only for no-game tests; a real Mac client always uses the signed-in user's directory. Nested scopes restore the outer one when disposed, innermost first; disposing an outer scope while an inner one is open throws.
- `FakeDataRoot` is a scope in which ValheimTesting's own folder on this machine (`%LOCALAPPDATA%\ValheimTesting` and its [platform equivalents](#this-machine-with-no-file)) is a given directory: the run journal that records every copy the process makes (`WorldFixture.Copy`, a run's runtime copies), the default host lock, leases and runs, and `CliBundle.DataRoot` move with it. A no-game test that copies a fixture opens one over its temporary folder in a `using` around the code under test (as [HostedScenarioTests](../../tests/Valheim.Testing.NativeAcceptance.Tests/HostedScenarioTests.cs) does), so its copies never show in the machine's `valheim-test env status`, and a test killed mid-run never leaves a run that makes `env preflight` refuse real runs. A copy keeps journalling where it was made, whichever flow retires it. Only for no-game tests. Nested scopes restore the outer one when disposed, innermost first; disposing an outer scope while an inner one is open, or a scope that is not in effect in the disposing flow, throws. `dotnet run scripts/validate.cs` fails when any of its commands creates, changes or removes anything in the real folder.
- `TempRuntime` is a runtime directory whose BepInEx log a test appends to or rewrites, as each boot does.
