# Platforms

*Assistant-written (Claude).*

The usual setup is one **Windows** PC with Valheim installed through Steam: unit tests, the integration tests and the native checks all run there, with an owned dedicated server and an owned client on the same machine ([one Windows PC](packages/Valheim.Testing.Game.md#on-one-windows-pc)). Everything below is for other hosts, and none of it is needed for that setup. The toolkit itself needs only the .NET 10 SDK on every host, plus PowerShell 7 on a Windows host ([host shells](#host-shells)), and CI runs bootstrap and validation on Windows, Linux and macOS.

| Host | Toolkit and tests | Game client (`GameLaunch.ForClient`, driven by ValheimCLI) | Dedicated server (native) | Server in a container | Remote server host |
|---|---|---|---|---|---|
| Windows | Yes; CI | Yes, `valheim.exe` | Yes, `valheim_server.exe` | Linux image; not tested on Windows | SSH game host in an environment inventory; a client starts in its desktop session, while a headless dedicated server starts from a disposable runtime copy without Steam or a desktop session |
| Linux | Yes; CI | Yes, `valheim.x86_64`; needs a display, a GPU and a signed-in Steam client the operator provides | Yes, `valheim_server.x86_64` | Yes, [docker/linux-server](../docker/linux-server/README.md); its smoke verified on a Linux x86-64 Docker host (server build 25527701) | SSH game host in an environment inventory; natively, a server-only run on a Linux VM over SSH |
| macOS | Yes; CI | Yes, `Valheim.app`, modded either way: native arm64 by default on Apple Silicon (requires a Doorstop with an arm64 slice and a BepInEx core on MonoMod 25), or x86_64 under Rosetta when explicitly selected; Intel Macs default to x64 ([native client](#native-apple-silicon-client)) | Yes, `valheim_server/Valheim` from Steam app 896660's macOS build, native arm64; modded needs a Doorstop with an arm64 slice and a natively running BepInEx core ([macOS](#macos)) | Experimental: x86-64 emulation on Apple Silicon | SSH game host in an environment inventory; a remote server profile passed natively, and remote client profiles require the SSH user at the unlocked console with Steam signed in (joined-client check passed over SSH to localhost; a separate runner machine is unverified) |

`GameLaunch.ForClient` builds a BepInEx game-client launch (Doorstop loader checks and variables, `-console`, `SteamAppId`) from a client install on its own OS, and `GameLaunch.ForServer` does the same for a dedicated server; each refuses the other's install and names the right one ([launching servers and clients](packages/Valheim.Testing.Game.md#launching-servers-and-clients)). A client needs an interactive desktop session with a display and a running Steam client, so `InteractiveClient` starts one inside a Windows, Linux or SSH Mac host's existing desktop session ([clients in a host's desktop session](packages/Valheim.Testing.GameSessions.md#clients-in-a-hosts-desktop-session)). A remote Mac's display may turn off if the computer stays awake and the console session remains unlocked; macOS Lock Screen settings determine whether that is possible.

## Host shells

Every script the toolkit runs on a host (this machine or one reached over SSH or in a container) runs in that OS's one shell: PowerShell 7 (`pwsh`) on Windows, `bash` on macOS and Linux. Windows PowerShell 5.1 is not used, and PowerShell is not used on macOS or Linux; an environment inventory's host names its `shell` accordingly and any other combination is refused. A Windows host needs `pwsh` on its PATH. Install it in a desktop terminal on that machine (over SSH the installer fails with access denied):

```
winget install --id Microsoft.PowerShell --source winget
```

Over SSH, restart the host's OpenSSH server (`Restart-Service sshd`) or the machine after installing, so new sessions see the new PATH. `valheim-test env preflight` and a session's host checks refuse a Windows host without `pwsh` and print that command (over SSH: from cmd.exe, the default login shell, in any language, or from an English Windows PowerShell login shell). The winget command installs the MSI package of a current PowerShell 7; 7.2 or later is needed, because the scheduled tasks the toolkit registers start the same `pwsh.exe` that registered them. A Microsoft Store install, whose executable lives in a packaged folder, is not tested. This page is the one place the requirement is written; other pages link here.

## Windows

A game client runs as `valheim.exe` and a dedicated server as `valheim_server.exe`, both from Steam installs (the server is the free Valheim Dedicated Server tool, app 896660). The owned client needs the Steam client running and signed in in the same desktop session; the dedicated server does not. Another Windows machine can host the server over SSH: a headless server starts from a disposable runtime copy without Steam or a desktop session ([a server-only plan on a remote host](packages/Valheim.Testing.GameSessions.md#a-server-only-plan-on-a-remote-host)).

Run `valheim-test` and the runners from an ordinary terminal (Windows Terminal, PowerShell or cmd), not from inside an MSIX-packaged app such as a desktop app that starts commands for you. Windows redirects such an app's AppData writes into its package, where the dedicated server's scheduled task and the game cannot see them, so `env preflight` and a run's host checks refuse a packaged process with that reason (#406).

## Linux and containers

Owned dedicated-server checks can run on Linux as well as Windows. `GameLaunch.DetectServer` reads a copied server runtime's platform from its executable (`valheim_server.exe` or `valheim_server.x86_64`) and `GameLaunch.ForServer` builds the direct launch that `DirectServerProcess` and `OwnedServerSession` own, including BepInEx's Doorstop variables on Linux. [docker/linux-server](../docker/linux-server/README.md) builds a local x86-64 image with the server, BepInEx and .NET 10, and the manual [Linux workflow](../.github/workflows/native-linux.yml) boots it once with [LinuxServerSmoke](../docker/linux-server/smoke/README.md). The [scheduled server checks](../docker/linux-server/README.md#scheduled-checks-in-ci) run that smoke and the [native acceptance suite](../tests/Valheim.Testing.NativeAcceptance/README.md#the-server-half-alone)'s server half every night and after each new public server build, and keep one tracking issue open while they fail. On Apple Silicon the image runs only under emulation and remains experimental.

Linux game clients run on a host whose desktop session (display, GPU, signed-in Steam client) the operator provides; the toolkit no longer ships a client container (#230). An [environment inventory and game hosts](packages/Valheim.Testing.GameSessions.md#game-hosts-and-the-environment-inventory) (local, SSH, container) run scripts, take a host lock, ship a revision, follow a log, fetch evidence and reach a loopback-only ValheimCLI through an SSH tunnel. `PinnedServerRun --inventory` runs a plan's dedicated server on an inventory host (Linux over SSH or in a container, or Windows), from any OS ([a server-only plan on a remote host](packages/Valheim.Testing.GameSessions.md#a-server-only-plan-on-a-remote-host)); a campaign (`PinnedServerRun.RunCampaignAsync`) places remote clients too, each started in its host's desktop session (`InteractiveClient`) on the Steam identity signed in there, leased so no two runs use it at once. A server-only run from macOS over SSH to a Linux VM has passed natively, and a Windows client was started in its desktop session over SSH during a crossplay run; provisioning the host and signing in its Steam client stays with the operator.

Server images contain Valheim's game files. Build them locally or in the CI job that uses them; never push, upload or publish an image, layer or server directory. The published Linux client base image contains no game files; do not publish it after installing the game.

## macOS

On macOS the dedicated server runs natively. Valheim Dedicated Server (Steam app 896660) has a macOS build: install it with anonymous SteamCMD (`steamcmd +force_install_dir <dir> +login anonymous +app_update 896660 validate +quit`; SteamCMD itself runs under Rosetta on Apple Silicon, the server does not). The install is not an app bundle: the server is `valheim_server/Valheim`, a universal (x86_64 and arm64) executable beside Unity's and Mono's libraries and its `Data` folder, and `steamapps/appmanifest_896660.acf` records its build id; check that the build ids match before comparing a Mac server with a client on another OS. `GameLaunch.DetectServer` returns `MacOS` for such a runtime, and on a Mac `GameLaunch.ForServer(…).ToStartInfo()` starts it through `/usr/bin/arch` as the machine's own architecture with Doorstop inserted. A macOS server runs only on a Mac, a Mac still runs neither the Windows nor the Linux server, and a `Valheim.app` client is refused as a server runtime.

Modded runs need BepInEx that runs natively on Apple Silicon: BepInExPack_Valheim's Doorstop and core are x86_64 only. Use an arm64 Doorstop and BepInEx core, as for the [native Mac client](#native-apple-silicon-client). The server depot has no local `steamclient.dylib`, and three earlier boots with Steam.app closed failed at `Steamworks.NET GameServer.Init()`. A profile run on 11 October 2026 opened the Steam server, loaded the pinned test mod, saved the fixture world and stopped cleanly while Steam.app was closed. It used seven pinned native files from a local SteamCMD installation. On this Mac the original Valve signatures were rejected by dyld, so the toolkit made arm64-only, locally signed **profile copies** and verified their resulting hashes; it did not change SteamCMD or the game install. This is a server-only result, not a joined-client or remote-Mac check.

For a profile campaign, run `valheim-test steam-runtime capture --steamcmd DIR --output steam-runtime.json`, then set the server role's `steamRuntimePackage` to that manifest. `valheim-test server-load` accepts the same manifest with `--steam-runtime-package FILE`. The package checks its SteamCMD build record, the full `@loader_path` dependency closure, arm64 slices and source SHA-256 hashes before staging. The run derives and verifies signed arm64 files inside its disposable profile, pins their staged hashes and records the source manifest in private evidence; it does not modify the installed game or bundle Valve files. Re-capture the manifest after updating SteamCMD. For an SSH Mac server campaign, keep the signed SteamCMD files on the Mac and make the manifest available to the runner; its `root` still names the Mac path. The campaign checks that remote source and stages the same disposable profile. A native Windows-station-to-Mac server-only profile campaign passed for [#504](https://github.com/tvongaza/ValheimTesting/issues/504), including interrupted-run recovery. The Linux image also builds on Apple Silicon with `--platform linux/amd64`, but only under emulation; see its [Apple Silicon notes](../docker/linux-server/README.md#apple-silicon-experimental).

### Native Apple Silicon client

The macOS game client is universal (`lipo -info <install>/valheim.app/Contents/MacOS/Valheim` lists `x86_64 arm64`), and a modded client can run either way. Rosetta is the compatibility path, not the only modded one:

| One-shot client architecture | Runs as | Install needs | Use it when |
|---|---|---|---|
| left out on Apple Silicon, or `"arm64"` | native arm64 | a `libdoorstop.dylib` with an **arm64 slice** at the install's root (UnityDoorstop 4.5 or later; a universal or an arm64-only build both have it) and a BepInEx core built on MonoMod 25 or later | Default on Apple Silicon, with mods that have no Intel-only native parts |
| `"x64"`, or left out on an Intel Mac | x86_64 (Rosetta on Apple Silicon) | BepInExPack_Valheim as installed: `doorstop_libs/libdoorstop_x64.dylib` and its core | Compatibility path for mods with Intel-only native parts |

The core matters as much as the loader. BepInExPack_Valheim's core uses legacy MonoMod (before 25), which cannot apply Harmony hooks on arm64, where a page is writable or executable but never both. A native core is BepInEx 5.4.23.5 rebuilt on HarmonyX 2.16.1 and MonoMod 25 ([source branch](https://github.com/bbauti/BepInEx/tree/codex/macos-arm64-valheim)); it is a community build, not an upstream BepInEx release. `GameLaunch.ForClient` checks both before anything starts: an arm64 plan whose game or Doorstop library has no arm64 slice, or whose `BepInEx/core/MonoMod.RuntimeDetour.dll` is missing or older than 25, is refused with the reason. `ClientRunPlan.Validate` runs the same check on an install on this machine, so a runner's `validate` refuses such a plan and `run` refuses it before it starts the server. It never falls back to Rosetta: the game starts through `/usr/bin/arch -arm64`, which fails rather than run another slice. Windows and Linux clients are x64 only, so `ClientRunPlan.Validate` refuses `arm64` for one, and a remote campaign client (Windows or Linux) refuses it too.

`valheim-test start` and `server-load` select arm64 by default for a local Apple Silicon client, and x64 for an Intel Mac. A custom inventory may set `"architecture": "x64"` for Rosetta, or pass `--client-architecture x64` to override one run. The selected slice is checked before copying; an install with only the stock x64 BepInEx stack is refused for an arm64 run and never silently falls back to Rosetta. Campaign plans and regression inputs that omit architecture inherit the inventory choice. A low-level hand-written `ClientRunPlan` and `GameLaunch.ForClient` also default to arm64 on Apple Silicon; select `"architecture": "x64"` (or pass `ClientArchitecture.X64`) explicitly to use Rosetta. A remote Mac inventory entry also defaults to arm64 when its CPU is unknown; set `"architecture": "x64"` explicitly for an Intel Mac.

A short recipe with the community installer [Relokk1/valheim-native-arm64](https://github.com/Relokk1/valheim-native-arm64), pinned to the commit checked here (read `install.sh` before running it; it downloads BepInExPack_Valheim 5.4.2333 from Thunderstore, replaces `BepInEx/core` with its rebuilt core, copies UnityDoorstop 4.5.0's universal `libdoorstop.dylib` to the install's root, sets `Type = GameObject` in `BepInEx.cfg`, removes the quarantine attribute and moves an existing `BepInEx` folder to `BepInEx.backup-<date>`). Use a test install and a disposable local character, never your own:

```sh
git clone https://github.com/Relokk1/valheim-native-arm64.git
cd valheim-native-arm64
git checkout cd5565a82dbff8332989c812cb141ad5638dbd52
./install.sh "<client install>"   # the folder that holds valheim.app
```

Then add ValheimCLI and your plugins to `BepInEx/plugins`, compute `installPins` with `InstallPins.Of("<client install>")`, and set the client section to launch natively:

```json
"client": {
  "mode": "owned",
  "install": "<client install>",
  "architecture": "arm64",
  "installPins": { "game": "...", "loader": "...", "patchers": "..." }
}
```

Do not start the game with the installer's `play.sh`; `ClientSession.Launch` starts it itself (the same `arch -arm64` launch with Doorstop inserted) and owns that process. The repository redistributes none of these binaries. `client-process.json` and the report's `clientArchitecture` record which slice ran; BepInEx's log reads `System platform: OSX Arm64` in a native process, and `vmmap <pid> | grep "Code Type"` shows `ARM64`.

Limits: the native arm64 path has run the native acceptance suite's synced-config scenario (join, confirmed save, server-only restart, rejoin, against a native macOS dedicated server) on one Apple M2 with macOS 26.5 and Valheim 1.0.16, with BepInEx 5.4.23.5 on MonoMod.RuntimeDetour 25.3.4 and exact pins ([#113](https://github.com/tvongaza/ValheimTesting/pull/113)); unit tests cover the plan field, slice and core selection and every refusal with synthetic installs; other chips, macOS versions and mods are unchecked. Arm64 plans against an install with the pack's MonoMod 22 core or without an arm64 Doorstop are refused before launch. Mods with native libraries built only for Intel, Windows or Linux will not load natively; asset bundles without Metal shaders render pink; unusual MonoMod IL hooks may behave differently on MonoMod 25; and some newer Macs were reported to need an arm64e Doorstop build. Test each mod natively before relying on it, and keep the x64 path for anything that fails.

Two Mac session limits apply to any owned Mac client, native or not. The client needs an awake Mac and an unlocked, logged-in desktop session; the display can turn off if that session stays unlocked. On a locked console the client can stall after the first scene and never reach its menu. And a bundle whose code seal is broken gets the "Valheim is damaged" dialog and is killed. A file added inside `Valheim.app` breaks the seal (BepInEx preloader logs a launch from `Contents/MacOS` leaves, a mod build's `publicized_assemblies`), which macOS tolerates for the install it already let run: the profile launches that install's own bundle, never a copy at a new path. Campaigns and the one-shot `valheim-test start` check the source bundle, read only, when they prepare its profile: `codesign --verify --deep --strict` refuses one with a changed or missing sealed file (verify the game's files in Steam to restore it; the run never repairs the source), files only added inside it are tolerated, and an intact bundle must also pass `spctl -a -t exec`.
