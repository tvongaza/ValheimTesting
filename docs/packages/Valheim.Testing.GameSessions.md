# Valheim.Testing.GameSessions

[Current preview API reference](https://tvongaza.github.io/ValheimTesting/). The package's README is this guide; use its versioned source commit from the package metadata when checking an older preview.

*Assistant-written (Claude).*

`Valheim.Testing.GameSessions` (net10.0) runs game sessions for mod tests: one or more real game processes in roles (a dedicated server, clients, a client that hosts its own world) on this machine or on others reached over SSH or a container, prepared, started, joined and torn down as one run. It is built on [`Valheim.Testing.Game`](Valheim.Testing.Game.md), which drives one game process; this package adds what a run of several processes, or a run on another machine, needs. Unofficial community tooling; not affiliated with or endorsed by Iron Gate or Coffee Stain. Valheim is a trademark of Iron Gate AB.

A test project that only observes or drives one game through `GameActor`, `OwnedServerSession`, `ClientSession` or `ClientRounds` needs `Valheim.Testing.Game` alone. Add this package for `TargetedRegression`, which now uses the shared hosted-runtime copy and recovery path, or when the test runs a session: a dedicated server with its clients, a hosted world with peers, a server-only load check, or any actor on another machine.

Topic pages: [pinned world dumps](../world-dump-contract.md) (`WorldDump`) and [evidence linked from `result.json`](../evidence.md) (review captures and clips).

## What it holds

- **The session:** `GameSession` (its server, clients by name, a hosting client, the scenario's `GameActor` handles, named barriers), the role actors `ServerActor`, `ClientActor` and `HostingClientActor`, and `ModDeclaration`. For xUnit, copy both the [GameSessionFixture adapter](../../examples/FullLifecycle/ExampleMod.Tests/GameSessionFixture.cs) and the native-test skip pattern in [ExampleSession](../../examples/FullLifecycle/ExampleMod.Tests/ExampleSession.cs). In that example, `Available=false` leaves `Session` unset when no private session manifest is present, so a plain `[Fact]` would fail offline; `SessionFactAttribute` skips that test. The [FullLifecycle guide](../../examples/FullLifecycle/README.md) shows the complete setup.
- **The pinned runner:** `PinnedServerRun` (`validate`, `run`, and `--inventory` for a server on another host) and `RunCampaignAsync` for a session manifest.
- **Hosts:** `IGameHost` with `LocalGameHost`, `SshGameHost` and `ContainerGameHost`, the host lock, CLI tunnels, installs, server and interactive-client starts on a host, macOS app-bundle checks.
- **Where actors run:** `EnvironmentRuns` places a session's actors on an `EnvironmentInventory` (the inventory itself, the description of the machines, is `Valheim.Testing.Game`'s) and reports, recovers and tears down what earlier runs left on its hosts (`valheim-test env status|recover|teardown`).
- **Steam accounts:** `SteamAccountHold` and its lease, so two clients never run on one account.
- **Evidence from a host:** `WorldDump`, `ReviewCapture` and `ReviewClip` fetch what the game wrote on its machine into the run's evidence.

From 0.1.0-preview.3 its types are in the `Valheim.Testing.GameSessions` namespace (`using Valheim.Testing.GameSessions;` beside `using Valheim.Testing.Game;`); through 0.1.0-preview.2 they kept the `Valheim.Testing.Game` namespace.

## Game sessions

`ServerActor` is the one place a run wires an owned server from its plan: each boot gets the plan's environment with the session token, its kept logs (`boot-N`), a `boot-N.process.json` record and recorded commands (`connection-N.jsonl`) in the output, the plan's startup events and quit time, strict pins, and test access on every boot. `ServerActor.OnThisMachine(plan, runtime, world, output, capability, tokenVariable)` runs it from disposable copies on this machine; `PinnedServerRun` places it on a host of the environment as well, and hands it to the scenario as `session.Server`. `actor.Game` is the current boot's `GameActor`.

`GameSession` is one run's game processes in their roles: `session.Server` (a `ServerActor`) or `session.Host` (a `HostingClientActor`, a client that hosts its own world: [hosted worlds](#a-hosting-client-in-a-session)), and `session.Clients["name"]` (`ClientActor`s), each with its in-game handle `.Game`. A scenario is `(GameSession session, TPlan plan) => Task` and coordinates the actors only through barriers, each a named Setup step with a bounded wait that names itself on timeout: `StartAsync()` boots the server and brings every client to its menu at the same time (one failure cancels the others, lets them settle, tears down and is rethrown); `ServerJoinable()`; `Join(client)` and `JoinAll()` (the one join, `SessionControl.JoinWorld`, optionally with an arrival point); `Rejoin(client)`; and `Barrier(name, wait, within)` for a scenario's own readiness. Disposing the session closes the clients in reverse order, then stops the server, each a Cleanup step. `PinnedServerRun` builds the session from the plan and calls the scenario with it; until the scenarios declare their clients (#258 step 6), `session.OpenClient(clientPlan, name?, directory?)` opens one through a new `ClientActor`.

### An owned client on this machine runs with a disposable loader profile

Set `"copyGame": true` on an owned `ClientRunPlan` when a profile cannot launch from its source install, such as a Windows source and profile on different volumes. This makes a full disposable game copy while keeping the source unchanged. Attached and in-place clients refuse `copyGame`.

An owned client opened locally outside a prepared hosted campaign (`session.OpenClient` or `ClientActor.OnThisMachine`) now stages a disposable loader profile by default. On macOS and Linux the installed game's executable runs with Doorstop pointed at the profile; on Windows an owned launch folder hard-links the game's files and contains its own Doorstop proxy beside the linked executable. The source install is checked before and after profile staging and never receives test plugins or a replacement proxy. A mod manager's unrelated root DLL proxy is excluded from the Windows launch folder. The selected ValheimCLI set replaces any installed set in the profile, and the plan is bound to the source game's code pin plus the profile's loader, patchers and plugin pins. `clientLaunchMode` and `clientInstall` in provenance show what ran. The owned folder is journalled before staging, retired once every client launched from it is proven stopped, and recoverable through `valheim-test env recover` after interruption. A client that leaves and rejoins between rounds reuses that same prepared profile. `inPlace` still launches the operator's existing install without staging. Prepared hosted campaigns also stage profiles for actors on this machine. They pin the game and loader roots separately on macOS and Linux, while Windows uses the owned launch folder; remote Windows and Linux actors use the same owned profiles, including SSH and container hosts. Remote macOS client and server actors remain unsupported pending [#613](https://github.com/tvongaza/ValheimTesting/issues/613). A campaign retires only its owned profile, never the source install. The runner’s `CopyGame` option, or `HostedCampaignPreparation.PrepareAsync(..., copyGame: true)` for a direct caller, requests full copies.

`--in-place` (before the mode) or `"inPlace": true` in a client plan, one name for both, runs the install as it is and writes nothing into it: no ValheimCLI set is staged and no loader is swapped. The install must already hold BepInEx and ValheimCLI; preflight refuses one that does not, naming what is missing. The static check runs only when the plan names a `cliManifest`; otherwise `cliPreflight` in the report says `live only: static check not run: your install, run in place`. A run still refuses to start while Valheim runs on this machine, and journals, leases and local-only test characters work as for a profile. `ClientSession.Launch` refuses an owned plan that is neither bound to a prepared runtime nor in place.

### A hosting client in a session

`HostingClientActor` is the hosting client as an actor (#258 step 8): one process with both capabilities, the session's `IOwnedServer` in place of a dedicated server. `GameSession.StartAsync` prepares it before any actor starts (`Prepare`: the plan's preflight, the save directory, the placed fixture, each its own step as for [hosted worlds](Valheim.Testing.Game.md#hosted-listen-server-worlds)), opens it to its menu, requires the session commands, checks the mod's Harmony patches on it when its pins load the mod ("host: the mod's Harmony patches are applied"), and hosts the world ("host the fixture world with the disposable character, protected"; then "establish test access on the owned host"). Its members: `Game` (server and client at once), `WaitUntilJoinable` (in its world with its player, and an open server by `cli_multiplayer_identity`), `Restart` (leave, which saves, re-pin at the menu, host again, test access; peers are disconnected), `LiveLog` (an owned host's BepInEx log on this machine), `World` (the placed `HostedWorld`). A session has a dedicated server or a host, not both.

A host's peer is a client plan with `"joinsHost": true` and no `join`, `passwordVariable`, `crossplay` or `hostWorld`. `session.Join(name)` waits until the host's world accepts connections, then joins it with `SessionControl.JoinHost(plan, host, worldUid)`: a listen server on Steam is reached through Steam, not an address, so it reads the host's Steam ID from `cli_multiplayer_identity` (read-only; it must be an open server on the Steamworks backend with a signed-in Steam user's 17-digit ID) and sends `cli_connect_steam_user <steamId>` once after `cli_select_character`, then waits as a crossplay join does, verifies the world pins and protects the player. A crossplay (PlayFab) host's peer join is refused: not supported yet. Disposing the session closes the peers first; then, when the run so far passed, the host leaves its world ("the host leaves its world to its menu"); an owned host is stopped, an operator's detached; then the world moves into the evidence only once no client can still host it (it left, or its owned process stopped), otherwise it is named in `hostWorldLeftInPlace`.

`PinnedServerRun.MainAsync(args, HostedRunOptions<TPlan>)` is the hosted run's lifecycle: `<runner> [--in-place] validate-host|host <plan.json> <new-output-directory>`. The options name the plan reader, the plan's hosting client section (`Host`), the mod's declaration, its log classifications and the scenario `(GameSession, TPlan) => Task`. `validate-host` runs only the plan's preflight; `host` hosts on this machine, runs the scenario, disposes the session, scans the host's logs and writes `result.json` and `junit.xml`. `FakeGameSession.Hosted(report, output, hostPlan, openClient, peers)` is the same session over scripted clients. The [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md)'s `hosted` scenario runs on it.

Limits: a hosted world has no password and is never public, because the start command would carry a password as text. A peer joins a host only within a session that declares it; the runner's hosted modes place the host on this machine and no peers, and a host with peers on other machines is a campaign without a dedicated server ([below](#a-campaign-remote-clients-and-steam-identities)). The Steam peer join (`cli_connect_steam_user`) is tested with fakes only. The macOS 1.0.16 native check covered a local hosted fixture, exact UID, protected player and owned-client teardown; broad host-mode behavior is still exercised through scripted transports.

## Pinned server runner

`PinnedServerRun.MainAsync` is the lifecycle of a mod's owned dedicated-server test runner, so the mod's `Program.cs` supplies only its plan fields and its scenario, `(GameSession session, TPlan plan) => Task`. Usage is `<runner> [--in-place] [--inventory <environments.json>] validate|run <plan.json> <new-output-directory>` (`--in-place`: [owned clients run their install as it is](#an-owned-client-on-this-machine-runs-with-a-disposable-loader-profile)); with `--inventory` the server runs on an inventory host ([a server-only plan on a remote host](#a-server-only-plan-on-a-remote-host)); `PinnedServerRun.RunCampaignAsync` runs a plan on a campaign's actors ([a campaign](#a-campaign-remote-clients-and-steam-identities)). A plan derives from `ServerRunPlan`, which is read strictly (unknown fields refused), and `ValidateServerPlan` applies the rules every pinned plan follows:
- pinned sources, and port and time bounds;
- a known executable;
- no runner-owned token or Doorstop variable in the environment;
- `-batchmode -nographics` and exactly one `-savedir {world}`;
- strict pins, with `worlduid` and an exact MD5 for every plugin;
- `runtimePins`: the runtime's game build, loader and patchers (see [Pins and the opt-out](Valheim.Testing.Game.md#pins-and-the-opt-out)).

The plan may also list `logScan` (per-run severities, named expected lines and the run's own patterns for the [log scan](Valheim.Testing.Game.md#log-scan-at-teardown), each with a reason).

For a runner with an owned joined client, set `PinnedServerRunOptions.ClientPlans` to return that plan's client sections (for one optional client: `ClientPlans = plan => plan.Client is null ? [] : [plan.Client]`). The runner checks each `passwordVariable` before creating evidence, copying either game, or starting the server. Set the named variable in the runner process (for example, `VT_JOIN_PASSWORD`); do not put its value in `client.environment`, which is serialized plan data. Local clients inherit the runner's variable; remote clients receive it through the host's secret-variable channel. An attached client keeps its operator's environment. Campaigns use their declared clients for this check automatically.

The runner then:
1. refuses an existing output directory, and checks the host before copying. It also refuses, before copying, when the output's drive lacks room for the runtime and world copies plus headroom (2 GB, or a tenth of the copies when that is larger; `freeBytesBeforeCopies` records what it saw). A full drive part-way through a copy would leave a broken runtime behind;
2. copies and verifies the runtime and world, recording plan, runner and toolkit hashes, mode, platform and input hashes, refuses a copy whose game build, loader or patchers differ from `runtimePins` (a patchers difference names what `BepInEx/patchers` holds) (the values found are recorded as `runtimeGameSha256`, `runtimeLoaderSha256` and `runtimePatchersSha256`);
3. stops there for `validate`;
4. otherwise checks the CLI port and starts the owned session on the copies, with per-boot logs, recorded commands and `DedicatedStartupEvents`, with test access established on the server on that boot and on every restart (`OwnedServerSession.EnsureTestAccess`, which the runner sets for every owned server, a load smoke's included: `TestAccess.Ensure` sends devcommands, then `confirmcheats`, each verified through ValheimCLI's `cli_access`; a new server process has neither gate) and runs the scenario;
5. always disposes the session (clients the scenario left open, then only the owned server), scans the session's logs (`session.Logs`: every boot's and client's, plus any `session.AddLog`; a `scan run logs` step, see [log scan at teardown](Valheim.Testing.Game.md#log-scan-at-teardown)), writes `result.json` and `junit.xml` (see phases below), and prints PASS (only for `run`), VALIDATED or FAIL. It exits 0 when every step passed, 1 on a failure and 2 on bad usage. A run whose only failures are host operations with an unknown outcome (a lost reply, a transport failure, an unproven lock; see [game hosts](#game-hosts-and-the-environment-inventory)) prints UNKNOWN, records `outcome` in the provenance and exits 3: neither a pass nor a failure.

**Phases and the four reported states.** Every step is recorded in one of four phases (`StepPhase`): `Preflight`, checks before anything is copied (the free-disk check, a client's install and save-directory preflight); `Setup`, copying, launching, joining, test access, arrival and the transitions between client rounds (save, leave, restart), until the runtime is ready (`validate` runs the copying Setup steps and launches nothing); `Scenario`, the mod's own steps, the default for `Step(name, action)`; and `Cleanup`, stopping, releasing, removing the runtime copy and the log scan (which reads what the mod logged, but runs after the processes stop). A failure outside any step is recorded in the phase of the last recorded step. `result.json` (schema 3) gives each step's `Phase` and four states derived from them: `PreflightPassed`, `RuntimeReady` (preflight and every Setup step passed), `ScenarioPassed` (the runtime was ready, and at least one Scenario step ran and every one passed) and `CleanupVerified` (at least one Cleanup step, and every one passed). `junit.xml` has one `testsuite` per phase, named `<report> / <phase>`. `Passed` and the exit code are unchanged: every step must pass, so a run whose scenario passed and whose cleanup failed prints FAIL and exits 1, and `ScenarioPassed: true, CleanupVerified: false` says which. Removing the runtime copy is a Cleanup step: a copy that could not be removed fails the run. A mod's runner tags its own steps with `report.Step(StepPhase.Setup, ...)` or `round.Step(StepPhase.Setup, ...)`; evidence attached inside a step records that step's phase.

**What ran.** Every `result.json` names the toolkit that ran in `Toolkit` (`ToolkitProvenance`, schema 3), read when the result is written: each toolkit package in the run's process (the Game package, the packages it references, and any other loaded: `Valheim.Testing`, `Valheim.Testing.GameSessions`, `Valheim.Testing.Bindings`, the `valheim-test` tool) and the ValheimCLI transport (`Valheim.Testing.Cli`), each with its version, the source commit its build recorded, its SHA-256 and its state. A `Valheim.Testing*` package is `released` when the release workflow built it (`release.yml` packs with `-p:ValheimTestingRelease=true`, which `src/Directory.Build.props` turns into assembly metadata), a `candidate` when its version carries `-candidate` (a local build identity, never published), and `unreleased` otherwise (a source build of any version). The transport is a `candidate` (its version names the valheimCLI commit) or `released` (a version the release refuses unless NuGet.org serves it; that package's nuspec names its commit, `releasedCliCommit` for the released one). `Runner` and `RunnerSha256` name the entry assembly; when the provenance cannot be read, `Error` says why and the result is still written. `Plugins` holds, per actor (`server`, each client by name, the hosting client), the plugin pins its game confirmed with `cli_expect` when it started: plugin GUID to MD5, or `absent`. An unpinned actor has none.

Hosted copies retain the source install's `BepInEx/config/BepInEx.cfg` when no reviewed loader package or explicit config replaces it. If a reviewed loader package has no `BepInEx.cfg`, the source file stays; if it has one, the package file wins. An explicitly selected config wins over both. The staged runtime checks the file against the selected source or package hash, so an arm64 Mac entrypoint setting does not silently revert to BepInEx defaults.

**What the output keeps.** The evidence stays: `result.json`, `junit.xml`, the plan and input hashes, each boot's logs and recorded commands, and the world copy, which is the run's actual save. The runtime copy goes once its server has stopped, on a pass, a failure or `validate`. Apart from what the run wrote, it is the pinned runtime's own files, which the input hashes already record, and it is about 2 GB per run. Before it is removed, every file the run added or changed in it (BepInEx's log, configs, a mod's cache, Steam's logs) is kept in `runtime-changes/` under its relative path. `runtime-changes/changes.json` lists the added, changed and missing files. A file over 64 MB, or past 256 MB kept in all, is listed there with its size and SHA-256 instead (`WorldFixture.Retire`). `runtimeCopy` in the report says what was removed and kept, and `outputBytes` gives the output's final size, which the runner also prints. The copy stays when its server did not stop cleanly, because a process may still use it: the report names it, with its size, to delete by hand. To keep the whole copy for hands-on debugging, set `VALHEIM_TESTING_KEEP_RUNTIME=1` for any runner; in a campaign it keeps every actor's prepared install (the disposable characters still go). One owner retires what a run leaves, after every process it started has stopped: the clients' disposable characters, then each runtime copy, each recorded as its own Cleanup step, under the host locks the run already holds. A campaign has one run id (`runId` in the report) for its prepared installs (`<runtime>/vt-prep-<runId>-<actor>`), its server run's directory and its journal: on each host, beside the host's lock, `journal/<runId>/<actor>.jsonl` gets one line before each copy or disposable character is made, another once it is made, and one when it is retired or kept, and the run's end is the last line (`state`, `cleanupVerified`). Each server boot and each remote client is journalled before it starts (`process-intended`, with its boot or launch directory, where its pid file goes, and the SHA-256 of the command line it will have) and after (`process-started`, with its pid and start identity), and each host lock once held and released; a client's Steam account lease is journalled on the lease host, as held, released or kept (while its client may still run). A standalone `--inventory` run journals the same on its server host under its own run id, for its runtime copy (`<runtime>/<runId>/runtime`) and the world copy it ships (`<runtime>/<runId>/world`) too: `copy-intended` before the copy or ship script runs, `copy-done` once verified, then `copy-retired` (the runtime copy, once removed; the world copy, handed over as the run's evidence) or `copy-kept`. A copy whose reply was lost, or a ship that failed partway, is still the run's: its teardown removes it, and when that fails too, the copy stays open in the journal for `env recover`. A campaign's server run journals its world copy the same way. An entry the host cannot write stops the run before that copy, character or process, so an interrupted run leaves a record of every path and process it may own. A run with its server on another host does the same there, still under the host's lock. A dedicated server's runtime copy, on a host or prepared by a campaign, leaves out the install's top-level `logs` folder, where Steam writes the server's own runtime output (`connection_log_*.txt`, `stats_log.txt`), some of it from other days; the install keeps it, and a pinned manifest that lists it is checked without it. It lists the host copy again, compares it with the listing made after copying, and has the host keep the changed files in `<run>/runtime-changes` within the same limits. It fetches that folder to `runtime-changes/` here, and removes only `<run>/runtime`. The run's world and boot logs stay in its host directory, and both are fetched too.

`server-load` uses the campaign's prepared runtime on every supported platform. The campaign owns its single verified server copy, records the files it stages there, and retires that copy after the server stops. A local macOS dedicated server uses this same path; its world is temporarily placed in the user's default `worlds_local` under the host lock and collected into the run's evidence after the server stops.

**Copies left behind.** Every copy `WorldFixture` makes on this machine is journalled there before it is made, in ValheimTesting's own folder (`journal/<runId>/fixture.jsonl`, beside this machine's default lock). Its removal or retire is journalled too, and so is a copy kept for a reason (kept on request, or one a server may still use). A run with its own run id (a campaign, which is how `server-load` runs on every supported platform, or a hosted run) journals its copies under that id, so one run is one journal run; other copies share one run id per process. A preserved copy without a reason, such as a run's world, is handed over to the output it is in. So `valheim-test env status` lists a killed process's copies as that run's, and `env recover --run ID` removes them. Before removing a copy it keeps what changed in `<copy>-changes`, and a world copy, a run's save, is handed over rather than removed. A copy is recognised only by what the toolkit writes: a `valheim-test-` directory with 32 hex digits holding `fixture-provenance.json`. The data folder must be writable: a copy that cannot be journalled is not made, and the error names the folder.

Copies made before runs journalled them are named by no journal. `env status` lists them as `UNJOURNALLED` when they are under this machine's ValheimTesting folder or under the runtime of one of its environments. Each entry has its kind (server runtime, client runtime, world or other), its size, when it was made and which running processes use it (`OwnedCopies.Find(root)` reads the same for any folder). `valheim-test env teardown --copy PATH` (`EnvironmentRuns.TeardownCopyAsync`, or `OwnedCopies.Remove(path, allowWorld)`) removes exactly the copy named. It refuses:
- a path that is not such a copy;
- a copy a running process uses, or one a live process on this machine journalled and still holds (or an older owner record says it does);
- a copy an open run's journal still names (not yet retired, kept or handed over), which belongs to `env recover|teardown --run`. A copy a run handed over to its output, such as its world save, can be removed by name.

Before removing a copy, it keeps what that copy's run changed in it in `<copy>-changes` beside it, with the larger limits when the run did not pass. There is no sweep, and nothing is removed because of its age.

**What runs left, from their journals.** Each journal line also names its runner: the machine, process ID and start time of the `valheim-test` process that wrote it. `process-started` also carries the SHA-256 of the process's command line, read on its host right after the start (Windows `Win32_Process.CommandLine` as UTF-8, Linux `/proc/<pid>/cmdline`, once the recorder's `env` has executed the game). `valheim-test env status [--inventory FILE] [--json]` (`EnvironmentRuns.WriteRunStatusAsync`) reads the journal of every host in the inventory (this machine with no file; only the hosts are needed, not an install) and changes nothing. For each run, it takes every copy, disposable character, process, Steam lease and host lock the run journalled and never journalled as retired or released, and checks each one on its host. A process still counts only when its ID, start time and command line all match the journal; an exited process or a reused ID is gone. A launch journalled as intended but never as started (a run killed in between) is judged by its pid file, which the launcher writes as the game starts (its ID and start identity: on Windows the start time as a file time, on Linux the start in clock ticks; a pid file from before this version holds a Linux process's ID only): when no process has that ID and start identity, the launch is gone, and an ID another process now holds is never that launch's and is never stopped. When the named process runs the command line the launch journalled, it is adopted as the run's process: `env status` names it (`process <pid> (started <identity>)`, "adopted from its pid file") and `env recover` stops it by identity like any other. A lock counts only while its journalled claimant still holds it. Each run that has not ended, or that left something, is printed with what it left, under one of these states:
- `LIVE`: its runner still runs on this machine, or on a Windows host of the journal that is its runner's machine (asked through that host by process ID and start time, for example the station PC's runs read from a Mac);
- `UNKNOWN`: it never journalled its end, and its runner was not journalled, or ran on another machine that is not a Windows host of the journal, or on one that could not be asked;
- `UNRECOVERABLE`: something it left cannot be proven its own or gone. Examples are a process whose ID and start time match but whose command line differs or cannot be read; a launch interrupted before its process was journalled whose pid file is missing or unreadable, names a running process without a start identity (a Linux launch from before this version), names one running another command line, or belongs to a launch journalled before launches journalled their command line; or a host that cannot tell;
- `RECOVERABLE`: it left things that are provably its own;
- `KEPT`: it ended and kept copies or leases on purpose (`VALHEIM_TESTING_KEEP_RUNTIME`, or a server that may still run).

Runs that ended and left nothing are only counted. A host whose journal cannot be read is printed as `UNREADABLE`, and none of its runs is reported as over. A journal line that cannot be read (cut short by a full disk or a killed write) is skipped, counted and named; the host is then not clean. The exit code is 0 when every host was read and every run left nothing, and 3 otherwise.

`valheim-test env recover --run ID [--inventory FILE] [--json]` (`EnvironmentRuns.RecoverRunAsync`) clears what that one run left, exactly as `env status` judged it; `env status` is its dry run. It refuses before anything changes when the run is `LIVE`, `UNKNOWN` or `UNRECOVERABLE`. Otherwise it works in phases across every host:
- each process the run started is stopped only if its ID, start time and command line still all match the journal, checked again right before the stops (by start time, so a reused ID is never touched);
- on each host where no process of the run was left, under the host's lock (the run's own when it still holds it, otherwise taken for the recovery, which an active run's lock refuses), and once no conflicting game runs there, its disposable characters are retired and its prepared copies removed, and so are a standalone hosted run's own runtime copy and a world ship that never finished (a world copy that was verified is the run's save, handed over where it is). Before a runtime copy goes, the game's own logs in it are kept in the run's evidence folder on that host, `<runs>/<run>/recovered-<actor>` beside its `boot-N` and client launch folders: BepInEx's `BepInEx/LogOutput.log`, Unity's `toolkit-unity.log` (a server's `-logFile`) and BepInEx's `preloader_*.log`, and for a client the host user's `Player.log`. Only a log written since the copy was made (its journalled start) is the run's; an older one came with the install and is named, not kept. A client started on that host after the interrupted run would make `Player.log` its own, which is one more reason to recover before the next run (`env preflight` refuses until then). The output names the folder, each log kept and each one left out. A copy whose logs could not be kept is not removed, and the step says so;
- its Steam leases are released by their own lease ids, but only when no process of the run was left on any host and every host's journal was read, so a client still signed in to the account keeps its lease. Lease ids are journalled since this version; an older lease is checked in the inventory's lease directory, is gone once its owner no longer holds it, and otherwise stays `UNRECOVERABLE` (a lease never lapses; see the escape hatch below);
- each host lock is released by its own claimant, but only once nothing of the run is left on that host.

A step that fails keeps everything that depends on it, and the rest waits for the next `env recover`. Each effect is journalled under the actor `recovery`, after it happens, and each host gets a `run-recovered` line. `env status` then shows the run as ended, or names what is still left. Copies and leases a run kept on purpose (`KEPT`) stay; `valheim-test env teardown --run ID` does the same as `recover` and removes those too, including a lease kept because its client might still run, once that client is proven stopped. Nothing is ever removed because of its age, and a Steam lease never lapses on a timer. The exit code is 0 when nothing of the run is left and 3 otherwise.

`valheim-test env teardown --run ID --machine-gone [--inventory FILE]` (`EnvironmentRuns.ReleaseLeasesOfGoneRunAsync`) is the escape hatch for a run whose machine is gone for good, so `env recover` can never prove its clients stopped, and for a claim whose reply was lost (no journal names it, and no client started on it). The flag is the maintainer's confirmation that no client of that run can still run; a client that still does is not told. On the inventory's lease host it releases every unreleased lease in the lease directory that names the run (in the claim's run line, or in an older claim's owner `<runner> <run> client <name>`) and journals each release there as `lease-released` with `machineGone=true` under the actor `recovery`. When it released a lease of a run whose end no readable journal holds, it journals that run's end there too (`abandoned: its machine is gone`), so `env status` and preflight stop waiting for it; it touches nothing else of the run. It refuses a run that is `LIVE`, a lease host whose journal cannot be read, and a `RECOVERABLE` or `KEPT` run when every host was read (then `env teardown --run ID` settles it the ordinary way). It needs no new configuration.

`session.OpenClient(plan.Client)` opens the plan's client through a `ClientActor`, the one client open path, whose logs (a failed startup's included) the teardown scan reads: on this machine (`ClientActor.OnThisMachine`, launched or attached as the plan's mode says), or, in a campaign, an owned client started in its assigned host's desktop session (below). Each call is one open; a client the scenario left open is closed at teardown, before the server stops. A runner that opens a client itself uses `ClientActor.OnThisMachine(name, plan, output)`: `Start()` opens it once, `Game` is its `GameActor`, `Logs` are the logs to scan, and disposing the actor closes it.

A clean test runtime is BepInEx core plus your plugins, with an empty `patchers` folder. Preloader patchers rewrite game assemblies before any plugin loads, so one a removed mod left behind breaks the whole run with a `TypeLoadException` on a game type. The `patchers` pin hashes everything the folder holds, so a leftover patcher is refused before launch, naming the folder's entries; pin a patcher only when the run needs it (for example a hook generator a dependency requires). Plans do not name patchers; a plan that does is refused with that instruction. An explicitly unpinned run checks no patchers, like the rest of its install.

Ctrl+C and SIGTERM cancel the run. Its cleanup (stopping what it started, retiring its copies and characters, releasing its leases and locks) then runs on a token of its own, never the cancelled one, and is bounded by 5 minutes (`RunCancellation.CleanupBudget`). A second Ctrl+C while cleanup runs is the escape from a cleanup that hangs: it stops waiting, and the remaining cleanup steps are recorded as not attempted. The run's journal gets `cleanup-abandoned` with the reason in place of its end, the runner prints `ABANDONED cleanup` with the command, and it exits 3. `valheim-test env status` then lists the run as recoverable, and `env recover --run ID` finishes the cleanup. The escape never kills anything itself. Options declare the mod (`Mod`, a `ModDeclaration`: its session capability and token variable and, optionally, its Harmony census capability, owner and declared patches, which the session checks on the server at runtime-ready as the Setup step "server: the mod's Harmony patches are applied" whenever the server's pins load the mod), apply the mod's own rules to the plan as it will run, for validate and run alike (`CheckPlan`, a campaign's plan once bound), and add provenance.

## Game hosts and the environment inventory

### Several machines

A mod author often edits on one machine and runs the game on another: a Windows gaming PC, a Linux box, a container, a rented VM. A macOS server runs only locally so far; a remote macOS server host is not supported yet. A private **environment inventory** lists your machines (hosts) and, in preference order, the game installs on them (environments) a run may use; an `IGameHost` does the work on that machine. A standalone run places its dedicated server from it (`--inventory`); a campaign assigns each of its declared actors (a server and named clients) an environment from it. The inventory holds no credentials and no Steam IDs: a client's identity is the one signed in on its host.

```json
{
  "hosts": {
    "linux-box":  { "kind": "ssh", "platform": "linux", "shell": "bash", "destination": "tester@linux-box.example",
                    "sshOptions": ["IdentityFile=~/.ssh/valheim_tests"], "lock": "/var/tmp/valheim-testing/lock" },
    "gaming-pc":  { "kind": "ssh", "platform": "windows", "shell": "powershell", "destination": "tester@gaming-pc.example",
                    "lock": "C:\\ValheimTesting\\lock" },
    "server-ctr": { "kind": "container", "platform": "linux", "shell": "bash", "container": "valheim-server", "user": "valheim",
                    "lock": "/home/valheim/lock" }
  },
  "environments": [
    { "name": "box-server", "host": "linux-box", "roles": ["server"], "install": "/opt/valheim/server",
      "runtime": "/srv/valheim-testing/runs", "cliPort": 5577, "gamePort": 2466 },
    { "name": "pc-client", "host": "gaming-pc", "roles": ["client"], "install": "C:\\Games\\Valheim",
      "runtime": "C:\\ValheimTesting\\runs", "cliPort": 5578 }
  ],
  "leaseHost": "linux-box",
  "leaseDirectory": "/var/tmp/valheim-testing/leases"
}
```

`EnvironmentInventory.Read(path)` refuses unknown fields (a credential or Steam field among them, without repeating its value) and validates everything at once before anything starts: known kinds, platforms and shells (`powershell` is Windows PowerShell 5.1, Windows only; `pwsh` anywhere; no `bash` on Windows), ssh destinations and options as `SshGameHost` accepts them (no password, the port given once), absolute paths in the host's own style, a runtime directory outside the install, no remote macOS server yet (local runs are supported), an environment's `roles` either `["server"]` or `["client"]`, a `gamePort` only on a server environment, and a listed `leaseHost` and absolute `leaseDirectory` when any client environment exists (left out, this machine's when every client is on it). Assigning actors then refuses one game client per host twice, a ValheimCLI port used twice on one host and two actors reached on the same port of this machine (a local host's or container's CLI port, an SSH environment's `localCliPort`). A `local` host must describe this machine's platform. An inventory describes one person's machines, so keep it beside the mod's tests, not in them. SSH uses keys or an agent only (BatchMode is always on, a password is never accepted), and the host key must already be known. Each `sshOptions` entry is `Name=value`, and the value is taken literally: ssh reads a `-o` value like a line of its config file, so a value with spaces, quotes or a leading `#` (`User=Some Name`, `IdentityFile=C:\Users\Some Name\.ssh\key`) is passed as `Name="value"`, with `"` and any backslash ssh would read as an escape escaped; other values are passed unchanged. An empty value or one with a control character (a tab, a line break) is refused. A value that needs an escape (a `"`, `\\` as in a UNC path, or a trailing backslash) needs OpenSSH 8.7 or later, which reads escapes; other quoted values, such as a Windows path with spaces, read the same in older versions.

| Operation | `IGameHost` | Contract |
|---|---|---|
| Run a script | `RunAsync(script, variables, timeout)` | bash or PowerShell. The script travels on standard input, never on a command line, and each variable arrives as a quoted literal no shell interprets. A small wrapper on the host reports the script's own exit code, so a Windows login shell that turns every failure into 1 still returns the real code. |
| Take the host lock | `AcquireLockAsync(lockPath, owner, timeout)` | The exclusive creation of an owner file in the lock directory; exactly one run wins. Each acquisition claims as the given owner plus a unique id (`HostLock.Owner`), so two runs that pass the same owner never both hold the lock and only the holding handle releases it. Another claimant's lock throws `HostLockException` with its holder, at once: nothing waits or retries. An unproven claim names the claimant it tried, to check with before deciding what to do. Disposing the `HostLock` releases it and throws if the release cannot be proven. A lock left by a crashed run stays until a person removes it. |
| Ship a revision or files | `ShipRevisionAsync(repository, revision, dir, timeout)`, `ShipFilesAsync(localDir, dir, timeout)` | `git archive` of a commit (tracked files only, never the working tree) or a local directory, as a tar checked by SHA-256 on the host and extracted into a new directory; `SOURCE.txt` there records the commit, tree and hash. |
| Follow a log | `LogOffsetAsync(log, timeout)`, then `WaitForLogAsync(log, offset, success, failures, timeout)` | Event driven on the host (`tail -F`, or a file watcher under PowerShell); lines are matched here with .NET regular expressions, failure patterns first. Take the offset before the action whose line you await. The log may not exist yet. A log the game recreates at each boot is best given a fresh path (the run's own runtime copy) and offset 0. Expiry returns `TimedOut`; `EnsureMatched()` throws the same `WaitFailedException` and `WaitTimeoutException` as `LogWait`. |
| Fetch evidence | `FetchDirectoryAsync(dir, localDir, timeout)` | A tar of the host directory, hash and size checked on both ends, extracted into a new local directory; entries that would land outside it are refused. |
| Reach ValheimCLI | `OpenCliTunnelAsync(cliPort, readyTimeout, localPort = 0)` | See below. |

A host result is `Exited` with the script's code, `TransportFailed` (ssh exit 255, a Docker error or a missing executable, without the host's report), or `Unknown`. A deadline always gives `Unknown` with `TimedOut` set: the script may not have run, may have finished or may still be running. `Succeeded` and `Failed` are both false for it, and a lock claim that timed out is `HostLockState.Unknown`, neither yours nor free. Nothing is retried, because a mutation must never be repeated blindly; check with a read-only script before deciding what to do.

A `pwsh` wrapper on a local or container host starts with `DOTNET_MultiCoreJitMinNumCpus=FFFF` (#133). PowerShell 7 records the methods it compiles at startup in one profile file per user (`StartupProfileData-NonInteractive` in its cache directory) and reads it on the next start. `pwsh` processes starting at the same time corrupt that file, and a later start that reads it can fail before the script runs: an invalid assembly or culture name, a stack overflow or a segmentation fault ([PowerShell#26528](https://github.com/PowerShell/PowerShell/issues/26528)). On GitHub's runners, pwsh 7.6.6 on .NET 10 failed 11 of 3000 parallel starts on macOS and 1 of 3000 on Linux. The variable turns off the runtime's multi-core JIT, which reads and writes that file, so the wrapper neither reads nor writes it and starts a little slower. Programs the script starts inherit it, which only changes how .NET programs start. Windows PowerShell 5.1 ignores it. An SSH host's `pwsh` does not get it, because ssh passes no variables unless the server's `AcceptEnv` allows them; set it in that host user's environment if the host starts many `pwsh` processes at once. This is a workaround until the upstream race is fixed ([#145](https://github.com/tvongaza/ValheimTesting/issues/145) tracks it); `dotnet run scripts/pwsh-startup-stress.cs` (add `--guard` for the workaround) counts startup crashes on a machine.

ValheimCLI listens on its host's loopback only, and stays that way. For an SSH host, `OpenCliTunnelAsync` starts `ssh -N -L 127.0.0.1:<local>:127.0.0.1:<cliPort>` with `ExitOnForwardFailure` and `GatewayPorts=no`; neither end is ever bound beyond loopback. A requested local port already in use is refused before ssh starts (a client would otherwise reach whatever listens there); 0 picks a free one. Checking the port and ssh binding it are separate steps, so another process can take it in between: ssh then exits (ExitOnForwardFailure) and the tunnel fails, but a readiness probe made before ssh exited could reach that process. ssh would also open the `LocalForward`, `RemoteForward` and `DynamicForward` entries an ssh config gives the host, possibly beyond loopback, and `ClearAllForwardings` would clear the tunnel's own forward too, so a host whose effective config (`ssh -G`) has any is refused. The tunnel is ready when a local connection succeeds, and disposing it stops that ssh process and no other. Connect as usual to `127.0.0.1:tunnel.LocalPort`, for example `StateWait.Connect(tunnel.Address, tunnel.LocalPort)`. A local host's CLI is its own port. A container's CLI is reachable only when the container shares the Docker host's network (`--network host`, Linux, a local Docker daemon): a published port reaches the container's own interface, never its loopback, so any other network mode is refused. Script runs pass `ClearAllForwardings=yes`, so an ssh config cannot add listeners to them.

Paths are literal: they arrive as quoted values, so spaces are fine, and they must be absolute because an SSH session's working directory is the user's home. A lock is per host, so two containers on one machine are two hosts. A bash host needs a POSIX login shell for SSH; a PowerShell host works under cmd.exe, bash or PowerShell.

CI checks every host kind: unit tests with fake processes cover the commands each kind starts, transport failures, timeouts (unknown outcome) and lock contention; the same end-to-end checks (literal values and exit codes, a timeout, lock contention, shipping a revision and files, fetching them back, following a log from an offset) run through a real local bash, Windows PowerShell and pwsh on every CI OS, and the `game hosts` job runs them over a real ssh to a throwaway sshd on localhost (bash and pwsh sessions, the loopback tunnel, an unreachable port; the client key's directory has a space in its name, and `ssh -G` reads quoted option values back as given) and into a throwaway container on the host network.

Limits: `GameLaunch.ToStartInfo` and `ClientSession.Launch` launch processes on this machine. `PinnedServerRun --inventory` runs a dedicated server on a Linux or Windows host, or on this Mac (below); in a campaign, `InteractiveClient` starts a Windows or Linux client in a remote desktop session, and a local macOS client uses `ClientSession.Launch` in the runner's GUI session. A native server-only run (Valheim 1.0.16) passed from macOS over SSH to a Linux VM: the host's lock, the runtime copied and verified on the host, the world shipped and verified there, the loopback tunnel, the owned-session identity, a confirmed save, a server-only restart, the stop by identity and the evidence fetched back. A Windows client was started in its desktop session over SSH during a native crossplay run (then through `--profile`, which the inventory and campaigns replaced). A server host in a container has not run a Valheim server this way. An `ssh` client on Windows is the system OpenSSH client. A Windows dedicated server has started headlessly from a disposable copy over SSH: BepInEx loaded, ValheimCLI listened through the loopback tunnel, the game opened its Steam server, and Ctrl+Break made it save and exit cleanly in 45 seconds. This was a focused `HostServer` smoke; the complete pinned `PinnedServerRun --inventory` Windows path still needs a scenario run.

### A server-only plan on a remote host

`PinnedServerRun` takes the inventory before the mode, so the same runner and plan run the dedicated server on another machine, for example from macOS to a remote Linux or Windows host:

```sh
dotnet run --project tests/Valheim.Testing.NativeAcceptance -- --inventory ../environments.json validate plan.json <new-output-directory>
dotnet run --project tests/Valheim.Testing.NativeAcceptance -- --inventory ../environments.json run plan.json <new-output-directory>
```

A standalone run has one actor to place, its dedicated server: the first server environment in inventory order whose host and ports can run the plan (below). Its choice and the reason, including each environment it skipped and why, are recorded as `serverEnvironment` in `result.json`, beside `inventorySha256`. When none fits, the run is refused before anything is written. Clients open on this machine; remote clients and several actors are a campaign's ([below](#a-campaign-remote-clients-and-steam-identities)). The removed `--profile` option is refused as bad usage with a message naming `--inventory` and the campaign route. A Windows server environment uses the same plan and command:

```json
{ "name": "pc-server", "host": "windows-server", "roles": ["server"], "install": "C:\\vt\\install", "runtime": "C:\\vt\\runs",
  "cliPort": 5577, "gamePort": 2466 }
```

The server host can be Linux over SSH, a Linux container (`kind: container`, `--network host`), this Linux or macOS machine (`local`) with `bash`, or Windows over SSH with PowerShell. A Mac server must be local; remote Mac server hosts remain unsupported. A Windows server host uses `"platform": "windows"` and `"shell": "powershell"` (or `"pwsh"`) over SSH. It starts the server through a short-lived scheduled task, with no Steam client needed. When the session asking is elevated (SSH as an administrator) the task is S4U and the server runs in session 0, with no signed-in desktop. In a user's own ordinary (UAC-filtered) desktop session, the one-PC case, Windows refuses S4U, so the task uses that session's interactive token at the limited run level and the server runs in that desktop session, with its console window there; signing out stops it. A session that is neither (not elevated and not a desktop session, or a user with several desktop sessions) is refused in preflight, naming why, before anything is copied. The environment's `cliPort` must be the plan's `port` (the runtime's ValheimCLI `[Server] Port`), and a `-port` in the plan's arguments (in any case, as the game reads it) must be its `gamePort`; an environment that does not fit is skipped for the next. A `crossplay` plan starts the host's server with `-crossplay`. A Linux host then needs `libpulse0` and `libpulse-mainloop-glib0`, which the game's `libparty.so` loads; step 4 checks that they are there. On Windows the crossplay preflight requires `Party.dll`; game startup proves whether it loads. The runner:

1. takes the server host's lock (`HostLock`) for the whole run; another run's lock refuses this one before anything on the host is touched;
2. copies `server.install` on the host into a new run directory, `<server.runtime>/run-<utc>-<id>/runtime`, and hashes every file there (links refused): the copy must be exactly the plan's `runtime` manifest. The plan's `runtime.source` is not read; the host's install is the runtime;
3. copies and verifies the plan's world here as usual, ships that copy to `<run>/world` (a tar checked by SHA-256 on the host) and verifies every file there again;
4. checks the host's copy as a local one is checked: the server executable (and its execute bit on Linux) and `runtimePins` (computed on the host's hashes, recorded as `runtimeGameSha256` and the rest). For crossplay, Linux checks `libparty.so` with `ldd` and Windows requires `Party.dll`. Windows also verifies the copied `winhttp.dll` and `doorstop_config.ini` form a coherent loader pair. `validate` stops here;
5. refuses a CLI port something already listens on at the host, then opens the loopback tunnel to it (`OpenCliTunnelAsync`); ValheimCLI is reached only through it and never listens beyond the host's loopback;
6. starts each boot with `HostServer.StartAsync` in `<run>/boot-N`: the plan's arguments and environment with `{runtime}` and `{world}` as the host's paths, the owned-session token in the server's environment, Doorstop and `SteamAppId` as `GameLaunch.ForServer` sets them, in its own session (`setsid`) under a small recorder on Linux; on Windows, a temporary task starts the server independently of the asking session (S4U in session 0 when elevated, otherwise in the user's desktop session), records its PID and start time and how it logged on (`boot-N.process.json` `taskLogon`), and is removed. An earlier boot's `BepInEx/LogOutput.log` moves into the boot directory first, so the startup waits for ValheimCLI's listening line in the host's log from offset 0 (`StartupEvents.CliListeningWait`), then the loaded-world push and the identity handshake (token, process ID, save root) through the tunnel;
7. stops only the process it started, by process ID and start time (`HostServerProcess`), moves the boot's logs into its boot directory and fetches it to `boot-N/` here (`game-0.log` BepInEx, `game-1.log` Unity with `-logFile {runtime}/toolkit-unity.log`; `stdout.log` and `stderr.log` only where the host records them), fetches the world copy to `host-world/`, closes the tunnel and releases the lock. The run directory on the host is never deleted automatically.

A pinned runtime manifest and `runtimePins` for a host install come from the host itself: `HostInstall.ListAsync(host, install, timeout)` returns every file's SHA-256 (`Files`, the manifest) and `HostInstall.Pins(listing)` the pins. A reply lost during the start or the stop leaves the outcome unknown (UNKNOWN, exit 3) and keeps the host's lock, because a server may still run there; remove `<lock>/owner` by hand once it has stopped. A Linux host needs bash, coreutils (`base64`, `mkfifo`, `sha256sum`, `tail`), `find`, `setsid`, `tar` and `/proc`; the [Linux server image](../../docker/linux-server/README.md) and Ubuntu have them. A Windows host needs PowerShell 5.1 or 7, OpenSSH when reached remotely, and either an elevated session (an administrator over SSH: an S4U task) or the user's own single desktop session (an interactive-token task). Its stop sends Ctrl+Break to the exact server process and kills it only if the clean quit deadline expires.

**Clients.** In a campaign, `session.OpenClient(plan.Client, "player")` (the name may be left out when the campaign declares one client) starts an owned client on the host its environment was assigned, through `InteractiveClient`: the install is its prepared disposable copy and the CLI port its environment's, the install's patchers and `installPins` are checked on the host's hashes, the client host's lock is held until teardown, its earlier BepInEx log moves aside, ValheimCLI is reached through that host's tunnel, and disposing the session stops only that client and fetches its BepInEx log and `Player.log` to `client-N/`. Every client of a campaign (with or without a dedicated server, the hosting client included) writes its evidence into its own folder `<output>/<name>/` (`client-process.json`, `client-commands.jsonl`, its kept logs and `client-N/`), because clients start at once and each launch writes files of the same names; `session.OpenClient(plan, name, directory)` with a `directory` uses that folder instead. A run with one client on this machine and no campaign keeps it in the output itself. A Linux client uses display `:0`. Before anything else on the client's host, its observed Steam identity is leased and its host checked to be signed in to it ([below](#a-campaign-remote-clients-and-steam-identities)).

CI covers the runner against a fake host (the whole lifecycle with a restart, validate, a copy that differs on the host, another run's lock, a lost start reply and an unproven stop as UNKNOWN with the lock kept, a scenario failure beside an unknown teardown as FAIL, a tunnel that cannot open, a busy port, an environment that does not fit the plan (skipped for the next one, or the run refused when none fits), a crossplay plan's launch, a crossplay host missing `libparty.so`'s libraries, and a remote client), the launch, start, stop and listing replies with fakes, and the host scripts for real: install listings and pins through local bash, Windows PowerShell and pwsh, and, on Linux, locally, over ssh to localhost and in a container in the `game hosts` job, an install shipped, copied and verified on the host, a stand-in server (a script with the server's name) started, awaited in its log from offset 0 after an earlier boot's line, stopped by identity beside a bystander that survives, and its evidence fetched back with the arguments and environment it got. The same hosts check crossplay's libraries with their own `ldd`: a stand-in `libparty.so` (a copy of the host's `true`) loads, and a copy with a dependency renamed is refused, both by the check and by a crossplay start. Natively, a server-only run from macOS over SSH to a Linux VM passed (see Limits above).

### Clients in a host's desktop session

A game client needs the logged-in user's desktop session: its display, GPU and signed-in Steam client. A process started over SSH or from a service has none of these, so `ClientSession.Launch` cannot start a client on another machine. `InteractiveClient.StartAsync(host, launch, launchDirectory, timeout, display)` starts one inside the host's existing session and returns an `InteractiveClientProcess` identified by process ID and start time, the identity an owned session checks against its adapter's reported process ID.

```csharp
var launch = GameLaunch.ForClient(@"C:\Games\Valheim", ["+connect", "server.example:2456"], hostPlatform: ClientPlatform.Windows,
    secretVariables: [plan.PasswordVariable!]);
await using var client = await InteractiveClient.StartAsync(new SshGameHost("gaming-pc", "tester@gaming-pc.example", HostShell.WindowsPowerShell), launch,
    @"C:\ValheimTesting\runs\run-42\client", TimeSpan.FromMinutes(2));
// Then wait for ValheimCLI's line with WaitForLogAsync and connect through OpenCliTunnelAsync.
```

- `GameLaunch.ForClient(install, arguments, environment, hostPlatform, secretVariables: …)` builds the same launch for a Windows or Linux install on a host, as data: `-console`, `SteamAppId`, Doorstop's variables on Linux (`LD_LIBRARY_PATH` and `LD_PRELOAD` put in front of the caller's value when the launch's environment sets one, otherwise the host session's), inherited Doorstop variables removed, and Doorstop overrides refused. The install is a path on the host; its game executable and BepInEx loader files are checked there before anything starts.
- **Windows** (a `powershell` or `pwsh` host): a scheduled task registered for the host user with "Run only when user is logged on" (an interactive token; no password is given or stored), under a unique name per launch (`ValheimTesting-client-<id>`). Starting it runs a small launcher in the desktop session, which starts the game and records its process ID and start time. The task is always removed again, whatever happened; if the removal cannot be proven, the client it started is stopped and the start fails with the `schtasks /Delete` command to run. A powershell window may flash once as the task starts.
- **Linux** (a `bash` host): `LinuxDisplay(display, waylandDisplay, runtimeDirectory, xAuthority)` names the existing session: a local X display (`:0` by default; Valheim draws through X, so a Wayland session needs its XWayland display), WAYLAND_DISPLAY and XDG_RUNTIME_DIR (`/run/user/<uid>` when it exists), XAUTHORITY (`$XDG_RUNTIME_DIR/gdm/Xauthority` or `~/.Xauthority` when not given) and the session bus. The game starts in its own session (`setsid`) under a small recorder that writes its process ID and later its exit code, so the end of the SSH session does not reach it. The host user must be the display's user. On a system whose logind kills a user's processes when the SSH session ends (`KillUserProcesses=yes`), the client ends with it.
- **macOS**: not supported from another machine. A process started over SSH is not in the logged-in user's GUI session and cannot reach its Steam client; `GameLaunch.ForClient` with a macOS host platform refuses it. Run the runner with GUI access in the Mac's unlocked desktop session and use a `local` client environment in a campaign or `ClientSession.Launch` directly.

The host refuses before anything starts, with `InteractiveSessionException`: `NoSession` when the user has no desktop session there (Windows: no process of the user in a session other than 0; more than one session is refused too, because the task could start in either), or when the X display is missing or refuses the user (checked with `xdpyinfo` where it is installed); `NoSteam` when no Steam client (`steam.exe`, or a Linux process named `steam`, on that display when its environment names one) runs as the user in it. A missing install file, an existing launch directory or a host of the wrong shell is refused as well. `StartAsync` returns once the game process exists, not when it is ready. `StopAsync` and disposal kill only that process, and only while its start time still matches, so a reused process ID is never touched; `WaitForExitAsync` waits on the host. `InteractiveClientProcess` is an `IOwnedProcess`, so it can be given to `ClientSession.Launch(plan, output, start, connect, ready)`.

The launch directory keeps the evidence: the recorded identity (its `pid` file), the game's standard output (Linux) or the launcher's error (Windows). The launch spec is not kept: the Windows launcher deletes its `spec.txt` once it has read it, as the server's launcher does, and the Linux start keeps it in memory. Environment values given to `GameLaunch.ForClient` are not secret: on Windows they pass through that file. A secret, such as the server join password named by `ClientRunPlan.PasswordVariable`, is named in `secretVariables` instead: its value is read from this process's environment at launch (a missing one is refused first), never goes on a command line and never enters the composed script, which the host's wrapper keeps in a temporary file while the script runs (and which a killed wrapper, for example after a dropped SSH connection, can leave behind). It follows the script on standard input as a line of its own, which the wrapper holds in memory and hands to the script as the variable `VT_SECRETS`; the script clears it at once. On Linux it is then exported into the game's environment, where the host user and root can read it (`/proc/<pid>/environ`). On Windows it reaches the desktop session through a `vt-secrets-<id>` file in the user's own temporary directory, which the launcher deletes as it reads and the start script deletes again when it ends; a start killed in between can leave that file (and the task, named in the error) behind. It is redacted from every reply and exception.

### Steam account leases

Steam allows one running session per account, and every client needs an account that owns Valheim. A campaign reads the account already signed in on each chosen client host during its host preflight, refuses one it cannot read and two simultaneous clients on one account, and leases each observed identity for the run. You list no Steam IDs and write no account file; there is no opt-out. Rented GPU VM clients are experimental in this campaign flow.

The lease records on the inventory's `leaseHost` stop separate runs from using the same signed-in account at once. Inventories that may use the same accounts must name the same `leaseHost` and `leaseDirectory`. These are runtime claim files keyed by an opaque hash of the identity (the account's lease key), not a handwritten account list; old released claims are pruned.

- A lease is the exclusive creation of the account's next numbered claim file under `<leaseDirectory>/<pool>/<account>` (a hard link; under PowerShell on Windows, a no-replace move), which exactly one claimer wins. Only the holder, proven by its own lease id, can release it. An account is free only when its latest claim is released: a lease never lapses on a timer (#257). It is released by its run, or by `env recover|teardown --run ID` once the run's clients are proven stopped (a crashed run's lease included), or, for a run whose machine is gone for good, by `env teardown --run ID --machine-gone`. A claim records its run id, so a run refused by a held lease is told which run holds it and the `env recover --run ID` that releases it once that run is over. A claim's second line is a far-future time, so an older runner that reads it as an expiry also sees it held. An unproven claim is `Unknown` and, if it happened, is held until a recovery releases it. A session's client holds its account as a `SteamAccountHold`, which the session acquires; the pool and its acquire and list are internal, and nothing waits or retries.
- Reports and exceptions carry the opaque lease key, never a SteamID or a credential.
- **The account playing on another computer (#257).** Leases keep the tool's own runs apart; a person (or another runner) can still be playing on the account. Starting a client on an account that plays elsewhere does not ask: Steam on the new machine logs `RecvMsgClientLoggedOff('Logged In Elsewhere')` the moment the game registers, signs out, and exits by itself a few seconds later, while the game quits before its menu with nothing about it in its own logs (seen on 5 Oct 2026; the other session is untouched). So:
  - `session check --hosts` and a campaign's preparation ask every other client host of the inventory (one the campaign runs no client on; the campaign's own client hosts already refuse any running Valheim) whether Valheim runs there as the host's user: its process list (`Valheim.exe` on Windows, by owner; `Valheim` or `valheim.x86_64` elsewhere, by user id). Another OS user's game is that user's Steam session and is left out. Where one runs, that host's signed-in account (read as the signed-in check reads it) must be none a client would use: a match is refused under the client's name, naming the host. An unreadable account, no signed-in account, a game whose owner cannot be read, or a host that cannot be asked is refused under the host's name: unknown is never a pass. A local host of another platform is another runner's machine and is not asked. Windows' `HKCU\Software\Valve\Steam\RunningAppID` is not read: on the station it was readable (0 with no game running), but whether it names Valheim for a game started directly, as the tool starts it, is unverified. Steam's `console_log.txt` is not read either: it adds only a game under another name, and after a Steam crash an entry never marked removed plus a reused process id would refuse a campaign for an unrelated process.
  - When a client starts, its host's Steam `logs/connection_log.txt` (Windows: the user's `SteamPath`, the machine's `InstallPath`, then `Program Files (x86)\Steam`; elsewhere the usual Steam directories) is followed from its length just before the launch. "Logged In Elsewhere" in it ends the start at once: "Steam account <key> is playing on another computer; Steam on this machine (<host>) has exited; when that session has ended, start Steam here and retry." A start that fails another way first (the client quit, a timeout) is named the same when the line is there. Earlier lines never count. A host with no Steam log to find only warns, and the failure is then the client's exit. The tool never answers a Steam prompt, signs in, or starts or stops Steam.
- **Steam sign-in:** sign into Steam on the client host before the run. The runner does not log into Steam or handle its password or Guard approval. A server join password is a separate plan setting and may still use `ClientRunPlan.PasswordVariable`.
- **Characters**: use a disposable local character for each account, staged on the host that runs it (the campaign's `character`). The game keeps local characters under the OS user's `characters_local` and Steam Cloud characters under the account; a test must never create or use a cloud character, and one OS user per account keeps each account's local characters apart.

CI covers both with fake processes (the commands and scripts each platform is sent, every refusal, a lost reply as an unknown outcome, a task that could not be removed, stopping by identity, contention and holder reports, release outcomes, and a canary secret that must not appear in any reply, exception, spec, argument list, report or process command line, with a negative control that finds the same value when it is passed as plain environment; the composed script, which the host writes to a file, counts as visible) and through real shells: the wrapper's secret hand-off through bash, Windows PowerShell and pwsh on every CI OS and over ssh and in a container in the `game hosts` job (the script receives each secret, and while it runs no file in the wrapper's temporary directory, the script and the upload, holds one; the negative control passes the same value as an ordinary variable and the same scan finds it in the script file); leases through bash, Windows PowerShell and pwsh on every CI OS (ten concurrent claims on three accounts give three distinct holders; a crashed holder's lease never lapses and names its run, another run's id releases nothing, the escape hatch for its run releases it, and the old holder cannot release the next run's lease; a failed run releases its lease; old claims are pruned) and, in the `game hosts` job, over ssh and in a container; the Linux start on a real X display (Xvfb) with a stand-in Steam and game, locally and over ssh to localhost (the loader and secret reach the game's environment, no command line or evidence file holds the secret, stopping leaves a bystander alone and the recorder reports the kill); the Windows task start in the Windows runner's own console desktop session, where GitHub runs the job (a stand-in Steam and game: the game runs in that session under the recorded identity, the task is gone afterwards, no secret file is left, and stopping leaves a bystander with the game's name alone); refusals of a missing display on Linux and of a Linux client on a macOS host.

Limits: natively, a Windows client has been started through `InteractiveClient` in its desktop session over SSH, during a crossplay run; a Linux client has not. Otherwise the Windows task path has been exercised on a CI runner, locally rather than over SSH, with stand-in processes. A lease store on a network file system has not been tested; it needs hard links (bash, and PowerShell on Linux and macOS) or an atomic no-replace rename (PowerShell on Windows).

A macOS campaign client uses the smaller **local** path: set its host to `{"kind":"local","platform":"macos","shell":"bash"}` and run the test runner with GUI access on that Mac's unlocked, logged-in desktop. The runner checks its Aqua session and console user before taking the client-host lock, then reuses `ClientSession.Launch` for the exact installed build, strict pins, local ValheimCLI connection, process-owned stop and copied logs. Binding sets the owned client plan's install and port from its prepared environment; the plan's CLI host must be loopback. An SSH, container or GUI-restricted sandbox cannot launch it; ordinary SSH does not place a game in the user's GUI session. The same identity lease and signed-in check run before launch, and an unproven stop retains the lease. The native check on macOS 26.5.2 and Valheim 1.0.16 loaded a pinned local world by UID with a clean character, then stopped the owned client and removed the staged character and world. For hosted local worlds on this Mac build, Valheim ignored `-savedir` and read the user's default `worlds_local`. The runner refuses a custom `hostWorld.saveDirectory` or `-savedir` before copying the fixture; use a disposable named world and let it stage into the signed-in user's default data directory. The exact world-UID check still refuses a same-named world from another directory.

#### A campaign: remote clients and Steam identities

A run with clients on other machines is a **campaign**: a manifest declares the actors (one dedicated server and named clients), each with its reviewed dependency lock and, for a client, its disposable character, and names the inventory they are placed from. A minimal one, one server and one remote client, with the inventory above:

```json
{
  "inventory": "environments.json", "world": "fixture-world", "join": "linux-box.example:2466",
  "server": { "dependencyLock": "locks/server.json" },
  "clients": { "player": { "dependencyLock": "locks/client.json",
    "character": { "store": "characters", "registeredName": "tester", "fileName": "vt-player" } } }
}
```

The character is staged into the client host user's own `characters_local` and checked against that host's Steam `userdata` for a same-named Steam Cloud character: both folders are resolved on the client host from its platform's standard paths (Windows `%USERPROFILE%\AppData\LocalLow\IronGate\Valheim\characters_local` and Steam's registered `SteamPath`, then `Program Files (x86)\Steam`; Linux `~/.config/unity3d/IronGate/Valheim/characters_local` and `~/.local/share/Steam`, `~/.steam/steam` or the Flatpak's; macOS under `~/Library/Application Support`). `session check --hosts` prints the resolved folders and refuses, naming every path it tried, when one is missing; set `charactersLocalDirectory` or `steamUserDataDirectory` on the character only for a non-standard place. Measured against what it replaces, for a server and one remote client: the old `profile.json` and `accounts.json`, plus the four plan fields that had to match them, were 32 hand-written fields; an inventory of two hosts (without `sshOptions`) and two environments plus this campaign are 33. The inventory is written once per set of machines; each further campaign is about 8 fields.

`PinnedServerRun.RunCampaignAsync(manifest, plan, clients, output, options)` runs a plan on it (the [native acceptance suite](../../tests/Valheim.Testing.NativeAcceptance/README.md#prepare-the-campaign) wraps it as `campaign check|run`); `valheim-test session check SESSION [--hosts] [--json]` reports every independent problem first. With `--hosts`, it also reads the run journal of every host the campaign touches, the lease host included. It refuses while another run is going on one of the campaign's own hosts (`LIVE`), left something there or on the lease host (`RECOVERABLE`, naming `env recover --run ID`, or `UNRECOVERABLE`), or may still be going on another machine (`UNKNOWN` with a runner elsewhere). It also refuses when a host's journal cannot be read. A run going elsewhere that shares only the lease host is not a conflict, since its lease keeps its account apart. The conflicting-use check refuses a Valheim client already running where a client of this run needs the desktop session, and any game running from a copy this run is about to use. A game elsewhere on the host is not a conflict. Each refusal names the process: as a run's when that run journalled it (with the run's state), otherwise as your own game, to stop or to describe in the inventory. The dependency locks and the character replace what used to be prepared by hand on each client install; binding fills the plan's installs, ports, runtime, world and pins from the prepared actors. Each named client, as their own steps:

1. `lease a Steam account for client player`, before anything else on the client's host (its lock, listing, port check or start) and before an attached session assumes the client. A held account refuses the client at once, naming its holder run and `env recover --run ID`; nothing waits or retries. The report's provenance records the opaque lease key and pool, never the SteamID.
2. `client player's host is signed in to Steam account <key> (signed-in check)`: the host's Steam account record must still match the identity observed in preflight (compared on the runner and never sent to a host or written to a report). Windows reads `HKCU\Software\Valve\Steam\ActiveProcess\ActiveUser` (the account id, the SteamID64's low 32 bits; 0 when none) in the SSH user's registry, which is the desktop user's; Linux and macOS read the account Steam last signed in from the host user's `loginusers.vdf` (`~/.local/share/Steam`, `~/.steam/steam`, the Flatpak's or `~/Library/Application Support/Steam`): its `MostRecent` user, or, since current clients (the macOS client in September 2026) write no `MostRecent` key, the user with the single newest `Timestamp`; a tie or no `Timestamp` is unknown. Another account or none is refused before launch, and so is a state that cannot be read: unknown is never a pass. `loginusers.vdf` records a remembered account, not a live session; it alone cannot prove Steam is running or still signed in. The client start checks process availability separately, then fails promptly if its fresh BepInEx log reports `SteamAPI_Init() failed`.
3. The lease is held for the whole run, with no renewals and no timer.
4. At teardown, after the client stopped, `release client player's Steam account lease`. A lease that was no longer this run's (a maintainer released it) fails this step. A release that cannot be proven fails it as an unknown outcome (UNKNOWN, exit 3, as an unproven lock release does); the lease is then held until `env recover --run ID` releases it. A client the scenario left open is stopped first; one whose stop could not be proven keeps its lease (`lease-kept`), because it may still run on the account, until `env teardown --run ID` proves it stopped.

A lease or signed-in check that does not finish (an unknown outcome) says where its time went, because each of those scripts first reports when it began on its host. "The shell had not begun the script after 90 s" means process start or the transport was starved, for example by a game run loading the machine. "The script began on the host, and it was still running at the deadline" means the script itself was slow. Either way the outcome stays unknown and is never taken as a lost lease.

A session client's `ClientSession` (opened, launched or attached with the lease by the session's `ClientActor`) and `InteractiveClient.StartAsync(hold, host, launch, launchDirectory, timeout)` each refuse a released or unchecked lease (the interactive start also one taken for another host) before anything starts. Dispose the session before the hold: `ReleaseAsync` throws when the lease was no longer this run's or its release is not proven.

CI covers it with the real lease scripts through this machine's shell as the lease host (bash, or Windows PowerShell): two environments whose clients run on different hosts contend for one account (six runs at once, exactly one wins, the rest are refused with the holder), a crashed holder's lease never lapses, its refusal names its run and `env recover --run`, and only the escape hatch hands it to the next run while the old holder's release fails, a released lease starts and attaches nothing through `ClientSession`, an unproven release is unknown, and the hosted runner against fake hosts: the lease is held while the client runs and released after it stopped, a held account refuses the client before its host is touched, naming the holder run, a client that fails to start still releases, one whose stop is unproven keeps its lease, the signed-in check passes only the leased account (another, none, unreadable and an unexpected reply are refused before launch), an attached client leases too; `--profile` is refused as bad usage and `--inventory` skips a server environment that does not fit the plan. The `loginusers.vdf` reading runs through bash and pwsh on Linux and macOS, the registry reading through Windows PowerShell and pwsh on Windows. An unrelated environment canary and the SteamID reach no report, evidence file, host script or lease file, while the lease key does; the negative control finds the canary once the run is given it as its name. Not run natively: two hosts signed in to one test account, where the second must be refused while the first keeps running.

**A campaign without a dedicated server** (#258 step 8b) leaves `server` and `join` out: one of its clients hosts the world and the others are its peers. The manifest's `world` is the hosted fixture. The inventory assigns only the clients; the preflight, preparation, leases, locks and retirement are the same, and `valheim-test session check SESSION [--hosts]` checks it as any campaign. The plan names its clients' sections: exactly one has a `hostWorld` section (its `world` and `worldUid` are bound to the campaign's fixture) and every other one sets `joinsHost` (`HostedCampaignPreparation.CheckHostedPlan`). `PinnedServerRun.RunCampaignAsync(manifest, plan, clients, output, HostedRunOptions<TPlan>)` runs it: the session's `Host` is the hosting client and its `Clients` are the peers, each opened on its host on its leased identity (`CampaignClients`, the same client placement a server's campaign uses). Teardown closes the session (peers, then the host, then its world), releases the leases, retires the prepared installs and characters, then releases the client hosts' locks. A hosting client on a local host gets its fixture in this machine's client data directory (as a standalone `host` run does); one on another machine gets it in its host user's own `worlds_local`, beside the `characters_local` its character was staged in (`hostWorldOn` in the provenance). There the run first refuses any entry named for the world (`<name>`, `<name>.*`, `<name>_*`, any case), journals the placement (a copy that `holds` `hosted-world`), ships the verified fixture into its own folder on that host (`<runtime>/<runId>/host-world-stage`) and checks every file, then moves the world's entries into `worlds_local`. Once no client can host it, the entries named for the world (the game's backups included) are moved out into `<runtime>/<runId>/host-world`, where they stay as the run's save, and fetched into the evidence. Nothing in the user's worlds is ever deleted. A world a killed run left there is moved out the same way by `env recover --run ID`, which refuses a journal line that does not name a `worlds_local` or a folder outside that run's directory.
